# 全栈开发工作流（文档驱动版）

## 核心设计哲学

本流程严格遵循 **"文档驱动，非上下文驱动"** 的原则：

1. **每个阶段先生成动态 Prompt 文件，再读 Prompt 文件执行**：每个 Phase 首先根据业务需求和模板约束，动态生成 `docs/prompts/phase_N_xxx_prompt.md`，然后读取该文件执行作业。AI 始终通过文件获取指令，不依赖会话上下文。

2. **模板是必要条件，不是充分条件**：模板仅定义了每个阶段的**必填结构**（输入文件列表、输出文件列表、可追溯性报告标准结构），但**不包含具体的业务指令**。实际生成的 Prompt 文件需要根据业务需求动态补充具体内容。

3. **动态 Prompt 生成规则**：
   - 读取 `docs/需求/需求输入.md` 中的技术栈字段（前端框架、后端语言、数据库）
   - 根据技术栈匹配对应的技术模板片段（见 `templates/tech_stack_templates.md`）
   - 将技术模板片段注入到 Prompt 的"动态内容补充"区域
   - 根据业务需求（需求规格说明书、详细需求模块）补充具体业务指令
   - 确保动态生成的 Prompt 既符合技术栈约束，又满足业务需求

4. **每个 Phase 必须读取指定的前序文档文件**：文件路径作为 Prompt 中唯一的输入来源，确保输入可追溯、可复现。前序文件不存在时，必须先执行前序阶段生成。

5. **每个 Phase 必须同时输出两份文档**：
   - **主产出文档**（如 `架构设计文档.md`、`API设计文档.md`、`数据库设计文档.md` 等）
   - **可追溯性报告**（`*_可追溯性报告.md`）：列出本次产出"是否符合需求、依据的需求点、是否符合 API、是否符合数据库设计"等核对结果，作为进入下一阶段的准入凭证。

6. **防幻觉**：通过"只认文件、不认上下文"的硬约束，防止 AI 在上下文过长时忽略或幻想内容。

7. **技术栈动态适配**：根据 Phase 1 收集的技术栈信息，动态调整后续阶段的 Prompt 和产出内容，支持 Vue/React/Angular 前端框架和 Python/Java/Node.js/Go 后端语言。

## 执行模式

- **AUTO_ADVANCE（默认）**：Phase 1 对话 + Phase 2~9 自动执行 + 统一汇报。
- **STEP_BY_STEP**：用户在 Phase 1 主动要求 "每个阶段都需确认" 时启用。

## Phase 8 审查-修复闭环机制

Phase 8（代码审查）采用**强制闭环**机制，确保代码质量在进入测试前达标：

```
审查 → 发现问题 → 修复 → 再审查 → 再修复 → ... → 问题清零 → 进入 Phase 9
```

**核心规则：**
1. **第 1 轮**：全量审查所有模块，生成审查报告和修复任务清单
2. **发现问题后立即修复**：根据修复任务清单，逐个修复 Critical/Major 问题
3. **第 2 轮**：增量审查（重点验证修复 + 回归检查 + 抽样）
4. **第 3 轮**：终验审查（仅审查仍有问题的模块）
5. **退出条件**：
   - Critical = 0 且 Major = 0 → 通过
   - 第 3 轮 Critical = 0 但 Major > 0 → 记录为已知风险，允许通过
   - 第 3 轮 Critical > 0 → 阻塞，报告用户决策
6. **最大轮次**：3 轮（防止无限循环）

## 可追溯性报告标准结构

每阶段产出的 `*_可追溯性报告.md` 必须包含以下四个部分：

1. **输入引用清单**：列出本阶段读取的所有输入文件（绝对/相对路径）。
2. **输出 → 输入映射表**：以表格形式展示每一项产出对应引用了输入文档中的哪一节/哪一条。
   - 示例：`REQ-001 用户登录 → API: POST /auth/login → DB: users, sessions → Code: src/auth/...`
3. **符合项核对清单**（✅/❌）：
   - 是否符合项目需求
   - 是否依据指定需求点（列出具体编号）
   - 是否符合架构设计
   - 是否符合 API 设计（若适用）
   - 是否符合数据库设计（若适用）
4. **差异与风险**：列出输入中尚未被本阶段产出覆盖的点、潜在风险。

## 开发进度矩阵状态流转规则

```
待开发 → 开发中 → 已完成 → 已审查 → 已测试 → 已发布

状态说明：
- 待开发：功能单元已定义，等待开发
- 开发中：功能单元正在开发
- 已完成：功能单元开发完成，等待审查
- 已审查：功能单元通过代码审查，等待测试
- 已测试：功能单元通过测试，等待发布
- 已发布：功能单元已部署上线

开发端标识：
- 前端：仅前端开发的功能单元
- 后端：仅后端开发的功能单元
- 全栈：需要前后端协作开发的功能单元

执行优先级：
- 后端功能单元优先于前端功能单元启动
- 前端功能单元需等待依赖的后端功能单元完成后才能启动
```

## 使用方法

当用户说 "我想从零开始做一个项目"、"帮我规划一个新项目" 等意图时调用本技能。

**每个阶段的执行流程（严格遵循）：**

1. **写动态 Prompt 文件**：根据业务需求和模板约束，动态生成 Prompt 内容，写入 `docs/prompts/phase_N_xxx_prompt.md`
   - 模板仅提供必要条件（输入文件、输出文件、标准结构）
   - 必须根据业务需求补充具体的业务指令和技术细节
   - 动态生成规则：读取技术栈 → 匹配技术模板片段 → 注入到 Prompt 中
2. **读 Prompt 文件**：读取该 Prompt 文件
3. **执行作业**：根据 Prompt 文件的指令执行

**关键约束：**
- Phase 1 与用户对话收集信息并落盘为 `需求输入.md`（包含技术栈信息）
- Phase 2~9 的 Prompt 全部以"读取前序文件 → 生成产出与可追溯性报告"的闭环自动推进
- **不依赖会话上下文**，从而防止上下文过长导致的幻觉
- **前序文件不存在时，必须先执行前序阶段生成**，不能跳过或凭空生成
- **技术栈动态适配**：根据 Phase 1 收集的技术栈信息，动态调整后续阶段的 Prompt 和产出内容
- **后端优先原则**：Phase 7B（后端开发）优先启动，Phase 7A（前端开发）在 API 定义完成后并行进行
- **Phase 8 审查闭环**：代码审查采用"审查→修复→再审查"强制闭环（最多3轮），Critical/Major 问题清零后才能进入 Phase 9。每轮审查后必须立即执行修复，不能跳过修复直接进入下一阶段

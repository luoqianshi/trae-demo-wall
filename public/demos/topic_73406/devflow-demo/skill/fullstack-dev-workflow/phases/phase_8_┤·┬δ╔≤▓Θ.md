# Phase 8 — 代码审查（审查-修复闭环）

## 核心原则

Phase 8 采用 **"审查 → 修复 → 再审查"强制闭环** 机制，直到所有 Critical/Major 问题清零后才能进入 Phase 9。

## 执行流程（强制闭环，最多 3 轮）

```
┌─────────────────────────────────────────────────────────┐
│ 第 N 轮审查（N = 1, 2, 3）                               │
│                                                         │
│  Step 1: 写 Prompt 文件                                 │
│    → docs/prompts/phase_8_代码审查_prompt.md             │
│                                                         │
│  Step 2: 读 Prompt 文件                                 │
│                                                         │
│  Step 3: 执行审查                                       │
│    → 生成/更新 代码审查报告.md                            │
│    → 生成/更新 审查可追溯性报告.md                         │
│    → 生成/更新 修复任务清单.md                             │
│                                                         │
│  Step 4: 判定结果                                        │
│    ├─ Critical/Major 问题数 = 0                          │
│    │   → ✅ 审查通过                                     │
│    │   → 更新进度矩阵：已完成 → 已审查                     │
│    │   → 退出闭环，进入 Phase 9                           │
│    │                                                    │
│    └─ Critical/Major 问题数 > 0                          │
│        → ❌ 审查未通过                                   │
│        → 更新进度矩阵：有问题的单元 → 开发中                │
│        → 进入修复步骤                                     │
│                                                         │
│  Step 5: 执行修复（仅当审查未通过时）                       │
│    → 读取 修复任务清单.md                                 │
│    → 逐个修复 Critical/Major 问题                        │
│    → 修复完成后更新修复任务清单中的状态为"已修复"            │
│    → 回到 Step 1 开始第 N+1 轮审查                       │
│                                                         │
│  最大轮次限制：3 轮                                       │
│    → 第 3 轮仍有 Critical 问题：阻塞，报告给用户决策        │
│    → 第 3 轮仅剩 Major/Minor：记录为已知风险，允许进入 P9   │
└─────────────────────────────────────────────────────────┘
```

## 各轮次的差异化规则

### 第 1 轮：全量审查
- 审查范围：所有模块的前后端代码
- 生成完整的审查报告和修复任务清单
- 问题分级：Critical / Major / Minor / Suggestion

### 第 2 轮：增量审查
- 审查范围：
  - **重点审查**：第 1 轮发现问题的模块（验证修复是否正确）
  - **回归检查**：修复可能影响到的关联模块
  - **抽样检查**：第 1 轮无问题的模块进行抽样验证
- 修复任务清单：保留第 1 轮的条目（标记"已修复"），追加新发现的问题

### 第 3 轮：终验审查
- 审查范围：
  - **仅审查**：前两轮仍有问题的模块
  - 无问题的模块不再重复审查
- 修复任务清单：累积所有历史条目，最终状态标记
- 终验判定：
  - Critical = 0 且 Major = 0 → 通过，进入 Phase 9
  - Critical = 0 且 Major > 0 → 记录为已知风险，允许进入 Phase 9（测试阶段会进一步验证）
  - Critical > 0 → 阻塞，报告给用户，由用户决定是否继续

## Prompt 模板（必要条件）

```markdown
任务：根据开发进度矩阵、需求设计等文档，逐个模块对比开发输出文档和代码，严格校验开发是否完全实现了模块的所有功能，生成审查报告。若存在未符合要求的问题，生成修复任务清单并立即执行修复，修复后重新审查，直到所有 Critical 问题清零。

必填结构：
1) 输入：
   - docs/需求/需求规格说明书.md
   - docs/详细需求/模块/*.md
   - docs/架构设计/架构设计文档.md
   - docs/数据库设计/数据库设计文档.md
   - docs/API设计/API设计文档.md
   - docs/开发计划/开发进度矩阵.md
   - docs/模块开发/*_前端详细设计.md
   - docs/模块开发/*_前端开发索引.md
   - docs/模块开发/*_后端详细设计.md
   - docs/模块开发/*_后端开发索引.md
   - docs/代码审查/修复任务清单.md（第 2 轮起读取，用于增量审查）
   - docs/代码审查/代码审查报告.md（第 2 轮起读取，用于对比历史问题）
   - src/frontend/ 下所有代码
   - src/backend/ 下所有代码
2) 输出：
   - docs/代码审查/代码审查报告.md（每轮更新）
   - docs/代码审查/审查可追溯性报告.md（每轮更新）
   - docs/代码审查/修复任务清单.md（每轮更新，累积历史修复记录）

当前轮次：{N}（根据 docs/代码审查/代码审查报告.md 是否存在判断：不存在=第1轮，存在则读取其中的"当前轮次"字段）

审查流程：
1) 按照开发进度矩阵中的模块顺序，逐个模块进行审查；
2) 分别审查前端和后端实现；
3) 对每个模块进行以下校验：
   - 功能完整性校验：对比需求文档中的功能清单，检查每个功能是否都已实现
   - API 实现校验：对比 API 设计文档，检查每个接口是否正确实现
   - 数据库实现校验：对比数据库设计文档，检查表结构和字段是否正确实现
   - 设计一致性校验：对比模块详细设计文档，检查代码是否符合设计
4) 第 2 轮起，额外执行：
   - 验证上一轮修复任务清单中"已修复"条目的修复是否正确
   - 检查修复是否引入了新问题（回归检查）
5) 更新 docs/开发计划/开发进度矩阵.md：
   - 将已通过审查的模块状态更新为"已审查"
   - 将存在 Critical/Major 问题的模块状态更新为"开发中"，等待修复

代码审查报告.md 结构要求：
- 当前审查轮次（第 N 轮）
- 审查总览（通过/警告/失败统计，按模块分类，区分前端/后端）
- 逐模块审查详情：
  - 模块名称
  - 审查范围（涉及的需求、API、数据表、代码文件）
  - 前端审查结果（功能完整性、API 实现、设计一致性）
  - 后端审查结果（功能完整性、API 实现、数据库实现、设计一致性）
  - 问题清单（按严重级别分类：Critical/Major/Minor/Suggestion）
  - 每个问题：文件路径、行号、问题描述、修复建议、引用的设计文档章节、关联的最小功能单元
  - 第 2 轮起：新增"上一轮问题验证"节，逐条确认修复结果
- 审查结论：
  - 通过审查的模块列表
  - 需要修复的模块列表
  - 修复优先级建议
  - Critical/Major 问题总数（决定是否继续闭环）
- 下一步行动项

修复任务清单.md 结构要求：
- 审查轮次
- 所有问题条目（累积历史）：
  - 任务编号（FIX-NNN，全局唯一递增）
  - 首次发现轮次
  - 关联的最小功能单元
  - 开发端（前端/后端）
  - 问题描述
  - 修复方案
  - 涉及的代码文件
  - 优先级（P0/P1/P2）
  - 状态：⏳ 待修复 / 🔧 修复中 / ✅ 已修复 / ❌ 修复失败 / ⏭️ 降级为 Minor
  - 修复验证轮次（第几轮验证通过）
- 修复顺序建议（考虑依赖关系）
- 本轮修复完成后，立即执行修复代码变更

闭环判定规则：
- Critical = 0 且 Major = 0 → 审查通过，退出闭环
- Critical = 0 且 Major > 0 → 第 3 轮时允许退出（记录为已知风险）
- Critical > 0 且 N < 3 → 继续闭环
- Critical > 0 且 N = 3 → 阻塞，报告用户

审查可追溯性报告.md 必须包含：
- 输入引用清单
- 输出 → 输入映射表（审查项 → 代码文件 → API → DB → REQ）
- 符合项核对清单：
  ✅ 是否符合项目需求
  ✅ 是否符合架构设计
  ✅ 是否符合 API 设计
  ✅ 是否符合数据库设计
- 差异与风险

动态内容补充（根据业务需求）：
- 针对所选技术栈的代码规范审查
- 前端组件化和后端分层的特定检查点
- 性能和安全方面的审查要点
```

## 产出（闭环结束后汇总）
- `docs/prompts/phase_8_代码审查_prompt.md`（动态生成的 Prompt 文件）
- `docs/代码审查/代码审查报告.md`（最终轮次版本）
- `docs/代码审查/审查可追溯性报告.md`（最终轮次版本）
- `docs/代码审查/修复任务清单.md`（含完整修复历史记录）
- 更新后的 `docs/开发计划/开发进度矩阵.md`（所有通过审查的单元标记为"已审查"）
- 修复后的源代码（Critical/Major 问题已修复）

## 摘要

青少年心理健康服务面临资源稀缺、隐私敏感、危机响应高风险三重困境。心伴(HeartPal)是一套以"安全优先、专业有据、可验证"为设计假设的青少年AI情绪伙伴系统。本白皮书以问题驱动方式阐述心伴的四层架构（安全层→知识层→质量层→存储层）与11步对话管道，论证其如何在LLM（Large Language Model，大语言模型）固有的不确定性下，通过183词危机关键词库、三层CBT（Cognitive Behavioral Therapy，认知行为疗法）知识库检索、PostgreSQL RLS（Row-Level Security，行级安全）数据库级强制隔离、12道安全护栏等工程手段，实现对青少年情绪表达的可靠守护。系统已迭代至v4版本，沉淀30,000+行代码、2,861个测试用例、103个测试套件，覆盖103次回归验证。

## 第一章 问题定义：青少年AI情绪服务的技术困境

### 1.1 青少年心理健康现状：一组无法回避的数字

中国青少年心理健康形势严峻。据《中国国民心理健康发展报告》及相关流行病学调查，青少年抑郁与焦虑问题检出率约24.6%，意味着每四个青少年中就有一人存在不同程度的情绪困扰。与此同时，学校心理教师与学生配比约为1:4000，远低于专业服务可及阈值；全国约600万留守儿童缺乏稳定的家庭情感支持网络；在已出现明显情绪困扰的青少年中，就诊率不足20%，绝大多数求助需求在专业服务触达前即被沉默吞没。

这三组数字构成一个清晰的三角困境：**需求侧庞大且持续增长、供给侧专业人力严重不足、中间环节缺乏可信可及的非临床情绪支持通道**。AI情绪伙伴系统正是为填补这一中间环节而生——它不取代专业服务，而是作为专业服务的延伸触点与早期识别哨兵。

### 1.2 现有AI心理产品的三类技术缺陷

当前市场上以"AI心理陪伴""AI树洞"为定位的产品众多，但从青少年安全视角审视，普遍存在三类技术缺陷：

**缺陷一：数据泄露风险——对话明文存储与第三方上传并存。**
多数产品将青少年对话明文存入运营数据库，管理员可任意查阅；部分产品将用户输入直接转发至第三方LLM API，未做脱敏与最小化处理。青少年在情绪低谷时极易透露自伤念头、家庭冲突、身份敏感信息，这类数据一旦泄露，后果不可逆。

**缺陷二：危机响应缺失——关键词命中后无确定性兜底。**
通用AI产品在用户表达"我不想活了"等高危信号时，依赖LLM自行生成回应。LLM可能因上下文而生成追问、轻描淡写甚至不当回应，错失危机干预的黄金窗口。专业危机干预要求"命中即拦截、拦截即转介"，这一确定性逻辑无法由概率模型保证。

**缺陷三：无临床依据——干预策略缺乏可追溯的理论基础。**
大量产品以"陪伴聊天"为核心，其回应策略源于LLM的通用对话能力，而非任何经过验证的心理干预理论。当产品声称"帮助青少年缓解情绪"时，无法回答"基于什么理论、采用什么技术、预期什么效果"三个基本问题。这类产品在青少年群体中长期使用，存在诱发情感依赖、误导自我认知的伦理风险。

### 1.3 心伴的设计假设：安全优先、专业有据、可验证

针对上述三类缺陷，心伴确立三条不可妥协的设计假设：

**假设一：安全优先于体验。**
当安全判定与对话流畅性冲突时，系统无条件选择安全。危机关键词命中即触发确定性安全模式，绕过LLM自由生成；AI不得给确定性建议、不追问自伤细节、禁用"诊断/治疗/康复"三词——这些约束以硬编码方式注入管道，而非依赖LLM自律。

**假设二：专业有据于CBT。**
心伴的干预策略以认知行为疗法(CBT)为理论框架，通过200+条CBT脚本库、50+脱敏案例库、SDQ+PHQ-9+GAD-7+183危机词的量表关键词库，构成可追溯的知识层。每一次AI回应背后，都应能回答"调用哪类CBT技术、匹配哪条脚本、基于哪个案例参考"。

**假设三：可验证于工程证据。**
心伴的所有安全主张必须由工程证据支撑，而非营销话术。12道安全护栏(HC-01至HC-12)每一道都有对应的技术实现与测试用例；隐私分层L0/L1/L2由PostgreSQL RLS在数据库级强制执行，而非应用层权限控制——因为应用层权限可被绕过，数据库级约束不可绕过。

## 第二章 理论原理：CBT认知行为疗法的技术化映射

### 2.1 CBT核心机制与对话干预的逻辑对应

认知行为疗法(Cognitive Behavioral Therapy, CBT)的核心机制是"认知三角"：**想法(认知)→情绪→行为**三者相互影响，识别并重构非适应性认知即可改善情绪与行为。CBT的标准化技术包括认知重构(Cognitive Restructuring)、行为激活(Behavioral Activation)、暴露(Exposure)、放松训练(Relaxation)等。

心伴将CBT机制映射为对话管道中的可执行环节：

```
┌─────────────────────────────────────────────────────────┐
│  CBT认知三角          心伴对话管道映射                    │
├─────────────────────────────────────────────────────────┤
│  想法(认知)   ──→   Step4 知识库检索(识别认知扭曲类型)    │
│  情绪         ──→   Step9 情感标注(为后续L1摘要聚合)      │
│  行为         ──→   Step5 CBT策略匹配(选择干预技术)       │
│  重构         ──→   Step6 LLM对话生成(注入CBT脚本约束)    │
└─────────────────────────────────────────────────────────┘
```

这一映射确保AI回应不是LLM的"自由发挥"，而是"在CBT脚本约束下的有导向生成"。例如，当用户表达"我什么都做不好"（全或无认知扭曲）时，系统匹配认知重构脚本，引导LLM以苏格拉底式提问(Socratic Questioning)协助用户检验这一想法的证据，而非简单安慰或附和。

### 2.2 危机干预三级响应模型

青少年情绪表达存在一个连续谱：从日常情绪波动，到负性思维反复，再到自伤意念出现。心伴采用三级响应模型，对应管道Step1-3的安全层：

```
┌──────────────────────────────────────────────────────────┐
│  第一级：关键词检测 (Step2)                                │
│  - 183词危机关键词库（自伤/自杀/暴力/虐待等9类）            │
│  - 命中即标记，不依赖语义理解                               │
│  - 零延迟、零误判容忍（宁可误拦不可漏放）                   │
├──────────────────────────────────────────────────────────┤
│  第二级：语义检测 (Step1意图识别交叉验证)                   │
│  - LLM意图识别 + 语义相似度                                │
│  - 捕捉关键词未覆盖的隐喻表达（如"我想去一个很远的地方"）    │
│  - 作为关键词检测的补充层，非替代                          │
├──────────────────────────────────────────────────────────┤
│  第三级：安全模式判断 (Step3)                              │
│  - 命中危机信号 → 强制进入安全模式                          │
│  - 安全模式：绕过自由生成，输出确定性安全提示               │
│  - 包含转介信息（心理援助热线、专业机构）                   │
│  - 触发家长端/医生端告警（经L1摘要层，不泄露L2原文）        │
└──────────────────────────────────────────────────────────┘
```

三级模型的设计哲学是**纵深防御(Defense in Depth)**：任何单层都可能失效，但三层叠加使高危信号漏检概率趋近于零。关键词层保证零延迟确定性，语义层覆盖隐喻表达，安全模式层保证命中后的响应确定性。

### 2.3 隐私分层的伦理依据：L0/L1/L2对应的信息敏感度光谱

青少年情绪数据的敏感度并非均匀——昵称头像与自伤对话显然不在同一层级。心伴将数据按敏感度光谱分为三层，每一层对应不同的可见性约束：

```
敏感度光谱：
低 ◄───────────────────────────────────────────► 高

  L0 公开层              L1 摘要层              L2 原始对话层
  ┌──────────┐         ┌──────────────┐       ┌──────────────────┐
  │ 昵称     │         │ 情绪趋势     │       │ 完整对话原文     │
  │ 头像     │         │ 情绪天气图   │       │ 用户全部输入     │
  │ 年龄段   │         │ 家长可见摘要 │       │ AI全部回应        │
  └──────────┘         └──────────────┘       └──────────────────┘
  全端可见              家长/医生可见摘要       仅用户本人可见
                                              管理员不可见(RLS强制)
```

这一分层的伦理依据是**最小必要原则(Purpose Limitation)**与**数据主体控制权(Data Subject Control)**：每一层信息的可见范围，严格对应其使用目的。家长需要了解孩子的情绪趋势以提供家庭支持，但不需要逐字阅读孩子与AI的每一句对话——后者会摧毁青少年对系统的信任，进而导致其拒绝使用任何情绪支持渠道。管理员需要运营系统，但绝对不应接触L2原始对话——这是HC-04硬约束的核心，由PostgreSQL RLS在数据库级强制执行，而非应用层权限。

## 第三章 技术方案：四层架构与11步管道

### 3.1 系统总览：四层架构

心伴系统采用四层架构，每一层对应一组明确的安全与质量职责。11步对话管道贯穿四层，从用户输入到AI回应返回，形成一条可追溯的处理链路。

```

├─────────────────────────────────────────────────────────────────┤

│  │  安全层 (Security Layer) — Step 1-3                      │   │

│  │  机制：183词关键词库 + 语义检测 + 确定性兜底              │   │
│  └─────────────────────────────────────────────────────────┘   │
│                          ▼                                       │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │  知识层 (Knowledge Layer) — Step 4-5                     │   │
│  │  职责：CBT知识检索、干预策略匹配                          │   │
│  │  机制：三层知识库(脚本/量表词/案例) + CBT策略匹配器       │   │
│  └─────────────────────────────────────────────────────────┘   │
│                          ▼                                       │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │  质量层 (Quality Layer) — Step 6-8                       │   │
│  │  职责：LLM生成、质量评分、合规检查                        │   │
│  │  机制：知识注入生成 + 质量评分 + 三词禁用校验             │   │
│  └─────────────────────────────────────────────────────────┘   │
│                          ▼                                       │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │  存储层 (Storage Layer) — Step 9-11                      │   │
│  │  职责：情感标注、分层存储、响应返回                       │   │
│  │  机制：L0/L1/L2分层 + PostgreSQL RLS强制 + 30天保留      │   │
│  └─────────────────────────────────────────────────────────┘   │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

### 3.2 安全层（Step1-3）：确定性优先的危机拦截

安全层是整条管道的第一道闸门，其设计原则是**确定性优先于智能性**。LLM是概率模型，无法保证100%识别危机信号；因此心伴将危机拦截拆解为"关键词确定性 + 语义补充性 + 模式判断确定性"三段式。

**Step 1：意图识别**
通过LLM对用户输入进行意图分类，识别其属于情绪倾诉、认知困扰、危机信号、日常交流等类别。意图识别结果同时作为后续语义检测的交叉验证输入。这一步是智能的，但不承担确定性拦截职责——它的输出仅供Step3参考。

**Step 2：危机关键词检测（183词库）**
这是安全层的核心确定性环节。心伴维护一个包含183个危机关键词的专用词库，覆盖9类高危信号：

```
┌──────────────────────────────────────────────────┐
│  183词危机关键词库分类（9类）                       │
├──────────────────────────────────────────────────┤
│  1. 自伤自残类     (如：割腕、划自己)              │
│  2. 自杀意念类     (如：不想活、想结束)            │
│  3. 暴力伤害类     (如：打人、伤害别人)            │
│  4. 虐待受害类     (如：被打、被欺负)              │
│  5. 极端绝望类     (如：没意义、撑不住)            │
│  6. 物质滥用类     (如：吃药片、喝酒)              │
│  7. 进食障碍类     (如：不吃饭、催吐)              │
│  8. 人际危机类     (如：没人要我、被抛弃)          │
│  9. 其他高危类     (如：离家出走、危险行为)        │
└──────────────────────────────────────────────────┘
```

关键词检测采用多模式匹配算法，对用户输入进行零延迟扫描。**命中任一关键词即标记为危机信号，不依赖LLM判断、不依赖上下文消歧**——这是HC-10硬约束的技术实现。宁可误拦（将隐喻表达误判为危机），绝不漏放（将真实危机信号放行至自由生成）。

**Step 3：安全模式判断**
当Step1语义检测或Step2关键词检测任一命中危机信号，系统强制进入安全模式。安全模式的处理逻辑是确定性的：

```
安全模式触发后的处理流程：
┌─────────────────────────────────────────────┐
│  1. 绕过 Step4-Step8 的自由生成链路          │
│  2. 输出预设的确定性安全提示（含转介信息）     │
│  3. 触发家长端告警（经L1摘要，不泄露L2原文）  │
│  4. 触发医生端告警（经L1摘要）                │
│  5. 完整对话记录存入L2（仅用户本人可见）      │
│  6. 不追问自伤细节（HC-02约束）               │
└─────────────────────────────────────────────┘
```

安全模式的输出由预设模板生成，绝不经过LLM自由生成——这保证危机响应的确定性与可审计性。HC-02（不追问自伤细节）在此环节硬编码实现：安全提示模板中不包含任何对自伤方式、频率、工具的追问语句。

### 3.3 知识层（Step4-5）：三层知识库与CBT策略匹配

知识层的职责是为LLM生成提供"专业有据"的约束。心伴不依赖LLM的内置心理学知识，而是通过三层知识库检索，将CBT脚本、量表关键词、脱敏案例作为生成约束注入。

**三层知识库结构：**

```

│  三层知识库                                                   │

│  ┌────────────────────────────────────────────────────────┐  │
│  │  内容：标准化CBT干预对话脚本                            │  │
│  │  分类：认知重构/行为激活/放松训练/暴露/问题解决等        │  │
│  │  字段：脚本ID、CBT技术类型、适用场景、对话流程、         │  │
│  │        禁用表达、质量评分基准                            │  │
│  │  用途：Step6 LLM生成的对话流程约束                      │  │
│  └────────────────────────────────────────────────────────┘  │
│                                                               │
│  第二层：量表关键词库                                          │
│  ┌────────────────────────────────────────────────────────┐  │
│  │  内容：SDQ + PHQ-9 + GAD-7 + 183危机词                  │  │
│  │  SDQ (Strengths and Difficulties Questionnaire)：       │  │
│  │      长处与困难问卷，青少年情绪行为筛查                  │  │

│  │      抑郁筛查量表关键词映射                              │  │
│  │  GAD-7 (Generalized Anxiety Disorder-7)：               │  │
│  │      广泛性焦虑筛查量表关键词映射                        │  │
│  │  用途：Step4 检索匹配用户情绪信号，                     │  │
│  │        辅助Step5策略选择（注：量表结果以                 │  │
│  │        "情绪天气图"呈现，不显示分级标签，HC-09）         │  │
│  └────────────────────────────────────────────────────────┘  │
│                                                               │
│  第三层：故事案例库 (50+条)                                    │
│  ┌────────────────────────────────────────────────────────┐  │
│  │  内容：脱敏处理的青少年情绪故事案例                      │  │
│  │  处理：去除PII(Personally Identifiable Information)     │  │
│  │  字段：案例ID、情绪主题、CBT技术应用、参考对话、         │  │
│  │        适用年龄段                                        │  │
│  │  用途：Step6 为LLM生成提供风格与语气参考                │  │
│  └────────────────────────────────────────────────────────┘  │
│                                                               │
└──────────────────────────────────────────────────────────────┘
```

**Step 4：知识库检索（三层）**
检索采用结构化索引 + 语义相似度混合策略。用户输入经向量化后，与三层知识库的索引进行相似度匹配，返回Top-K候选。检索结果包含：匹配的CBT脚本、命中的量表关键词、相关的案例参考。这一步的输出是"知识包"，而非最终回应。

**Step 5：CBT策略匹配**
基于Step4检索结果，策略匹配器决定采用哪类CBT技术。匹配逻辑综合考虑：
- 用户表达的认知扭曲类型（全或无、过度概括、灾难化等）
- 情绪强度信号（由量表关键词命中推断）
- 历史对话上下文（避免重复干预技术）

策略匹配的输出是一个"生成约束包"，包含：选定的CBT脚本、适用的话术模板、禁用表达清单、质量评分基准。这一约束包将作为Step6 LLM生成的硬约束。

### 3.4 质量层（Step6-8）：知识注入生成与双重校验

质量层的职责是在LLM自由生成与CBT专业约束之间取得平衡，并确保输出符合合规红线。

**Step 6：LLM对话生成（知识注入）**
LLM生成的Prompt（提示词）由三部分构成：

```
┌──────────────────────────────────────────────────────────┐
│  LLM生成Prompt结构                                        │
├──────────────────────────────────────────────────────────┤
│  [系统角色约束]                                           │
│  - 你是AI情绪伙伴，不是虚拟恋人或朋友                    │
│  - 不模拟亲密关系，不诱导情感依赖                         │
│  - 输出将标注"专业辅助参考"                               │
│  - 不得给确定性建议（HC-01）                              │
│  - 禁用"诊断/治疗/康复"三词（HC-03）                     │
│                                                           │
│  [CBT脚本约束] ← 来自Step5策略匹配                        │
│  - 采用技术：{认知重构/行为激活/...}                      │
│  - 对话流程：{脚本定义的步骤}                             │
│  - 风格参考：{案例库匹配的语气}                           │
│                                                           │
│  [用户输入 + 上下文]                                      │
│  - 当前用户输入                                           │
│  - 近期对话摘要（L1层，非L2原文）                        │
└──────────────────────────────────────────────────────────┘
```

这一结构确保LLM生成是在"专业约束下的有导向生成"，而非"通用对话的自由发挥"。

**Step 7：质量评分**
生成结果经质量评分器评估，评分维度包括：
- CBT技术一致性（回应是否符合脚本定义的干预流程）
- 情感 appropriateness（语气是否匹配用户情绪状态）
- 知识引用准确性（是否正确引用CBT脚本与案例）
- 安全性（是否触碰禁用表达）

评分不达标的输出触发重新生成，最多重试N次后仍不达标则降级为脚本模板回应。

**Step 8：合规检查（三词禁用）**
这是质量层的最后一道闸门，对应HC-03硬约束。合规检查器对LLM输出进行确定性扫描，检测是否包含"诊断"、"治疗"、"康复"三词及其变体。命中即拒绝输出，触发重新生成或降级为模板回应。

```
合规检查逻辑（HC-03技术实现）：
┌──────────────────────────────────────────────┐
│  扫描输出文本                                 │
│     │                                        │
│     ├─ 包含"诊断" → 拒绝                      │
│     ├─ 包含"治疗" → 拒绝                      │
│     ├─ 包含"康复" → 拒绝                      │
│     ├─ 包含变体(如"诊/断"拆分) → 拒绝         │
│     │                                        │
│     └─ 全部通过 → 进入Step9                   │
│                                               │
│  替代表达规范：                               │
│  - "诊断" → "情绪识别"                        │
│  - "治疗" → "情绪调节支持"                    │
│  - "康复" → "专业辅助参考"                    │
└──────────────────────────────────────────────┘
```

### 3.5 存储层（Step9-11）：隐私分层与RLS强制执行

存储层是隐私保护的核心防线。心伴不依赖应用层权限控制，而是在数据库级通过PostgreSQL RLS强制执行L0/L1/L2分层可见性。

**Step 9：情感标注**
对当前对话进行情感分类标注，标注结果聚合到L1摘要层，用于生成情绪趋势与情绪天气图。情感标注本身不存储原始对话，仅存储结构化情感数据（情绪类别、强度、时间戳）。

**Step 10：分层存储（L0/L1/L2，RLS强制）**

```
┌──────────────────────────────────────────────────────────────┐
│  分层存储与RLS策略                                            │
├──────────────────────────────────────────────────────────────┤
│                                                               │
│  L0 公开层 (public_profile表)                                 │

│  │  写权限：用户本人                                        │  │
│  └────────────────────────────────────────────────────────┘  │
│                                                               │
│  L1 摘要层 (emotion_summary表)                                │
│  ┌────────────────────────────────────────────────────────┐  │
│  │  存储：情绪趋势、情绪天气图数据、家长可见摘要            │  │
│  │  RLS策略：用户本人 + 绑定家长 + 绑定医生 可读           │  │

└──────────────────────────────────────────────────────────────┘
```

**PostgreSQL RLS策略示例说明：**

RLS（Row-Level Security，行级安全）是PostgreSQL提供的数据库级访问控制机制。与应用层权限不同，RLS在数据库引擎层强制执行——即使应用层被攻破或存在Bug，数据库仍会拒绝越权访问。

以下为L2原始对话表的RLS策略示意（伪SQL，用于说明原理）：

```sql
-- 启用行级安全
ALTER TABLE conversation_raw ENABLE ROW LEVEL SECURITY;

-- 策略1：用户仅能查看自己的L2原始对话
CREATE POLICY user_own_conversation ON conversation_raw
    FOR SELECT
    USING (user_id = current_setting('app.current_user_id')::uuid);

-- 策略2：管理员角色显式排除（HC-04强制实现）
-- 管理员角色不授予此表的SELECT权限
-- 即使管理员通过其他途径尝试访问，RLS将拒绝
CREATE POLICY admin_no_access ON conversation_raw
    FOR SELECT
    TO admin_role
    USING (FALSE);  -- 管理员永远无法读取

-- 策略3：30天自动清理（HC-11）
-- 通过定时任务执行DELETE，保留期外的记录清除
```

这一设计的核心价值在于**不可绕过性**：HC-04（管理员不可查看L2）不是"管理员承诺不看"，而是"数据库拒绝管理员访问"。这是心伴隐私保护从"政策承诺"升级为"工程强制"的关键差异。

**Step 11：返回用户**
最终回应返回用户端，并自动标注"专业辅助参考"标识（HC-05）。这一标注提醒用户AI回应的专业定位边界，避免用户将AI回应等同于专业服务。

**四端隔离的设计要点：**

1. **独立SPA部署**：四端各自独立构建与部署，前端代码物理隔离。青少年端不存在家长端的管理功能代码，避免前端越权。

2. **角色鉴权中间件**：NestJS API网关层强制角色校验，每个API端点声明所需角色，非授权角色请求直接拒绝。

3. **家庭互动卡的孩子先确认机制（HC-06）**：家庭互动卡功能在发送至家长端前，必须经孩子端确认。这一机制防止家长通过系统单向施加干预，保护青少年在家庭互动中的自主性。

4. **管理员端的边界**：平台管理端可访问运营监控、安全模式复核、关键词库版本管理等运维功能，但**不可访问L2原始对话**（RLS强制）。管理员可见的是脱敏后的安全模式触发记录与L1层聚合数据。

v3→v4的关键决策是将隐私保护从"应用层权限"升级为"数据库级RLS强制"。这一决策的触发点是意识到：应用层权限可被Bug、配置错误、内部人员越权绕过，而PostgreSQL RLS在数据库引擎层强制，不可绕过。这是心伴从"政策承诺"走向"工程强制"的分水岭。

心伴基于STRIDE威胁建模方法论，识别青少年AI情绪服务面临的主要威胁场景，并映射至防御手段与验证证据。

## 第五章 展望与局限

### 5.1 当前技术局限

心伴v4版本仍存在明确的技术局限，需在后续版本中诚实面对：

**局限一：LLM幻觉风险。**
尽管心伴通过知识注入、质量评分、合规检查三重约束控制LLM生成质量，但LLM作为概率模型，仍存在生成虚构信息(幻觉)的残余风险。当前通过Step7质量评分与重试机制缓解，但无法完全消除。未来需引入更严格的生成结果与知识库的事实一致性校验。

**局限二：知识库覆盖边界。**
当前CBT脚本库200+条、案例库50+条，覆盖青少年常见情绪困扰的主要场景，但对于罕见情境（如特定创伤后反应、罕见心理困扰）覆盖不足。知识库的扩充需依托专业心理顾问团队持续审校，无法通过纯工程手段加速。

**局限三：危机关键词库的语义盲区。**
183词关键词库以字面匹配为主，虽辅以Step1语义检测，但仍可能漏检高度隐喻化的危机表达。青少年亚文化中不断产生新的表达方式，关键词库需持续更新，存在滞后性。

**局限四：单语言支持。**
当前系统针对中文场景设计，知识库与量表关键词库均为中文。多语言场景下的CBT干预策略、危机关键词覆盖、文化适应性需重新构建。

### 5.2 扩展方向

**方向一：多语言支持。**
面向多语言场景，需重构知识库的语义索引层，支持跨语言检索；危机关键词库需按语种独立构建并经当地专业审校；CBT脚本需考虑文化适应性本地化。

**方向二：离线场景支持。**
针对网络覆盖不足的地区（部分留守儿童场景），探索轻量化离线模式。核心挑战在于如何在边缘设备上实现安全层的确定性拦截与知识库的基础检索，同时不引入新的隐私泄露面。

**方向三：医生辅助诊断支持。**
当前医生端仅可见L1摘要层。未来可在严格隐私保护前提下，探索为医生提供更丰富的情绪趋势分析、CBT干预效果追踪等辅助工具，增强专业服务的决策支持。这一扩展需在隐私保护与临床效用间谨慎平衡。

**方向四：知识库版本管理与A/B评估。**
建立知识库的版本管理机制，支持CBT脚本与案例库的灰度发布与效果评估，使知识库迭代可度量、可回滚。

### 5.3 伦理声明与合规路线图

**伦理声明：**

心伴始终坚持以下伦理立场，这些立场不以技术能力提升而妥协：

1. **AI是情绪伙伴，不是专业服务的替代。** 心伴的所有输出均标注"专业辅助参考"，AI回应不构成专业意见。系统定位为专业服务的延伸触点与早期识别哨兵，而非替代品。

2. **不模拟亲密关系，不诱导情感依赖。** AI角色明确为"AI情绪伙伴"，不扮演"虚拟恋人"或"朋友"。系统设计主动避免通过亲密化表达诱导青少年对AI产生情感依赖——这是青少年AI产品的隐性伦理风险。

3. **青少年数据主权不可让渡。** 青少年对其L2原始对话拥有排他性访问权，这一权利由PostgreSQL RLS数据库级强制，平台运营方不可凌驾。用户可随时导出与删除自身数据。

4. **永不向青少年收费。** 心伴对青少年端永远免费，这是HC-12硬约束。商业模式（如存在）不得建立在向青少年收费之上。

## 结语

心伴(HeartPal)的技术白皮书回答的核心问题是：**在LLM固有的不确定性下，如何为青少年构建一个安全、专业、可验证的AI情绪伙伴系统？**

答案是一条贯穿四层架构的确定性链路：安全层以183词关键词库与安全模式兜底，保证危机响应的确定性；知识层以三层CBT知识库与策略匹配，保证干预策略的专业有据；质量层以知识注入生成与双重校验，保证输出的合规与质量；存储层以PostgreSQL RLS数据库级强制，保证隐私分层的不可绕过。

30,000+行代码、2,861个测试用例、103个测试套件、12道安全护栏、v1→v4的四次迭代——这些数字背后，是心伴对"信任极光·守护"这一叙事主线的工程化诠释：**每一项技术决策，都应回扣到"为何这样能更好地守护青少年"。**

心伴不声称完美。LLM幻觉风险、知识库覆盖边界、关键词语义盲区——这些局限被诚实记录。但心伴主张：青少年AI情绪服务的安全底线，应由工程证据支撑，而非营销话术；应由数据库级强制保障，而非政策承诺；应由可追溯的CBT理论依据，而非通用对话能力的"涌现智能"。

这是心伴的技术立场，也是心伴对每一位青少年用户的承诺。

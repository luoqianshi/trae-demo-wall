# 食刻搭子后端设计说明

这份后端设计基于当前 HTML 小程序原型，不限定真实开发平台。它的作用是说明：如果这个创意从原型变成真实产品，背后需要哪些数据、服务和接口来支撑。

## 后端整体思路

前端负责展示页面和收集用户操作，后端负责保存数据、分析用户状态、返回推荐结果。用户打开产品后，前端把当前位置、场景选择、预算偏好和已有食材发送给后端；后端再结合商家数据和推荐规则，返回“自己做、点外卖、吃食堂、混合搭配”等方案。

## 核心服务模块

| 模块 | 负责内容 | 对应原型功能 |
|---|---|---|
| 用户服务 | 保存用户预算、口味、忌口、生活模式 | 我的页面、场景模式 |
| 食材服务 | 管理食材名称、数量、保质期 | 食材页、三日消耗计划 |
| 定位服务 | 接收用户定位，判断所在区域 | 首页定位、附近页 |
| 商家服务 | 返回周边商家、食堂窗口、价格、距离 | 附近商家、校园食堂窗口 |
| 推荐服务 | 计算最合适的饮食方案 | 首页推荐、帮我选 |
| 记录服务 | 记录饮食历史、预算消耗、外卖次数 | 本周饮食观察 |
| 拼单服务 | 保存投票、拼单人数、多人选择 | 室友投票、拼单机会 |

## 推荐逻辑

推荐服务可以先使用简单规则，不必一开始就做复杂 AI。

| 判断因素 | 规则 |
|---|---|
| 食材保质期 | 2 天内到期的食材优先进入推荐 |
| 用户预算 | 预算剩余较少时优先推荐食堂、低价商家、已有食材 |
| 时间紧张 | 当前场景为赶时间时，优先推荐配送快或距离近的选择 |
| 健康偏好 | 用户选择健康模式时，降低高油高盐外卖权重 |
| 距离 | 商家越近，得分越高 |
| 拼单机会 | 满减差额较小或多人投票时，提高拼单方案得分 |

推荐分可以简单表示为：

```text
合适度 = 预算分 + 时间分 + 食材利用分 + 健康分 + 距离分 + 拼单分
```

## 主要接口设计

| 接口 | 方法 | 作用 |
|---|---|---|
| `/api/user/profile` | GET | 获取用户预算、偏好和生活模式 |
| `/api/foods` | GET | 获取用户食材库存 |
| `/api/foods` | POST | 添加新食材 |
| `/api/merchants/nearby` | GET | 根据定位获取附近商家和食堂窗口 |
| `/api/recommendations` | POST | 根据用户状态生成推荐方案 |
| `/api/records/weekly` | GET | 获取本周饮食观察 |
| `/api/votes` | POST | 创建拼单投票 |
| `/api/votes/{id}` | PATCH | 参与投票 |

## 原型中的后端流程

1. 用户进入首页，前端请求用户信息、食材库存和附近商家。
2. 后端根据定位返回周边商家、校园食堂和便利店。
3. 推荐服务计算“自己做、直接外卖、混合搭配”的合适度。
4. 前端展示推荐结果和推荐理由。
5. 用户添加食材或参与投票后，后端更新数据。
6. 记录服务生成本周预算、外卖次数和饮食观察。

## 展示时可以这样解释

这个作品虽然是 HTML 原型，但它已经设计了真实产品所需的后端结构。前端负责让用户看到推荐和完成操作，后端负责管理用户、食材、商家、推荐、预算和拼单数据。这样设计后，产品不只是一个静态页面，而是具备继续开发成真实应用的基础。

### 1. Demo 简介

#### 是什么

**多端产品矩阵**：微信小程序（双角色）+ Web 管理后台 + 品牌官网，三位一体的 AI 驱动婚礼场景设计协作平台。

- **微信小程序**：新人端 + 策划师端双角色系统，原生微信生态
- **Web 管理后台**：基于 Vue3 的内容与业务管理端
- **品牌官网**：面向公域流量的展示与获客站点
- **AI 交互式 Demo**：四份纯前端 HTML 单文件，浏览器直接打开即可体验

#### 面向谁

| 角色 | 核心诉求 |
|---|---|
| **准新人** | 签约前看到效果、预算分配透明、不被忽悠 |
| **婚礼策划师 / 中小工作室** | 快速出方案、控制成本利润、一人多单并行 |
| **平台运营方** | 案例沉淀、订单流转、合同与排期统一管理 |

#### 主要功能（3 个核心）

**① AI 设计对话 + 渐进式需求提取**（新人端）
- 多轮自然语言对话，AI 自动识别 8 类话题（场地 / 风格 / 预算 / 道具 / 流程 / 婚期 / 人数 / 偏好）
- 对话中智能推送匹配案例卡片，所见即所得
- 自动生成结构化方案（场地 / 风格 / 道具清单 / 报价）

**② AI 方案生成 + 成本利润引擎 + 双层定价**（策划师端）
- 一键将新人对话沉淀为可执行方案
- 内置道具折旧、花材底价、人工成本的「成本引擎」
- 同时输出对新人报价（含利润）和对策划师成本视图（透明拆解）

**③ 业务运营闭环**（双端联动）
- 方案确认 → 自动生成订单 + 合同 → 排期日历冲突检测 → 待办事项 + 亲友团任务下发
- 策划师端工作台 Dashboard 实时呈现接单 / 收入 / 待跟进线索 / 近期婚礼进度
- 管理后台 10 大模块（仪表盘 / 案例 / 文章 / 图片 / 订单 / 客户 / 酒店 / 道具 / 合同 / 线索）

### 2. Demo 创作思路

#### 灵感来源

婚礼策划是高度依赖个人经验的「手工艺行业」。我观察到身边朋友筹备婚礼时的两个极端：
- **新人侧**：签约前看不到效果，全凭策划师口头描述和参考图想象，沟通成本极高
- **策划师侧**：反复跑场地、手写方案、靠记忆估道具量，一个人最多同时管 3-4 单

而 LLM 和生图模型在 2025 年已经成熟，但婚礼行业几乎没有专属的数字化工具——通用项目管理软件无法理解「道具折旧」「花材底价」「场景设计」等行业概念。

#### 想解决的痛点

| 真实存在的痛点 | 现状 | 期望 |
|---|---|---|
| 签约前看不到效果 | 口头描述 + 参考图 | 所见即所得，AI 渲染场地效果图 |
| 报价靠拍脑袋 | 策划师经验估算 | 成本结构透明、利润可控 |
| 一人多单瓶颈 | Excel + 脑子记 | AI 一键出方案，产能放大 10 倍 |
| 道具库存靠记忆 | 纸质清单 | 数字化管理 + 市场比价参考 |

#### 为什么做这个方向

**判断**：
1. **市场空白**：武汉每年 ~8 万对新人，全国 ~700 万对，婚礼策划市场 ~2000 亿元，却无专属 SaaS 工具
2. **AI 价值密度高**：婚礼方案的「理解需求 → 结构化输出 → 可视化」流程正好是 LLM 擅长的场景
3. **付费意愿强**：B 端策划师有明确效率诉求，C 端新人有体验升级诉求，双边市场可平衡

**取舍**：
- 优先做 AI 设计对话 + 成本引擎（核心价值），暂缓支付在线化（先跑通业务闭环再商业化）
- 双角色系统而非单一新人人格：策划师是付费方和决策方，必须同时赋能
- 选择微信小程序作为主战场：低门槛、社交裂变、与新人画像高度重合

### 5. 经验总结与开发心得（附加部分）

#### 5.1 TRAE 在多端项目中的价值

本项目横跨微信小程序、Vue3 管理后台、纯前端官网、云函数 4 类技术栈，TRAE 的核心价值体现在：

- **跨文件上下文理解**：修改一个云函数时，TRAE 能同时理解小程序前端调用方和管理后台 SDK 调用方，避免接口断裂
- **设计令牌一致性**：通过 TRAE 维护 app.wxss / variables.css / demos 内联 CSS 的三套样式系统色值同步（暖白 #FFF9F2 + 香槟金 #D4AF37）
- **架构审查能力**：阶段三结束后，用 TRAE 对后端架构做了一次「实施真源审查」，识别出 14 处 utils.js 重复、缺少索引 / 事务等技术债

#### 5.2 踩过的坑（已沉淀到 project_memory）

| 坑 | 根因 | 解决方案 |
|---|---|---|
| admin-api 云函数 EXCEED_AUTHORITY | 权限未设置为「所有用户可调用」 | 云开发控制台修改权限 + 部署时勾选「安装依赖」 |
| 聊天气泡溢出 | `justify-content: flex-end` 在 flex 容器中失效 | 改用 `margin-left: auto` + `max-width: 85%` |
| WXSS 中文类名不识别 | 微信小程序 WXSS 不支持中文类名 | 全部改为英文类名，design token 通过 CSS 变量传递 |
| SVG `<symbol>` 渲染失败 | `<defs>` 内 `<symbol>` 标签未正确闭合 | 严格遵循 `<defs><symbol>...</symbol></defs>` 嵌套 |
| 真机调试样式丢失 | CSS 语法错误（`.var(--text-primary)` 多了点）+ 共享样式写在页面级 wxss | 修正语法 + 共享样式统一上提到 app.wxss |

#### 5.3 增量演进优于全量重构

项目坚持「文档先行 → 增量修改 → 80% 对齐即收手」的策略，避免无谓重构。例如阶段三结束时的后端架构审查发现代码与文档对齐度 ~80%，选择沉淀「真源文档」记录实际实现而非推倒重来，ROI 显著优于全量重构。

#### 5.4 Demo 工程化的思考

最终交付的 4 份单文件 HTML Demo 是经过多轮迭代的产物：
- **第一版**：直接截图 + emoji 装饰 → 评审反馈「界面不够精致」
- **第二版**：金边手机外壳 + 水彩纹理 + 玻璃拟态 + 40+ SVG symbol 替换 emoji → 评审通过

关键经验：**Demo 是产品的脸面**，视觉投入的 ROI 远高于堆砌功能。SVG symbol 方案比 emoji 更可控、比图片更轻量，是单文件 Demo 的最优解。

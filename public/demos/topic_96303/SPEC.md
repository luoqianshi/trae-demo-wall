# SPEC：快递取件码视觉定位 Web 原型

## 1. Problem Statement（问题陈述）

普通取件用户在驿站取快递时，虽然已经知道取件码，但面对一个货架格或一整层货架中的多个包裹贴码，仍然需要肉眼逐个查找目标包裹，效率较低，也容易看错。

本原型希望验证一种简单的视觉定位流程：

用户上传取件码截图和货架照片，系统通过 OCR 识别目标取件码，并在货架照片中用红色矩形框标出目标位置，帮助用户更快找到包裹。

第一阶段目标是 **跑通完整流程**，不是追求生产级识别准确率。

---

## 2. Proposed Solution（方案描述）

### 2.1 产品形态

做一个面向普通取件用户的 Web 原型。

用户通过手机浏览器或本地浏览器访问页面，完成以下操作：

1. 上传取件码截图。
2. 系统 OCR 识别截图文字。
3. 系统用正则规则提取候选取件码。
4. 如果有多个候选码，用户手动选择并确认目标码。
5. 用户上传货架照片。
6. 系统 OCR 识别货架照片中的文字区域。
7. 系统匹配目标 4 位取件码。
8. 找到后，在货架照片中用红色矩形框标注目标位置。
9. 前端展示标注后的图片。
10. 未找到时，返回“未找到”，并提示用户重新拍摄更清晰照片。

---

## 3. Core Functional Requirements（核心功能需求）

### 3.1 上传取件码截图

用户可以上传包含取件码的截图。

截图来源需要兼容多种情况，包括：

* 短信通知截图
* 菜鸟 / 驿站类 App 截图
* 微信小程序 / 公众号通知截图
* 其他包含取件码文本的截图

系统不能依赖固定截图版式，应基于 OCR 文本内容和规则提取候选码。

---

### 3.2 取件码格式

目标码优先按以下格式处理：

```text
货架号-层数-四位编码
```

示例：

```text
18-4-7353
```

其中：

* `18` 表示货架号
* `4` 表示层数
* `7353` 表示 4 位取件码

系统需要提取：

* 完整目标码：例如 `18-4-7353`
* 目标 4 位码：例如 `7353`

货架照片定位时，**优先匹配最后 4 位编码**。

---

### 3.3 候选码确认

如果取件码截图中 OCR 提取出多个候选码，前端应展示所有候选码，让用户手动选择一个作为目标码。

系统不应默认选择第一个候选码，以避免误识别。

---

### 3.4 上传货架照片

用户上传的货架照片预期范围为：

* 一个货架格
* 或一整层货架照片

照片中可能包含多个包裹贴码，但第一版不要求处理整面货架、远距离复杂照片或严重模糊照片。

前端需要重点适配手机浏览器，支持用户从相册选择图片或直接拍照上传。

---

### 3.5 OCR 识别货架照片

系统对货架照片执行 OCR，识别图片中的所有文字区域及其文本框坐标。

识别范围限定为：

* 驿站贴码上的大号编码
* 与目标取件码相关的数字编码

系统不识别、不展示、不存储以下信息：

* 面单姓名
* 手机号
* 地址
* 其他个人隐私信息

---

### 3.6 目标码匹配规则

定位时，系统优先匹配目标码中的最后 4 位编码。

例如用户确认目标码为：

```text
18-4-7353
```

则货架照片中主要匹配：

```text
7353
```

匹配规则：

1. 优先匹配最后 4 位编码。
2. 货架号和层数作为辅助信息，不作为第一版强制匹配条件。
3. 正常情况下，不应出现多个相同 4 位编码。
4. 如果 OCR 识别出多个相同 4 位编码，系统应视为异常情况，不自动猜测唯一结果。
5. 遇到重复匹配时，应提示用户重新拍摄或人工确认，不编造结果。

---

### 3.7 图片标注

当系统找到目标 4 位码对应的 OCR 文本框后：

* 使用 OpenCV 在原图上绘制红色矩形框
* 红框覆盖目标文字区域
* 标注样式固定为红色矩形框
* 不在图片上额外绘制文字标签
* 返回标注后的图片文件
* 前端优先展示标注后的图片

结果页最重要的信息是：**红框标注后的图片**。

---

### 3.8 未找到处理

当系统无法匹配目标 4 位码时：

* 返回明确的“未找到”状态
* 不返回伪造位置
* 不猜测目标位置
* 不编造识别结果
* 提示用户重新拍摄更清晰的货架照片

建议提示语包括：

* 请靠近拍摄
* 请保持对焦清晰
* 请避免反光
* 请确保贴码完整入镜
* 请尽量拍摄目标货架格或目标层完整区域

未找到属于正常业务结果，不应视为系统异常。

---

### 3.9 识别详情展示

OCR 识别详情默认不展示。

前端提供“查看识别详情”按钮，第一版只展示简化信息。

可展示内容包括：

```text
是否找到：是 / 否
目标码：7353
匹配文本：7353
OCR 引擎：PaddleOCR / RapidOCR
是否启用备用 OCR：是 / 否
```

第一版不要求展示完整 OCR 文本框列表，也不新增独立调试接口。

---

## 4. Technical Constraints（技术约束）

### 4.1 后端技术栈

后端使用：

* Python
* FastAPI

后端采用 API-first 设计，方便未来迁移到：

* 微信小程序
* 离线手机 App
* 其他移动端应用

但第一版不实现微信小程序或离线 App。

---

### 4.2 OCR 技术栈

默认 OCR 引擎：

* PaddleOCR

备用 OCR 引擎：

* RapidOCR

推荐策略：

1. 默认使用 PaddleOCR。
2. 当 PaddleOCR 执行失败时，启用 RapidOCR。
3. 当 PaddleOCR 未从取件码截图中提取出候选码时，启用 RapidOCR。
4. 当 PaddleOCR 在货架照片中未匹配到目标 4 位码时，启用 RapidOCR。
5. RapidOCR 的结果也必须经过同样的正则提取和匹配规则。
6. 系统不得合并、猜测或编造不存在的识别结果。

---

### 4.3 图像处理技术栈

图像处理使用：

* OpenCV

第一阶段只做基础处理，包括：

* 图片读取
* 图片格式转换
* 必要的缩放
* 灰度化
* 锐化或二值化
* 根据 OCR 文本框坐标绘制红色矩形框

第一阶段不要求实现：

* 自动裁剪
* 透视矫正
* 复杂去噪
* 自动旋转校正
* 拍摄角度智能修复

---

### 4.4 前端技术栈

前端推荐使用：

* 轻量 React 单页应用

原因：

* 流程存在多个状态步骤
* 适合做上传、确认、展示结果等交互
* 方便后续迁移到微信小程序或 App
* 可以与 FastAPI 后端保持解耦

前端需要重点适配手机浏览器：

* 竖屏布局
* 上传按钮清晰
* 候选码选择清楚
* 标注图片展示足够大
* 标注结果最好支持缩放查看

---

### 4.5 API 设计

第一版使用两个接口。

---

#### 接口 1：提取取件码

```text
POST /api/extract-code
```

输入：

* 取件码截图图片

输出：

* 候选目标码列表
* 每个候选码的完整格式
* 每个候选码的最后 4 位编码
* OCR 引擎信息
* 是否启用备用 OCR
* 失败时返回错误说明

示例响应：

```json
{
  "candidates": [
    {
      "full_code": "18-4-7353",
      "short_code": "7353"
    }
  ],
  "ocr_engine": "paddleocr",
  "fallback_used": false
}
```

如果没有提取出候选码，返回：

```json
{
  "candidates": [],
  "message": "未识别到取件码，请重新上传更清晰的截图",
  "ocr_engine": "paddleocr",
  "fallback_used": false
}
```

---

#### 接口 2：定位货架照片中的目标码

```text
POST /api/locate-code
```

输入：

* 货架照片
* 用户确认后的完整目标码
* 用户确认后的 4 位目标码

示例输入字段概念：

```text
image: 货架照片
full_code: 18-4-7353
short_code: 7353
```

---

### 4.6 `/api/locate-code` 返回规则

#### 找到目标码时

返回标注后的图片文件。

响应示例：

```text
Content-Type: image/jpeg
X-Found: true
X-Target-Code: 7353
X-Matched-Text: 7353
X-OCR-Engine: paddleocr
X-Fallback-Used: false
```

前端收到图片 Blob 后直接展示标注图片。

---

#### 未找到目标码时

返回 JSON。

示例响应：

```json
{
  "found": false,
  "target_code": "7353",
  "message": "未找到目标取件码",
  "suggestions": [
    "请靠近拍摄",
    "请保持对焦清晰",
    "请避免反光",
    "请确保贴码完整入镜"
  ],
  "ocr_engine": "paddleocr",
  "fallback_used": false
}
```

建议业务状态仍返回 `200 OK`，因为“未找到”是正常识别结果，不是系统错误。

---

### 4.7 图片格式

第一版明确支持：

* JPG
* PNG
* WEBP

HEIC 不作为第一阶段强制支持格式。

如果后端无法解码 HEIC 或其他格式，应返回清晰错误提示，引导用户重新上传 JPG、PNG 或 WEBP 图片。

第一版不严格限制图片大小，但需要处理图片解码失败、空文件、非图片文件等异常情况。

---

### 4.8 数据存储与隐私

第一版不保留上传图片和识别记录。

要求：

* 不保存取件码截图
* 不保存货架照片
* 不保存 OCR 结果
* 不保存标注图片
* 不建立用户历史记录
* 单次请求处理完成后尽量清理临时文件

系统不需要登录，不做用户身份识别。

---

### 4.9 运行环境

第一版优先面向本地开发运行。

要求：

* 开发者在本机启动 FastAPI 后端
* 前端在本地运行 React 页面
* 不要求公网部署
* 不要求局域网手机访问开发机服务
* 不要求多用户并发能力
* 不要求生产级账号、权限、日志、监控

---

## 6. Success Criteria（成功标准）

第一阶段成功标准是：**完整流程跑通即可**。

满足以下条件即视为原型成功：

1. 用户可以打开 Web 页面。
2. 用户可以上传取件码截图。
3. 系统可以通过 OCR 识别截图文字。
4. 系统可以从截图 OCR 文本中提取候选取件码。
5. 如果存在多个候选码，用户可以手动选择目标码。
6. 用户可以上传货架照片。
7. 系统可以通过 OCR 识别货架照片中的文字区域。
8. 系统可以优先按最后 4 位编码匹配目标取件码。
9. 找到目标码时，系统可以在图片上用红色矩形框标注目标位置。
10. 找到目标码时，前端可以展示标注后的图片。
11. 未找到目标码时，系统返回“未找到”。
12. 未找到目标码时，系统提示用户重新拍摄更清晰照片。
13. 系统不保存上传图片。
14. 系统不保存识别记录。
15. 系统不识别、展示或存储姓名、手机号、地址等隐私信息。
16. 系统不会在识别不到时编造结果。
17. PaddleOCR 失败或无法识别时，可以按策略启用 RapidOCR 兜底。
18. 前端“查看识别详情”按钮可以展示简化识别信息。
19. 红框样式固定为红色矩形框，不需要文字标签。
20. 原型可以在本地开发环境中完成端到端验证。

## 7. 第一版完整用户路径

```text
打开页面
  ↓
上传取件码截图
  ↓
OCR 识别截图文字
  ↓
正则提取候选码
  ↓
用户选择并确认目标码
  ↓
上传货架照片
  ↓
OCR 识别货架照片文字区域
  ↓
匹配目标 4 位码
  ↓
找到？
  ├─ 是：返回红框标注图片，前端展示
  └─ 否：返回“未找到”，提示重新拍摄
```

## 8. 当前已关闭的待确认项

以下事项已确认：

1. HEIC 不作为第一版强制支持格式。
2. `/api/locate-code` 找到时返回图片文件，未找到时返回 JSON。
3. “查看识别详情”第一版只展示简化识别信息，不新增调试接口。
4. 红框样式固定为红色矩形框，不需要文字标签。
5. 第一版不要求局域网手机访问开发机服务。
6. 前端采用轻量 React 单页应用。
7. 后端采用 FastAPI API-first 设计。
8. 默认 OCR 使用 PaddleOCR，RapidOCR 作为兜底。
9. 图像处理采用 OpenCV，第一版只做基础增强和红框绘制。
10. 成功标准以完整流程跑通为主。

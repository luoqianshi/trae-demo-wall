### 2. **格式转换：YUV420SP → BGR**
```cpp
cv::Mat bgr(height, width, CV_8UC3, data);

```

### 3. **缩放至模型输入尺寸**
```cpp
cv::Mat model_bgr(model_height, model_width, CV_8UC3);
cv::resize(bgr, model_bgr, cv::Size(model_width, model_height), 0, 0, cv::INTER_LINEAR);
```

### 4. **传递给推理**
```cpp
memcpy(rknn_app_ctx.input_mems[0]->virt_addr, model_bgr.data, model_width * model_height * 3);
inference_retinaface_model(&rknn_app_ctx, &od_results);
```

## 关键点总结

| 阶段 | 格式 | 说明 |
|------|------|------|
| **摄像头采集** | YUV420SP | 硬件原生格式 |
| **格式转换后** | BGR | OpenCV 标准格式 |
| **模型输入** | RGB (NHWC) | RetinaFace 要求 |

```cpp
// 消息大小 → 分配的块大小

<= 512KB  → 512KB
<= 1MB    → 1MB  
<= 2MB    → 2MB
<= 4MB    → 4MB
其他      → 8MB
```

```

```

这是 Pangofly 框架用于高效进程间通信的共享内存池。

## Loan 接口内存块大小确定机制

### 核心逻辑

`LoanSample` 接口的内存块大小确定遵循以下流程：

```
用户调用 → expected_size 参数 → alloc_size 计算 → 向上取整 → 分配内存块
```

### 步骤详解

#### 1. alloc_size 计算

```cpp
size_t alloc_size = expected_size > 0 ? expected_size : sizeof(MessageT) + 1024;
```

| 场景 | alloc_size 值 |
|------|--------------|
| 用户传入 `expected_size` | 使用用户指定的值 |
| 用户未传入（默认0） | `sizeof(MessageT) + 1024` |

**人脸识别 Demo 示例**：
```cpp
// image_capture_node.cc 中的调用
Sample<ImageFrame> sample = writer_->LoanSample(sizeof(ImageFrame) + data_size);
```
其中 `data_size = 640 * 480 * 3 = 921600`

#### 2. 向上取整（GetCeilingMessageSize）

alloc_size 会被向上取整到最近的预定义大小：

```cpp
// 预定义的块大小阶梯（字节）
64 → 128 → 256 → 512 → 1024 → 2048 → 4096 → 8192 →
16384 → 32768 → 65536 → 131072 → 262144 → 524288 → 
1048576 (1MB) → 2097152 (2MB) → 4194304 (4MB) → 8388608 (8MB)
```

**人脸识别场景计算**：
```
alloc_size = sizeof(ImageFrame) + 921600 ≈ 923KB
923KB 在 524288 (512KB) 和 1048576 (1MB) 之间
向上取整到 1048576 (1MB)
```

### 完整流程图

```
用户调用 LoanSample(expected_size)
        │
        ▼
┌───────────────────────────────┐
│ expected_size > 0 ?          │
└───────────────────────────────┘
        │
   ┌────┴────┐
   │         │
  Yes       No
   │         │
   ▼         ▼
expected_size  sizeof(MessageT) + 1024
        │         │
        └────┬────┘
             ▼
        alloc_size
             │
             ▼
┌───────────────────────────────┐
│ GetCeilingMessageSize()      │
│ 向上取整到预定义大小          │
└───────────────────────────────┘
             │
             ▼
    实际分配的内存块大小
```

**Loan 接口的内存块大小由用户传入的 `expected_size` 决定**，框架会自动将其向上取整到预定义的标准大小（如 1MB、2MB 等），以优化内存管理和分配效率。

## 推荐方案

有两个选择：

### 方案 A：统一用 RGB888（当前方案，转换在采集端）

```
摄像头 NV12 → [image_capture_node 转换] → RGB888 → face_recognition_node → BGR → 模型
```

**优点**：接口简单，推理节点直接拿 RGB 用
**缺点**：采集端需要做 NV12→RGB 转换，占用 CPU

### 方案 B：直接传 NV12（更高效）

```
摄像头 NV12 → face_recognition_node → [NV12→BGR] → 模型
```

**优点**：减少一次内存拷贝，传输数据量小（1.5字节/像素 vs 3字节/像素）
**缺点**：推理节点需要处理 NV12 格式转换

---

### 我的建议

考虑到 Luckfox 是嵌入式平台，**推荐方案 B（传 NV12）**：

1. **数据量减少一半**（921KB → 460KB），共享内存压力小
2. **减少一次格式转换**，整体更高效
3. NV12 是嵌入式视觉系统的标准格式，符合行业惯例
4. RKNN 模型本身也可以直接配置 NV12 输入（减少 CPU 转换）

### 关于 pass_through 模式

API 中有个 `pass_through` 字段，但它的作用是：
- **TRUE**：数据直接透传给模型，不做任何转换
- **FALSE**：根据 type 和 fmt 做格式转换

这不是支持 NV12 的方式——如果模型是按 RGB 训练的，传 NV12 进去结果会完全错误。

既然 RKNN 需要 RGB/BGR，而摄像头输出 NV12，那么格式转换是必须的。有两个选择：

| 方案 | 转换位置 | 传输格式 | 优劣势 |
|------|---------|---------|--------|
| **A** | 采集节点转 | RGB888 | 推理节点简单，但数据量大（3字节/像素） |
| **B** | 推理节点转 | NV12 | 数据量小（1.5字节/像素），但推理节点要做转换 |

1. **数据量减半**：共享内存传输压力小
2. **NV12 是标准格式**：摄像头原生输出，符合嵌入式视觉惯例
3. **格式转换可以用硬件加速**：Rockchip 平台有 RGA（2D 图形加速硬件）可以做 NV12→RGB 转换，不占 CPU

## 一、错误全景清单

### G 类：需求理解偏差

#### G1. "卡片弹窗"歧义 — 雪球问你

| 维度 | 详情 |
|------|------|
| **问题** | 用户说"雪球问你卡片弹窗"，我理解为修改 `DailyQuestion.tsx` 组件本身（替换 ❄️ emoji、增加副文案）。实际需求是修改回答后弹出的 `QuestionAnswerCard`（在 `CelebrationEffect.tsx` 中） |
| **根因** | "卡片弹窗"一词存在歧义：用户指的是"操作后弹出的反馈卡片"，我理解成了"功能卡片本身"。问题卡片（提问）和弹出卡片（反馈）是两个不同的组件 |
| **影响** | 回滚 DailyQuestion.tsx 全部修改，重做 CelebrationEffect.tsx 中的 QuestionAnswerCard。浪费约 30% 的工作量 |
| **避免措施** | 1. **操作流程举例法**：接到歧义需求时，写出一句操作流程描述让用户确认。例如："用户回答了雪球的问题后，屏幕中央会弹出一个写着'已记录你的回答'的卡片——这个弹出卡片，对吗？"<br>2. **组件调用链标注**：在动手前先画出完整的交互链路图，标出链路上的每个组件名，在要改的节点上打勾让用户确认<br>3. **代码定位三段确认**：使用"文件路径 → 函数/组件名 → 行号范围"三级定位，发给用户确认后再改 |

#### G2. "挑战卡片弹窗"歧义

| 维度 | 详情 |
|------|------|
| **问题** | 用户说"挑战卡片弹窗"，我理解为修改 `ChallengeCard.tsx` 组件本身（替换 ⭐/💎/👑 图标、增加底部鼓励文案）。实际需求是修改挑战完成后的庆祝弹窗 `ChallengeCelebration` |
| **根因** | 与 G1 完全相同——"卡片弹窗"被理解为"宿主组件"而非"弹出层"。两个场景共享同一个根因 |
| **影响** | 回滚 ChallengeCard.tsx 全部修改，重做 ChallengeCelebration.tsx。浪费约 25% 的工作量 |
| **避免措施** | 与 G1 相同。此外建议在项目规范中将"弹窗"统一为特定术语，如仅用"弹出层/Popup/Dialog"表示临时覆盖层，用"卡片/Card"表示功能组件 |

### H 类：运行时错误

#### H1. 看板视图崩溃（stage 未定义）

| 维度 | 详情 |
|------|------|
| **问题** | 看板视图打开后系统崩溃，`ReferenceError` — `stage is not defined` |
| **根因** | `KanbanColumn` 组件在 `TasksPage` 函数体内用 `function` 声明，但它无法访问 `TasksPage` 内部的 `const { stage } = useSnowball()`。JS 的函数声明（`function KanbanColumn(){}`）不会从外层作用域捕获变量——只有箭头函数赋值（`const KanbanColumn = () => {}`）或嵌套匿名函数才能形成闭包 |
| **影响** | 看板视图完全不可用，用户无法切换到此视图 |
| **修复** | 在 `KanbanColumn` 组件内部增加 `const { stage } = useSnowball()`，让其自行获取 |
| **避免措施** | 1. **React 子组件自给自足原则**：任何子组件要么通过 props 接收所需数据，要么自己调用 hooks。**永远不要**假设子组件能通过闭包访问父组件的变量<br>2. **作用域安全检查清单**：对每个 `function SubComponent()` 声明，检查它内部引用的每个变量是否在自身作用域或 props/hooks 中定义<br>3. **TypeScript 严格模式**：启用 `noImplicitAny` 和 `strictNullChecks`，这类错误会表现为编译错误而非运行时崩溃<br>4. **ESLint 规则**：`no-undef` 可捕获未定义变量引用 |

### I 类：配置粒度问题

#### I1. 空状态文案在同一视图内重复

| 维度 | 详情 |
|------|------|
| **问题** | 目标视图中 5 种分组（长任务/习惯/快速任务/目标关联/普通任务）的空状态显示完全相同的文案"我还没有目标可以追呢~"；看板视图中待办列和已完成列也显示相同文案 |
| **根因** | 文案配置表 `snowball-story-text.ts` 只按视图粒度定义场景键（`taskEmptyGoal`、`taskEmptyKanban`），未按视图内的可空分组细分场景。配置表只有 6 个任务场景键，但实际需要 9 个 |
| **影响** | 用户看到重复文案，体验不佳 |
| **修复** | 将 `taskEmptyGoal` 拆分为 `taskEmptyBig | taskEmptyHabit | taskEmptyQuick | taskEmptyGoalGroup | taskEmptyNormal`（5 个），将 `taskEmptyKanban` 拆分为 `taskEmptyKanbanPending | taskEmptyKanbanDone`（2 个） |
| **避免措施** | 1. **枚举所有空状态子场景**：在定义文案配置前，遍历视图中的所有可空分组，统计最大可空数。场景键数量 ≥ 最大值<br>2. **文案配置粒度设计规则**：配置键的粒度应与组件的分组逻辑对齐，而非与视图对齐。分组逻辑是什么粒度，配置键就是什么粒度<br>3. **Fallback 链**：实现 `getStoryText(specificScene) → getStoryText(genericFallback) → 默认文案` 的层层回退，避免遗漏 |

### 4.1 新增分类：F 类 — 需求理解与沟通类问题

在已有 A~F 分类基础上，本轮新增 **G 类（需求理解偏差）**。其特征：

| 特征 | 描述 |
|------|------|
| 识别信号 | "改A的B"、"A组件中的弹窗"——使用了可多义的关键词 |
| 典型场景 | 弹窗/卡片/页面/区域等 UI 元素术语存在实际组件与视觉效果的歧义 |
| 高发阶段 | 需求-编码交接期，通常在用户验收时发现 |
| 修复代价 | 中到高（30%-50% 的重做率） |

**G 类问题专用预防流程**：

```
G类问题预防流程:
  输入: 用户需求 "改X的Y"
  
  步骤1: 问场景
    "用户做了什么操作后看到Y? → 在哪个页面上?"
  
  步骤2: 查代码
    grep -n "Y相关函数" src/app/path -- 找到真实组件名
  
  步骤3: 画链路
    用户操作 → 事件处理 → 状态变化 → 子组件渲染
                       ↑
               这里是要改的吗？
  
  步骤4: 发确认
    "用户点击[XX]后，屏幕上弹出[YYYY]卡片——是这个卡片对吗？"
    
  步骤5: 收到确认后再动手
```

### 4.2 React 组件作用域规则（新增规范）

```
规则：React 子组件自给自足原则

❌ 禁止：
  function Parent() {
    const data = useHook();
    function Child() {          // function 声明，非闭包
      return <div>{data}</div>; // ReferenceError!
    }
    return <Child />;
  }

✅ 允许方案A — props 传递：
  function Child({ data }: { data: T }) {
    return <div>{data}</div>;
  }
  function Parent() {
    const data = useHook();
    return <Child data={data} />;
  }

✅ 允许方案B — 自行获取：
  function Child() {
    const data = useHook();  // 自己调 hook
    return <div>{data}</div>;
  }
  function Parent() {
    return <Child />;
  }

✅ 允许方案C — 箭头函数赋值（形成闭包）：
  function Parent() {
    const data = useHook();
    const Child = () => <div>{data}</div>; // 箭头函数，闭包可访问
    return <Child />;
  }
```

**FAQ**：
> Q: 为什么 `function Child()` 不能访问父函数的变量？
> A: JS 中只有三种方式能访问外部作用域变量：
>   1. **嵌套函数/闭包**（`function Parent() { function Child() {} }` — 可以）
>   2. **箭头函数**（`const Child = () => {}` — 可以）
>   3. **块级函数**（ES6 strict mode 中的块内声明 — 行为特殊）
> 而 `function Child()` 如果定义在父函数体**外层**（即使写在同一个文件但不在父函数内部），则无法访问父函数的变量。

### 4.3 文案配置粒度设计规则（新增规范）

```
规则：配置键粒度 = 组件的分组逻辑粒度

公式：
  所需场景键数 = Σ(每个分组的可空分组数)
  
示例：
  目标视图分组: [长任务, 习惯, 快速任务, 目标关联, 普通任务]
  所需场景键数 = 5 (taskEmptyBig/Habit/Quick/GoalGroup/Normal)

检查清单：
  □ 是否枚举了视图的所有可空分组？
  □ 每个分组的文案是否独立且有辨识度？
  □ 是否有 fallback 机制防止遗漏？
  □ 同一渲染树中的空状态是否使用了不同的场景键？
```

## 五、可复用工程经验补充

### 5.1 "9 宫格"需求确认法

当需求描述存在歧义时，使用 9 宫格确认法：

```
用户说："改A的B"
                            
        是A本身？       是A内部？      是A被触发的？
        ┌──────┐      ┌──────┐      ┌──────┐
        │  ❌  │      │  ❌  │      │  ✅  │  ← 弹出层
        └──────┘      └──────┘      └──────┘
        
        是A的结果？    是A的配置？    是A的样式？
        ┌──────┐      ┌──────┐      ┌──────┐
        │  ❌  │      │  ❌  │      │  ❌  │
        └──────┘      └──────┘      └──────┘
        
        是A的数据？    是A的动画？    是A的文案？
        ┌──────┐      ┌──────┐      ┌──────┐
        │  ❌  │      │  ❌  │      │  ❌  │
        └──────┘      └──────┘      └──────┘
```

每次改需求前，在 9 宫格中打勾确认要改的是哪个节点，发给用户看。

### 5.3 React 函数声明 vs 闭包速查表

| 声明方式 | 能访问外部变量？ | 适合作为子组件？ | 性能特征 |
|---------|----------------|----------------|---------|
| `function Child() {}` （嵌套在父函数内） | ✅ 可以 | ✅ 可以 | 每次渲染重建 |
| `const Child = () => {}` （嵌套在父函数内） | ✅ 可以 | ✅ 可以 | 每次渲染重建 |
| `function Child() {}` （在父函数外部） | ❌ 不能 | ✅ 可以，用 props | 组件外部定义，稳定引用 |
| `const Child = React.memo(function Child(){})` | ❌ 不能 | ✅ 可以，用 props | ✅ 性能最优 |

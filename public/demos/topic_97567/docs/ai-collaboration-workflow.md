## 第一部分：AI 协作开发的核心挑战

### 1.1 AI 编程的独特痛点

| # | 痛点 | 雪球日记中的体现 | 影响 |
|---|------|----------------|------|
| 1 | **上下文窗口有限** | 30+ API 路由、40+ 组件，单次对话无法覆盖全貌 | 容易忽略已有实现，引入重复代码 |
| 2 | **记忆非持久化** | 多次出现"已修复的 Bug 再次引入" | 需要文档体系弥补 |
| 3 | **需求理解偏差** | "卡片弹窗"歧义导致 30% 工作量浪费 | 需要确认机制 |
| 4 | **历史变更不知情** | 分数格式"雪球+X%"未更新为"+X分 ⚡" | 修改前必须查阅变更记录 |
| 5 | **过度自信生成** | 并行计分三套体系共存，AI 未主动合并 | 需要约束性规则 |
| 6 | **删除不彻底** | 旧文件残留、废弃端点仍在引用 | 重构清单必须强制删除步骤 |
| 7 | **测试同步滞后** | Mock 不一致、测试假通过 | Mock 最小化 + 测试数据自给自足 |

### 1.2 成功模式 vs 失败模式

```
成功模式：
┌─────────────────────────────────────────────┐
│  Spec 驱动 → 垂直切片 → 即时验证 → 文档沉淀  │
│  每个环节有明确产出的可验证项                 │
└─────────────────────────────────────────────┘

失败模式：
┌─────────────────────────────────────────────┐
│  模糊需求 → 水平分层 → 延期验证 → 知识丢失  │
│  错误累积到后期集中爆发                       │
└─────────────────────────────────────────────┘
```

## 第二部分：项目初始化体系

### 2.1 初始化清单

项目启动时，必须完成以下初始化才能开始编写业务代码：

```
Phase 0: 项目骨架
├── 技术栈锁定（Next.js + TypeScript strict + Vitest + Tailwind）
├── 目录结构约定（src/app/api/ + src/lib/ + src/hooks/ + src/contexts/）
├── ESLint 自定义规则（禁止 toISOString.split、禁止 as any、禁止 console.log）
├── TypeScript strict 模式（strict + noUncheckedIndexedAccess + verbatimModuleSyntax）
├── 核心工具函数库（date-utils / api-client / logger / test-helpers / response-mapper）
└── 数据架构约定（单一数据源原则、后端权威写入）

Phase 1: AI 上下文文件
├── AGENTS.md（项目全局规则——AI 的第一份阅读材料）
│   ├── 技术栈版本
│   ├── 命名规范（snake_case DB → camelCase 前端）
│   ├── 设计规范（颜色、间距、组件惯例）
│   ├── 核心概念（任务分类逻辑、视图分组优先级）
│   └── 当前项目状态
├── docs/data-model.md（所有实体类型定义和关系）
├── docs/architecture.md（系统架构和模块边界）
└── .trae/rules/project_rules.md（命令和自动化规则）

Phase 2: 持续维护
├── 每次功能完成 → 更新 AGENTS.md（最新更新部分）
├── 每次架构变更 → 更新 docs/architecture.md
├── 每次 Bug 修复 → 创建 docs/BUG修复文档/YYYYMMDD-问题简述.md
└── 每次迭代结束 → 更新 docs/project-status.md
```

## 第三部分：Spec 驱动的迭代工作流

### 3.1 一次迭代的完整流程

```
┌──────────────────────────────┐
│  1. 需求分析                  │  ← AI 理解需求，输出技术方案
│     产出：spec.md             │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│  2. 方案确认                  │  ← 人类审核技术方案，消除歧义
│     方法：操作流程举例法       │
│     产出：确认的 spec.md      │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│  3. 任务分解                  │  ← AI 拆解为独立可验证子任务
│     产出：tasks.md            │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│  4. 垂直切片开发              │  ← 按"数据→API→Hook→组件"切片
│     方法：TDD 红灯→绿灯→重构  │
│     规则：每个切片 < 4h       │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│  5. 即时验证                  │  ← 每完成一个切片立即验证
│     运行：typecheck + test    │
│     产出：通过的测试          │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│  6. 集成验证                  │  ← 全量回归测试
│     运行：lint+typecheck+test │
│     +build                   │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│  7. 清理沉淀                  │  ← 删除旧实现、更新文档
│     产出：更新 AGENTS.md      │
│     + project-status.md       │
└──────────────────────────────┘
```

### 3.2 垂直切片优先 vs 水平分层

```
❌ 水平分层（失败模式——本项目教训）：
   做完所有 API → 做完所有 Hook → 做完所有 Component
   → 发现 API 字段与前端不匹配 → 返工 30 个路由

✅ 垂直切片（成功模式——本项目验证）：
   完成"挑战列表 API → Hook → Component → 验收"
   → 完成"挑战详情 API → Hook → Component → 验收"
   → 每个切片可独立验证，问题在切片内解决
```

### 3.3 每次对话的标准化节奏

```
启动阶段（5 分钟）：
├── 读取 AGENTS.md（了解当前项目状态）
├── 读取 project-status.md（了解最近变更）
├── 读取相关 spec.md（了解功能规格）
└── 明确本轮目标

开发阶段（30-60 分钟）：
├── 先搜索相关代码（理解现有架构）
├── 查看数据模型（了解字段和关系）
├── 编写代码（遵循现有惯例）
└── 运行 typecheck + test（即时验证）

结束阶段（5 分钟）：
├── 更新 project-status.md
├── 更新 AGENTS.md（如有架构变更）
└── 沉淀经验教训
```

### 3.4 需求歧义消除机制

从本项目中两次"卡片弹窗"歧义提炼：

```
操作流程举例法：
  用户说"改 X 的 Y"时 →
  AI 用一句话描述用户操作流程 +
  指出要改的具体节点 +
  发给用户确认

  示例：
  "用户回答了雪球的问题后，屏幕中央会弹出一个写着
  '已记录你的回答'的卡片——是这个弹出卡片，对吗？"

组件调用链标注法：
  用户点击 [添加任务]
  → handleCreateTask (page.tsx:180)
    → createTask (useTasks.ts:45)
      → POST /api/tasks (route.ts:30)
      → setTasks([...prev, newTask])
    → setShowCreateModal(false)
  → ✅ 任务列表自动更新

  标注：[✅] 改添加成功后的 Toast 文案

代码定位三段确认：
  "文件路径 → 函数/组件名 → 行号范围" 三级定位
  示例："src/app/tasks/page.tsx → handleCreateTask → :180"
```

## 第四部分：AI 行为规则（Rules）体系

### 4.1 必须遵循的编码规则

```
## 代码规范（强制）

### 命名规范
- 数据库字段使用 snake_case（task_type, goal_id）
- 前端字段使用 camelCase（type, goalId）
- 通过 response-mapper 统一转换，禁止 ad-hoc 映射

### 常量使用
- 所有分值必须引用 SCORE_VALUES 常量
- 禁止硬编码数值型文案（"+5分" 必须从常量计算得出）
- 新增枚举值必须同步更新对应的分值常量和 filter 条件

### 日期处理
- 禁止使用 toISOString().split('T')[0]
- 必须使用 date-utils.ts 中的 toLocalDateStr() 等函数

### 错误处理
- 所有 fire-and-forget 异步调用必须有 .catch()
- 每个独立功能区域必须有单独的 ErrorBoundary
- 关键数据通过函数参数传递，不依赖 state.find() 查找

### 类型安全
- 禁止 as any（测试辅助函数除外）
- 新增类型必须在 data-models.ts 或 lib/types/ 中定义
- 使用 verbatimModuleSyntax 强制类型导入

### 组件规范
- 子组件自给自足：要么通过 props 接收数据，要么自己调 hooks
- 不依赖父组件闭包传递数据
- useState 不使用于管理动画状态（使用 useRef + classList）

### 测试规范
- 仅 mock 外部依赖，不 mock 内部模块
- 测试数据自给自足：每个测试自己创建所需数据，不依赖全局默认数据
- 修改核心逻辑后必须运行全量测试（不只是相关模块）
```

### 4.2 开发流程规则

```
## 开发流程（强制）

### 修改前必读
□ 读取 AGENTS.md 了解当前项目状态
□ 搜索相关代码理解现有实现
□ 读取数据模型确认字段名和关系
□ 查看 docs/BUG修复文档/ 中是否有相关 Bug 记录

### 修改中遵循
□ 垂直切片优先：完成"数据→API→Hook→组件"完整链路再进入下一个
□ 先写测试再写代码（TDD 红灯绿灯模式）
□ 每次只改一个关注点，改完立即跑测试
□ 不修改不相关的代码

### 修改后检查
□ 运行 typecheck（tsc --noEmit）
□ 运行 lint（ESLint）
□ 运行全量测试（vitest run）
□ 删除 console.log 调试日志
□ 删除旧实现（重构场景）
□ 废弃接口的全局搜索引用端
□ 更新 project-status.md
```

### 4.3 安全规则

```
## 安全规则（强制）

### 数据安全
- 禁止在代码中硬编码密钥和 Token
- 环境变量缺失时必须有明确的降级提示（非静默降级）
- API 路径的认证检查不可绕过

### 代码安全
- 不引入不必要的第三方依赖
- 不生成未经确认的 UI 变更
- 不操作 git 仓库（提交、推送、分支管理）除非用户明确要求
```

### 4.4 规则分层体系

```
规则的优先级和存储位置：

Level 1: 项目不变规则 → AGENTS.md
  技术栈、命名规范、核心概念、设计规范
  修改频率：极低（仅架构变更时）

Level 2: 流程规则 → .trae/rules/project_rules.md
  构建命令、测试命令、lint 命令
  修改频率：低（依赖变化时）

Level 3: 用户偏好 → .trae/rules/user_rules.md
  个人编码风格、偏好库、跳过项
  修改频率：中

Level 4: 临时上下文 → workspace rules（系统级）
  当前对话的特殊约束
  修改频率：高（每轮对话）
```

## 第五部分：AI 技能（Skill）体系

### 5.1 核心技能清单

基于雪球日记项目的实战经验，建议为 AI 编程配置以下技能：

```
## 核心开发技能

### 1. bugfix-workflow（Bug 修复工作流）
触发条件：用户报告 Bug、错误、异常行为
流程：
  1. 理解现象 → 复现步骤
  2. 搜索相关代码 → 阅读 BUG修复文档/ 中同类问题
  3. 5-Why 根因分析（至少问 3 层）
  4. 制定修复方案（需有回退方案）
  5. 先写测试再修复代码（TDD）
  6. 全量回归测试验证
  7. 创建 BUG修复文档/ 沉淀经验
  关键产出：根因链 + 避免措施 + 影响范围评估

### 2. writing-plans（多步骤任务规划）
触发条件：有多个步骤的复杂任务
流程：
  1. 理解需求 → 搜索现有代码
  2. 分解为 3-8 个可验证子任务
  3. 确定子任务的依赖关系和执行顺序
  4. 用 TodoWrite 跟踪进度
  规则：每个子任务 < 4h，可独立测试，无耦合依赖

### 3. karpathy-guidelines（编码行为准则）
触发条件：所有代码编写
规则：
  - 最小改动原则：只改必须改的代码
  - 不改不相关的代码
  - 先搜索后编码（避免重复实现）
  - 手术刀而非大锤（精确修改而非全面重写）
  - 定义可验证的成功标准

### 4. find-skills（技能发现）
触发条件：用户表达需要某种能力时
作用：查找是否有社区开发的现成技能可用
```

### 5.2 领域专项技能

```
## 领域专项技能

### 1. api-design-principles（API 设计）
在新建或修改 API 端点时使用：
  - RESTful 资源命名规范
  - 请求/响应类型定义
  - 错误处理模式
  - 字段映射规范（snake_case → camelCase）

### 2. vercel-react-best-practices（React 性能优化）
在编写 React 组件时使用：
  - 组件拆分粒度
  - 状态管理选择
  - 避免不必要的重渲染
  - 代码分割策略

### 3. tdd（测试驱动开发）
在编写核心逻辑时使用：
  - 红灯阶段：先写失败测试
  - 绿灯阶段：实现最小代码通过测试
  - 重构阶段：优化实现保持测试通过
```

### 5.3 技能配置示例

```yaml
# .trae/skills.yaml（或等价配置）
skills:
  - name: bugfix-workflow
    trigger: "用户报告 bug、错误、异常"
    order: 1  # 高优先级

  - name: writing-plans
    trigger: "复杂多步骤任务"
    order: 2

  - name: karpathy-guidelines
    trigger: "所有编码任务"
    order: 3  # 始终生效

  - name: api-design-principles
    trigger: "新建或修改 API"
    order: 4

  - name: tdd
    trigger: "核心逻辑实现"
    order: 5
```

### 5.4 技能 vs 规则的分工

```
技能（Skill）— AI 主动执行的流程
├── 触发条件驱动：当用户说"修复 Bug"时自动触发
├── 定义步骤流程：按特定顺序执行操作
├── 有明确产出：spec.md / checklist.md / tasks.md
└── 可组合使用：一个任务可串联多个技能

规则（Rule）— AI 必须遵守的约束
├── 全局生效：所有编码任务都适用
├── 有强制约束：禁止/必须/只能
├── 可静态检查：ESLint 规则、TypeScript 配置
└── 优先级分层：从 AGENTS.md 到 project_rules.md
```

## 第六部分：文档体系与知识管理

### 6.1 文档分层模型

```
Level 0: 系统级规则
├── workspace rules（运行时由系统自动注入）
├── 作用：项目入口、语言设置、全局约束
└── 更新：自动

Level 1: 项目常量文档
├── AGENTS.md
├── 作用：技术栈、命名规范、核心概念、设计规范
├── 长度：<500 行，每个 AI 进入时必然读取
└── 更新：低频（架构成熟后很少改动）

Level 2: 架构参考文档
├── docs/architecture.md, docs/data-model.md, docs/api-design.md
├── 作用：按需读取的设计参考
└── 更新：低频

Level 3: 项目状态文档
├── docs/project-status.md
├── 作用：当前进度、最近变更、计划中的任务
└── 更新：高频（每次功能完成立即更新）

Level 4: 知识沉淀文档
├── docs/BUG修复文档/, docs/project-retrospective.md
├── 作用：教训经验、根因分析、避免措施
└── 更新：每次 Bug 修复后
```

### 6.2 文档更新机制

```
每次功能完成后的文档更新检查清单：
```

## 第八部分：从本项目中提炼的 10 条 AI 协作铁律

### 铁律 1：Spec 先行，代码后行

> 每次功能开发前，先产出 spec.md（做什么）→ checklist.md（怎么验收）→ tasks.md（怎么做），经人类确认后再编码。

雪球日记中所有成功的功能迭代都有清晰的 spec，所有失败都是因为跳过 spec 直接编码。

### 铁律 2：垂直切片，而非水平分层

> 每次完成一个完整的数据→API→Hook→组件链路，验证通过再进入下一个。绝不做完"所有 API"再开始"所有组件"。

本项目多次经历"做完整个 API 层再做前端"导致返工。

### 铁律 3：修改前必搜索，理解再动手

> 任何修改前，先搜索项目中的相关代码和文档。理解现有架构、惯例、常量定义后再编码。

"雪球+X%"格式未更新的教训：修改前未搜索旧格式的使用范围。

### 铁律 4：先写测试，再写实现

> 核心逻辑开发时，先写失败测试（红灯），再写实现（绿灯），最后重构。

成就条件测试、分数计算测试中，先写测试确保边界覆盖。

### 铁律 5：每步验证，不累积错误

> 每完成一个子任务立即运行 typecheck + test，不等到全部完成再验证。

### 铁律 6：删除旧实现，不留后患

> 重构时不仅添加新实现，还必须删除旧实现。在 commit message 中列出被删除的文件。

`snowball-stage.ts` 未清理导致两套阶段体系冲突的教训。

### 铁律 7：API 响应必须经映射层

> 所有 API 路由的响应必须通过 response-mapper 转换，禁止直接透传数据库字段。

`task_type` vs `type` 导致 4 大功能同时失效的教训。

### 铁律 8：废弃必搜索引用端

> 废弃任何 API 端点、函数或常量时，必须全局搜索所有引用端并替换。

`PUT /api/tasks` 返回 410 但 `useTasks.updateTask` 仍引用的教训。

### 铁律 9：修改后跑全量测试

> 修改核心工具函数或基础设施后，必须运行全量测试，不只跑相关模块。

修改 `toISOString().split('T')[0]` 后 7 个测试因测试数据未同步更新而失败的教训。

### 铁律 10：一次 Bug 修复，一份永久文档

> 每次 Bug 修复后，创建 BUG修复文档/YYYYMMDD-问题简述.md，记录根因链和避免措施。

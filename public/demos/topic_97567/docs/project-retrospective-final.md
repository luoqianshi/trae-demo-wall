## 第一部分：项目概览与迭代历程

### 1.1 项目定位

雪球日记是一个基于"最小成功记录法"的个人成长陪伴工具，核心理念是将微小成功像滚雪球一样积累，通过记录微小成功、可视化成长轨迹，帮助用户建立正向反馈循环。

### 1.2 技术栈

| 层级 | 技术选型 | 版本 |
|------|---------|------|
| 前端框架 | Next.js 16 (App Router) + React 19 | 16.2.4 / 19.2.4 |
| 样式方案 | Tailwind CSS | 4.2.2 |
| 类型系统 | TypeScript | 5.x |
| 动画 | Framer Motion | 12.38.0 |
| 数据可视化 | Recharts | 3.8.1 |
| 数据存储 | 本地 JSON 文件（`data/local-db.json`） | - |
| AI 服务 | 智谱 AI (GLM-4-Flash) + OpenAI fallback | - |
| 测试 | Vitest + React Testing Library | 4.1.5 / 16.3.2 |
| 部署 | Vercel | - |
| 状态管理 | React Context + Hooks | 无额外状态库 |

## 第三部分：逐案例根因分析

### 3.1 架构级错误（7 项）

#### A1. 三套并行的分数计算体系

| 维度 | 详情 |
|------|------|
| **涉及文件** | `snowball-score.ts`（常量）、`snowball-score-calculator.ts`（重算）、`score-engine.ts`（事件追加） |
| **根因** | 不同开发阶段引入不同实现方式，没有及时合并去重；缺乏"单一数据源"原则约束 |
| **影响** | 同一用户行为在不同入口产生不同分数 |
| **避免措施** | ① 项目启动时明确"单一数据源"原则<br>② 引入 ADR 机制，新增实现前必须回答"为什么不复用"<br>③ CI 中加入死代码检测（ts-prune） |

#### A2. 两套雪球阶段体系

| 维度 | 详情 |
|------|------|
| **涉及文件** | `snowball-stage.ts`（旧，基于记录数）与 `snowball-score.ts`（新，基于分数） |
| **根因** | 重构时仅添加新实现，未删除旧文件，导出同名函数但阈值完全不同 |
| **影响** | 不同组件引用不同文件，阶段判断不一致 |
| **避免措施** | ① 重构 checklist 中强制纳入"删除旧实现"步骤<br>② CI 检测同名导出冲突<br>③ 开启 `verbatimModuleSyntax` |

#### A3. Mock/Supabase 双路径耦合

| 维度 | 详情 |
|------|------|
| **涉及文件** | 32 个 API 路由文件 |
| **根因** | `isMock` 标志在运行时切换数据源，两种逻辑混在同一函数中 |
| **影响** | 代码量翻倍，测试无法有效隔离 |
| **避免措施** | ① 使用 Repository 模式定义统一接口<br>② Mock 和真实实现各自实现接口<br>③ API 路由只依赖接口，不依赖具体实现 |

#### A4. 组件间字段断裂（challenge_type → type / task_type → type）

| 维度 | 详情 |
|------|------|
| **涉及文件** | 30+ API 路由 + 前端数据消费组件 |
| **根因** | 数据库字段名（snake_case）与前端接口（camelCase）缺乏统一 DTO 映射层 |
| **影响** | 首页挑战、任务视图、记录创建、目标视图 4 大功能同时失效 |
| **避免措施** | ① 使用 Zod 定义 API 响应 schema，编译时 + 运行时双重校验<br>② 建立 response-mapper 集中映射<br>③ API 契约测试验证响应 shape |

#### A5. 三源并存积分系统（加分系统重构阶段）

| 维度 | 详情 |
|------|------|
| **问题** | 三套分数写入路径：`snowball-score-calculator.ts`（重算）、`score-engine.ts`（事件）、`challenges/route.ts`（直接写 growthData） |
| **根因** | 迁移时保留了旧路径，挑战分数走独立通道，未统一纳入事件系统 |
| **影响** | 加分后立即被另一路径回读覆盖 |
| **避免措施** | ① 数据写入必须走统一入口<br>② 架构迁移时必须绘制"数据写入路径图"<br>③ 建立"数据写入追溯"——每条变更可追溯到唯一写入点 |

#### A6. API 废弃后未全量更新引用端

| 维度 | 详情 |
|------|------|
| **问题** | `PUT /api/tasks` 标记为 410 Gone，但 `useTasks.updateTask` 仍引用该端点 |
| **根因** | 接口废弃时仅修改路由文件，未全局搜索并更新所有调用端 |
| **影响** | 任务完成操作静默失败，刷新后状态丢失 |
| **避免措施** | ① 废弃 API 端点必须执行"引用端全局搜索 + 全部替换"<br>② 废弃端点应保留一段时间的兼容转发<br>③ TypeScript 签名变更使调用端编译报错 |

#### A7. 认证层 token 解析不完整

| 维度 | 详情 |
|------|------|
| **问题** | `extractUserIdFromToken` 对 `mock-jwt-token-1` 格式直接返回原 token 字符串作为 userId |
| **根因** | token 格式随架构迁移多次演变，但解析函数只适配了最初格式 |
| **影响** | score_events 按错误 userId 查询返回空数组，分数始终为 0 |
| **避免措施** | ① token 格式变更时必须在解析函数中添加对应分支并写测试<br>② 认证层添加"未知格式降级到安全默认值"逻辑<br>③ 添加结构化日志记录每次解析结果 |

### 3.2 React 状态管理错误（5 项）

#### B1. 长任务完成标题消失

**链式根因**：`expandedBigTask === taskId` → `parentId` 错误设为自身 → `patchTask` + `fetchTasks` 替换 state → `tasks.find()` 引用的对象"游离" → 批量异步更新覆盖 `title`。

**修复原则**：函数参数闭环捕获——将 `task.title` 从调用源直接通过参数传入，切断对 state 的依赖。

#### B2. 任务完成界面跳转 + 效果丢失

**根因**：`fetchTasks()` 全量重渲染导致滚动位置丢失；`useState` 动画状态被重渲染重置。

**修复原则**：① 滚动位置保存/恢复 ② 纯 CSS 动画代替 React state（`useRef` + `classList`）。

#### B3. 新手引导触发全局错误页

**四重并发根因**：
1. `createRecord` 未传 `skipCelebration: true` → 庆祝效果与 OnboardingFlow 覆盖层渲染冲突
2. `fetchFeedback` 异步调用无 `.catch()` → 组件卸载后 `setState` → 渲染崩溃
3. OnboardingFlow 无独立错误边界 → 错误冒泡到全局
4. 全局 ErrorBoundary 只能 reload 恢复，无降级路径

**修复方案**：① `skipCelebration: true` ② `.catch()` + 空值检查 ③ 独立 ErrorBoundary ④ ErrorBoundary 添加重试/跳过路径。

#### B4. addScore 乐观更新被 refreshStats 覆盖

**根因**：乐观更新 + 全量刷新是矛盾模式——乐观更新假设"我知道新值"，全量刷新假设"让服务端告诉我"，两者混用必然冲突。

**避免措施**：① 乐观更新后使用"差异补丁"模式 ② 或完全放弃乐观更新，改为"加载态 → 服务端返回 → 渲染" ③ 必须等待异步写入确认后再刷新。

#### B5. SnowballContext 重写遗漏 cleanup

**根因**：新增 `setTimeout` 延迟同步时忘记添加 `useEffect` cleanup。

**避免措施**：`react-hooks/exhaustive-deps` 规则 + 审查清单纳入"异步 cleanup"项。

### 3.3 异步编程与事件驱动缺陷（4 项）

#### C1. 成就庆祝触发链断裂

**根因**：4 个 hook 调用 `checkAchievements()` 后未捕获返回值，缺乏统一的"检查 → 结果 → 庆祝"标准流程。

**修复方案**：统一使用 `checkAndCelebrate()` 封装函数，每个 hook 中 `const unlocked = await checkAchievements(); if (unlocked.length) triggerCelebration(unlocked)`。

#### C2. 雪球互动成就异步时序竞争

**根因**：`syncInteractionToServer()` PATCH 是 fire-and-forget，`checkInteractAchievements()` POST 到达时数据库仍为旧值。

**修复方案**：合并为原子 PATCH 操作——端点内完成"计数更新 + 成就检查 + 返回 newlyUnlocked"。

**核心教训**：**写后即读**的操作必须在同一个请求-响应周期内完成。

#### C3. 急救拖延成就触发时机错误

**根因**：`procrastination_count` 在创建会话时递增，但成就检查只在会话完成时触发。

**修复方案**：在创建会话和完成会话两个时点都检查成就。

#### C4. 雪球问你错误创建快速任务

**根因**：`DailyQuestion` 的 `onAnswer` 回调中错误调用了 `createTask`。

**避免措施**：组件回调的副作用必须在 PRD 中明确定义，禁止在非目标场景下调用有副作用的函数。

### 3.4 数据一致性问题（8 项）

| # | 问题 | 根因 | 避免措施 |
|---|------|------|---------|
| D1 | 加分后归零（认证层） | 数据写入用 `user_id: '1'`，读取用 `mock-jwt-token-1`，userId 不一致 | 读写必须使用同一 userId 解析路径 |
| D2 | 任务完成双重计分（前后端双写） | 前端 `addScore('RECORD_CREATED')` + 后端 `createRecord` 调用 `addScoreEvent` | 明确"加分由后端权威写入，前端仅刷新读取" |
| D3 | 子任务双重计分（类别重叠） | filter 条件 `!t.type || ...` 未排除 `parent_id` | 分类统计使用决策表验证互斥性 |
| D4 | 习惯打卡不产生分数 | 迁移遗漏加分逻辑 | 迁移时逐行对照旧代码，确保所有副作用完整迁移 |
| D5 | 挑战分数与核心分数脱节 | 挑战奖励走独立 `awardSnowballSize()` | 建立"功能-分值映射表" |
| D6 | big 类型任务完成不得分 | 新增任务类型未同步分值定义 | 类型枚举与分值枚举一一对应 |
| D7 | SCORE_TEXT_MAP 硬编码 | 页面组件不引用 SCORE_VALUES | 所有分值必须引用常量，禁止硬编码 |
| D8 | 连续天数计算逻辑不一致 | `todayStreak` 与 `calculateStreakDays` 两套算法 | DRY；公共逻辑提取后原函数复用 |

### 3.5 UI/UX 细节问题（4 项）

#### E1. "卡片弹窗"需求理解歧义（雪球形象集成）

**问题**：用户说的"雪球问你卡片弹窗"实际指回答后弹出的 `QuestionAnswerCard`，被误理解为修改 `DailyQuestion.tsx` 组件本身。

**根因**：术语"卡片弹窗"存在多义性——"操作后弹出的反馈卡片"vs"功能卡片本身"。

**避免措施**：**操作流程举例法**——写出一句操作流程描述让用户确认。"用户回答了雪球的问题后，屏幕中央会弹出一个写着'已记录你的回答'的卡片——是这个弹出卡片，对吗？"

#### E2. 空状态文案粒度不足

**问题**：目标视图中 5 种分组显示相同文案"我还没有目标可以追呢~"。

**根因**：文案配置键只按视图粒度定义，未按视图内的可空分组细分场景。

**修复**：`taskEmptyGoal` 拆分为 5 个场景键。

#### E3. 分数显示格式未对齐统一分数制

**问题**：QuestionAnswerCard 显示"雪球+5%"，ChallengeCelebration 显示"雪球+X"，未使用统一格式"+X分 ⚡"。

**根因**：开发前未查阅历史变更记录。

**避免措施**：修改前必读 AGENTS.md 中相关功能的最新变更记录。

#### E4. 看板视图崩溃（stage 未定义）

**根因**：`KanbanColumn` 组件在父函数体内用 `function` 声明，无法访问父函数内部的 `const { stage } = useSnowball()`。

**修复**：子组件内部自己调用 `useSnowball()`。

**避免措施**：**子组件自给自足原则**——子组件要么通过 props 接收数据，要么自己调用 hooks，永远不依赖父组件闭包。

### 3.6 测试相关问题（3 项）

| # | 问题 | 根因 | 避免措施 |
|---|------|------|---------|
| F1 | Mock 不一致导致测试假通过 | Mock 了内部模块且缺少新增字段 | 仅 mock 外部依赖，内部模块使用 `vi.importActual()` |
| F2 | 修改核心逻辑后只跑相关测试 | 未执行全量回归测试 | 修改核心函数后必须运行全量测试 |
| F3 | 测试依赖默认数据中的预设数据 | 测试假设了默认数据中存在特定记录 | 每个测试用例自行创建所需数据，不依赖 `getDefaultData()` |

## 第四部分：根因分析矩阵与系统性归纳

### 4.1 系统性根因归纳

经过对全部 34 个错误案例的分析，归纳出 **7 大系统性根因**：

| # | 系统性问题 | 涉及案例数 | 核心症结 |
|---|-----------|-----------|---------|
| 1 | **缺乏统一的数据契约层** | 10+ | API 字段名/数据格式/序列化方式在 DB→API→Frontend 链路中不一致 |
| 2 | **并行实现/死代码未清理** | 7 | 重构时新增实现但不删除旧实现，三套分数计算体系为最典型案例 |
| 3 | **前端状态生命周期管理不当** | 6 | useState 依赖全量刷新、缺少 cleanup、z-index 冲突、ErrorBoundary 缺失 |
| 4 | **测试覆盖不足且 mock 失真** | 4 | Mock 数据不与真实 schema 同步、测试验证错误行为 |
| 5 | **废弃接口未全局搜索引用端** | 3 | API 废弃后仍有调用方，静默失败 |
| 6 | **前后端同步机制缺失** | 4 | 乐观更新 + 全量刷新矛盾模式，认证层读写 userId 不一致 |
| 7 | **缺乏功能集成检查清单** | 3 | 新增功能缺少对现有系统的完整性检查 |

### 4.3 5-Why 深度分析精选

#### 案例：加分后归零

```
Why 1: 为什么总分显示为 0？
→ calculateEventScore 查询不到 scoreEvents

Why 2: 为什么查询不到？
→ 按 userId "mock-jwt-token-1" 查询，而数据用 user_id "1" 写入

Why 3: 为什么读写用了不同的 userId？
→ extractUserIdFromToken 对 mock-jwt-token- 格式未做解析

Why 4: 为什么解析函数只适配了 local-token- 格式？
→ 认证方案从 Supabase JWT → local-token → mock-jwt-token 三次演变，
  但解析函数仅更新了一次

Why 5: 为什么三次架构演变没有覆盖测试？
→ 认证层没有隔离测试，token 解析逻辑与 API 路由紧耦合

系统性原因：认证层缺乏独立可测试的 token 解析模块 + 架构演变时未执行全量回归
```

#### 案例：成就系统 14 个成就永远无法解锁

```
Why 1: 为什么成就永远无法解锁？
→ conditionMap 中 14 个条件被硬编码为 false

Why 2: 为什么被硬编码为 false？
→ 成就定义散落三处（mock-data.ts、ACHIEVEMENT_SEEDS、conditionMap）

Why 3: 为什么没有实现？
→ 开发时数据源为 Supabase，Mock 模式下无法获取真实的挑战/互动数据

Why 4: 为什么 Mock 模式无法获取？
→ Mock 数据只模拟了基础 CRUD，没有模拟聚合统计

Why 5: 为什么没有在 Mock 层实现聚合统计？
→ 缺乏"Mock 必须覆盖所有 conditionMap 路径"的开发规范

系统性原因：Mock 层与业务逻辑层的覆盖范围没有约束关系
```

### 6.2 架构设计原则

| # | 原则 | 说明 | 本项目典型反例 |
|---|------|------|--------------|
| 1 | **单一数据源** | 每个业务概念只有一个权威实现，新增前必须回答"为什么不复用" | 三套分数计算体系 |
| 2 | **后端权威写入** | 数据变更（加分、状态、计数器）必须由 API 层执行，前端仅读取 | 前端 addScore 直接写入分数事件 |
| 3 | **Repository 模式** | 数据访问通过接口隔离，Mock 和真实存储各自实现 | isMock 标志混在路由中 |
| 4 | **互斥分类验证** | 枚举类型的分类统计必须互斥且完备 | 子任务同时归入 normal 和 subtask |
| 5 | **DTO 映射层** | API 响应字段在 response-mapper 中集中转换 | task_type vs type |
| 6 | **时区安全** | 所有日期处理使用统一的本地化函数 | toISOString 跨日 bug（34 处） |
| 7 | **重构即删除** | 重构时必须删除旧实现，不能仅添加新实现 | snowball-stage.ts 未清理 |
| 8 | **废弃必搜索** | 废弃接口/函数时必须全局搜索并更新所有引用端 | PUT /api/tasks 410 但仍有引用 |
| 9 | **认证独立可测** | token 解析为独立纯函数，有完整单元测试 | extractUserIdFromToken 未知格式无处理 |
| 10 | **原子操作用于写后即读** | 有依赖关系的写入+读取合并为单次请求 | PATCH+POST 竞态 |
| 11 | **组件级错误边界** | 每个独立功能区域（引导、挑战、拖延急救等）有自己的 ErrorBoundary | OnboardingFlow 错误冒泡到全局 |
| 12 | **函数参数闭环捕获** | 关键数据通过函数参数从调用源闭合传递，切断对 state 依赖 | 长任务标题 state 游离丢失 |
| 13 | **副作用清单模式** | 每个业务操作有明确的副作用清单 | 习惯打卡遗漏加分 |
| 14 | **条件与判定分离** | 条件"是什么"和"怎么判断"是两个独立关注点 | 36 行硬编码 conditionMap |
| 15 | **默认即最小** | `getDefaultData()` 必须是系统最小可运行状态，所有集合默认空数组 | 默认数据中的预设目标导致成就误触发 |

### 7.3 风险预判与应对机制

#### 高风险模式识别表

| 风险信号 | 含义 | 预判的问题 | 本项目触发次数 |
|---------|------|-----------|--------------|
| 两个文件导出同名函数 | 重复实现 | 结果不一致 | 3 次 |
| 定义了但未引用的常量 | 遗漏集成 | 功能不生效 | 2 次 |
| `toISOString().split('T')[0]` | 时区陷阱 | 跨日 bug | 17 文件 34 处 |
| `as any` | 类型逃逸 | 运行时错误 | 30+ 处 |
| `fetch().then()` 无 `.catch()` | 未捕获异常 | 页面崩溃 | 多次 |
| 多个 filter 条件用 `\|\|` | 分类重叠 | 双重计分 | 2 次 |
| useState 管理动画 | 重渲染丢失 | 动画闪烁/消失 | 多次 |
| localStorage 存储需持久化的数据 | 数据丢失 | 跨设备不可用 | 1 次 |
| 异步函数在 useEffect 中无 cleanup | 内存泄漏 | 性能下降 | 1 次 |
| 废弃端点仍有调用方 | 静默失败 | 功能失效 | 2 次 |
| 乐观更新 + 全量刷新共存 | 竞态条件 | 数据回退 | 2 次 |

#### 应急响应流程

```
发现问题 → 定级 (P0-P3) → 分析根因 (5-Why 至少问 3 层) → 影响范围映射
→ 制定方案 (2+ 方案对比) → 实施修复 (先写测试再写代码) → 验证 (全量测试 + 手动回归) → 复盘

复盘模板（5 步）：
1. 问题描述：什么行为不符合预期，影响哪些用户
2. 根因分析：5-Why 追溯到系统性原因
3. 修复方案：具体改了什么代码，为什么这样改
4. 防范措施：如何避免同类问题（工具 / 规则 / 流程）
5. 经验提炼：可复用的通用规则（加入本文档）
```

### 7.4 可复用的代码模式

#### 模式一：条件评估器工厂

```typescript
// 适用于：游戏化系统、权限系统、规则引擎等需要大量条件判定的场景
function numericCondition(field: string, threshold: number): AchievementCondition {
  return {
    evaluate: (stats) => (stats[field] as number) >= threshold,
    progress: (stats) => Math.min(1, (stats[field] as number) / threshold),
    threshold: { field, value: threshold },
  };
}

// 注册表——新增条件只需一行
export const CONDITIONS: Record<string, AchievementCondition> = {
  'records_1': numericCondition('records_count', 1),
  'records_7': numericCondition('records_count', 7),
};
```

#### 模式二：API 端点三位一体

```typescript
// GET    — 只读查询，返回完整状态
// POST   — 触发副作用检查（如成就解锁）
// PATCH  — 增量更新（如计数 +1）
export async function GET(request: NextRequest) { ... }   // 查询
export async function POST(request: NextRequest) { ... }  // 操作
export async function PATCH(request: NextRequest) { ... } // 增量更新
```

#### 模式三：响应映射器（response-mapper）

```typescript
// 集中在 lib/utils/response-mapper.ts
function toApiTask(dbTask: DBTask): Task {
  return {
    ...dbTask,
    type: dbTask.task_type,       // snake_case → camelCase
    goalId: dbTask.goal_id,
    parentId: dbTask.parent_id,
    completedAt: dbTask.completed_at,
  };
}
```

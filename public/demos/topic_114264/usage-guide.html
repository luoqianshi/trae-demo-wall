快速开始

五分钟跑通第一次导入
1

安装并初始化

从源码构建 CLI（pnpm workspace），首次运行会在 ~/.knowledge-forge/ 下生成配置与数据库。

# 克隆并构建 git clone <repo> knowledge-forge cd knowledge-forge pnpm install pnpm build # 初始化（生成 ~/.knowledge-forge/config.yaml + knowledge.db） node packages/cli/dist/cli.js init # 建议设置 alias（写入 ~/.zshrc） alias kf="node $(pwd)/packages/cli/dist/cli.js" source ~/.zshrc

初始化后必做

  • →编辑 ~/.knowledge-forge/config.yaml
  • →修改 vault.path 指向你的 Obsidian 库
  • →添加 sources[].config.watchPaths
  • →填写 llm.apiKey
  • →Node 22+ 需 --experimental-sqlite
2

导入第一批文件

扫描配置的本地目录，写入收件箱 + 创建 KnowledgeVersion。

# 扫描所有配置的本地目录 kf ingest --source local # 限制单批最多 50 个（首次冷启动推荐） kf ingest --source local --now --limit 50 # YOLO 模式：导入后直接跑完整管道（compile+lint+review+write+archive+link-replace） kf ingest --source local --auto
3

搜索知识库

# 全文搜索（FTS5 + 中文二元分词） kf search "设计模式" # 语义搜索（向量相似度） kf search "如何解耦" -s # 混合搜索（全文 + 语义） kf search "状态管理" -a # 深度研究（LLM 多步推理） kf search "微前端方案对比" -r
02

配置文件详解

~/.knowledge-forge/config.yaml

所有行为由这一份 YAML 驱动。修改后无需重启进程——下次 CLI 调用会重新加载。关键段落如下：

vault

Obsidian 保险库

输出 Markdown 笔记的根目录。schemaPath/indexPath/logPath 都是相对于该目录的辅助文件。

vault: path: ~/Documents/Obsidian Vault schemaPath: SCHEMA.md indexPath: index.md logPath: log.md

sources

数据源列表

数组结构，每项 type 决定连接器。enabled: false 的源会被 kf ingest 跳过。

sources: - type: local enabled: true config: watchPaths: - ~/Documents/待整理 - ~/Downloads/知识文件 ignorePatterns: ["*.tmp", ".DS_Store"] maxFileSize: 52428800 # 50MB

llm

LLM Provider

驱动 Compile 阶段的摘要/标签/交叉引用生成，以及图片视觉描述。支持 openai / anthropic / ollama 兼容接口。

llm: provider: openai model: mimo-v2.5 apiKey: <your-key> maxTokens: 4096 temperature: 0.3 local: endpoint: https://api.example.com/v1 embedding: provider: local model: Xenova/all-MiniLM-L6-v2

search

搜索引擎

fullText 用 SQLite FTS5（中文二元分词），semantic 用本地 embedding 向量相似度。

search: fullText: enabled: true fields: [title, content, tags] semantic: enabled: true threshold: 0.7 provider: local

dedup + pipeline

去重与管道

三层去重（精确 hash → 模糊相似度 → 语义 embedding）。管道 30s 超时保护，maxConcurrent 控制并发。

dedup: levels: exact: { enabled: true, action: skip } fuzzy: { enabled: true, highThreshold: 0.9 } semantic: { enabled: true, embeddingThreshold: 0.85 } versioning: maxVersions: 20 # 每个 lineage 最多保留 20 版 pipeline: autoSummarize: true autoTag: true autoLink: true maxConcurrent: 3 timeout: 30000

schedule + coldStart

定时与冷启动

schedule 通过 macOS launchd 触发；coldStart 在 pending ≥ 50 时自动分批（mtime-desc + size-asc 排序，30 分钟超时）。

schedule: enabled: true hour: 2 minute: 0 batchSize: 10 coldStart: coldStartThreshold: 50 batchSize: 10 timeoutMs: 1800000 # 30 分钟 inbox: maxRetries: 3
03

典型工作流

五个真实场景
场景 A

首次冷启动 · 数百个积压文件

检测到 pending 条目 ≥ 50 时，--auto 模式自动启用 ColdStartManager：按 mtime-desc + size-asc 排序，分批处理（默认 batch=10），每批 30 分钟超时保护。

# 第一次冷启动：分批处理，自动跑完整管道 kf ingest --source local --auto --limit 50 # 查看进度 kf inbox --stats # 处理中断时从中断处续传 kf ingest --resume
输入
~/Documents/待整理/*
过程
9 阶段管道 / 批 10
输出
vault/*.md + 原文件 symlink
场景 B

日常增量导入

手动触发或由 launchd 定时触发。新文件走完整 9 阶段管道，重复文件按 hash 跳过。

# 手动增量（不跑管道，只入收件箱） kf ingest --source local # 手动增量 + 跑完整管道（适合偶尔手动整理） kf ingest --source local --auto # 只编译已有 KnowledgeVersion（不重新扫描文件） kf compile # 全量重建（重新编译所有 version） kf compile --rebuild
场景 C

launchd 定时任务自动化

macOS 系统级定时，不依赖 node-cron 常驻进程。注册 LaunchAgent 后每天定时触发 kf ingest --auto --now。

# 注册 LaunchAgent（每天 02:00 执行） kf schedule --enable --hour 2 --minute 0 --batch-size 10 # 查看状态 kf schedule --status # 修改时间 kf schedule --disable kf schedule --enable --hour 3 --minute 30 # 完全卸载（删除 plist 文件） kf schedule --teardown
plist 位置: ~/Library/LaunchAgents/com.knowledge-forge.ingest.plist
日志位置: ~/.knowledge-forge/logs/launchd-stdout.log
场景 D

错误恢复与中断续传

CLI 进程被杀、SQLite 锁、LLM 超时等场景下，InboxEntry 会卡在 processing 状态。RecoveryManager 实现状态机验证 + 智能决策（resume/retry/fail）。

# 列出所有中断条目（processing 状态） kf recover --list # 检测中断并给出建议 kf recover --detect # 应用恢复决策（resume/retry/fail 由状态机判定） kf recover --apply <id> # 手动重试（保留 retryCount，不重置） kf recover --retry <id> # 重置所有卡住的条目（processing → pending） kf recover --reset-stuck
场景 E

人工审核 · YOLO 模式例外

即便启用了 --auto（YOLO），含敏感词（身份证 / 银行卡 / 金额 / 合同号）的条目会强制进入 pending review 状态等待人工决策。

# 列出待审核条目 kf review --list # 查看详情 kf review --show <id> # 批准并写入 vault kf review --approve <id> # 拒绝（不写入 vault） kf review --reject <id> --note "内容重复" # 编辑后批准（修改摘要内容） kf review --edit <id> --summary "新的摘要内容..."

命令参考

17 个子命令按职能分组

初始化与配置

kf init
生成配置文件 + 数据库，若 schedule.enabled 同时注册 LaunchAgent
kf config
打印当前生效的 SystemConfig（已脱敏 apiKey）
kf stats
统计：lineages / versions / pages / inbox / dedup records

导入与编译

kf ingest
-s/--source local|email|wechat|douyin --auto 跑完整管道 --now 应用 batchSize --resume 中断续传 --limit N 单批上限
kf compile
-r/--rebuild 全量重建（重新编译所有 version）
kf lint
质量审查：构建 IndexEntry + LinkGraph，输出 LintIssue

搜索

kf search <query>
-l/--limit 结果数（默认 20） -s 语义 -a 混合 -r 深度研究

收件箱与审核

kf inbox
-l 列出 -s <status> 按状态过滤 -a <id> 归档 -r <id> 重试 --stats 统计
kf review
--list / --show <id> / --approve <id> / --reject <id> / --edit <id> --summary "..."
kf recover
--list / --detect / --apply <id> / --retry <id> / --reset <id> / --reset-stuck

归档与版本

kf archive
-s 统计 / -l <lineageId> 列出该 lineage 的所有归档版本
kf prune
--dry-run 预览 / -s by-version|by-age 策略 / -l <lineageId> / -n N 保留 N 版 / -a days 保留 N 天
kf merge
-n/--dry-run 跨源同名文件归并预览（按 normalizeFilename）
kf history [file]
-l N 查看 Gitea 提交历史（默认 20 条）

调度与同步

kf schedule
-e 启用 / -d 禁用 / -s 状态 / -t 完全卸载 / --hour / --minute / --batch-size
kf sync
-p 推送 / -l 拉取 / -s 状态（Gitea 双仓同步）
05

数据源连接器

四个内置源

local · 本地文件

已实现

扫描 watchPaths 下的所有文件，支持递归、ignorePatterns、maxFileSize 限制。是当前最完整的连接器。

使用：kf ingest --source local

email · 邮件

部分实现

IMAP 协议拉取指定文件夹（默认 INBOX），支持附件下载（pdf/docx/txt），按 fetchSince 增量。

使用：kf ingest --source email

wechat · 微信导出

已实现

扫描本地微信导出文件夹（HTML/TXT），正则提取正文。文件名约定 chatName_sender_20260101.html 用于解析元数据。不直接连接微信客户端。

使用：kf ingest --source wechat

douyin · 抖音视频

占位

设计用于提取视频字幕与描述，需要 cookies 文件。当前仅配置占位，连接器未实现。

使用：暂不可用

三种搜索模式

关键词 / 向量 / LLM 推理
MODE 01

全文搜索

SQLite FTS5 + 中文二元分词（连续中文字符 2 字符滑窗）。匹配关键词命中。

kf search "设计模式"
适合：精确关键词、术语、文件名片段
MODE 02

语义搜索

本地 embedding 模型（Xenova/all-MiniLM-L6-v2）计算向量相似度，threshold=0.7 过滤。

kf search "如何解耦" -s
适合：自然语言提问、概念查询
MODE 03

混合 + 深度研究

混合 = 全文 ∪ 语义，按融合分数排序。深度研究用 LLM 多步推理生成研究报告。

kf search "状态管理" -a kf search "微前端对比" -r
适合：开放性问题、跨文档综合

故障排查

常见问题与解决

数据库锁定 / SQLITE_BUSY

通常由前一个 kf 进程异常退出导致。CLI 已在 finally + SIGINT/SIGTERM 中关闭连接，但极端情况下仍可能残留。

# 检查是否有残留进程 lsof ~/.knowledge-forge/knowledge.db kill -9 <pid>

配置验证失败

CLI 启动时会检查 config.isValid。常见原因：vault.path 不存在、watchPaths 不可读、llm.apiKey 为空。

kf config # 查看当前配置 mkdir -p ~/Documents/Obsidian\ Vault

LLM 调用超时 / 失败

默认 30s 超时（pipeline.timeout）。Compile 阶段失败会跳过该文件的页面生成，但 inbox 状态会保留以便重试。

# 调大超时（修改 config.yaml） pipeline: timeout: 60000 # 60s # 重试失败条目 kf inbox -r <id>

中断条目卡在 processing

CLI 被 Ctrl+C 或 kill 后，正在处理的条目会停在 processing 状态。用 RecoveryManager 智能恢复。

kf recover --detect # 检测并给建议 kf recover --apply <id> # 应用决策 kf recover --reset-stuck # 批量重置

数据库 schema 变更后无法启动

schema 不向后兼容时（如字段删除），直接删除重建是推荐做法。

# 备份后删除 mv ~/.knowledge-forge/knowledge.db ~/.knowledge-forge/knowledge.db.bak rm ~/.knowledge-forge/search.db kf init # 重建 schema kf compile --rebuild # 重新编译所有内容

# 软件工程文档使用指南（面向智能体）

> **目标读者**：AI编程助手（如Trae智能体）、开发者  
> **目的**：让智能体理解 PRD 与详细设计文档的区别，知道何时读取、如何理解、按什么顺序使用

---

## 一、核心概念

软件工程项目中有两类核心文档，智能体必须先区分清楚再行动：

### 1. PRD（Product Requirements Document）— 产品需求文档

| 属性 | 说明 |
|------|------|
| **回答的问题** | 做什么、为什么做、为谁做 |
| **典型内容** | 业务背景、用户角色、功能清单、业务流程、界面描述、验收标准 |
| **产出者** | 产品经理 / 业务方 |
| **产出时机** | 项目启动阶段，开发之前 |
| **抽象程度** | 高——描述"要什么"，不描述"怎么实现" |
| **读者** | 产品、设计、测试、开发（所有人） |

### 2. 详细设计文档（Low-Level Design Document）— 技术设计文档

| 属性 | 说明 |
|------|------|
| **回答的问题** | 怎么做、改什么文件、用什么技术、数据怎么存 |
| **典型内容** | 数据表设计、API签名、组件树、路由设计、实施步骤、文件修改清单 |
| **产出者** | 技术负责人 / 开发工程师 |
| **产出时机** | PRD定稿后，编码开始前 |
| **抽象程度** | 低——直接指导代码怎么写 |
| **读者** | 开发工程师（人类或AI） |

---

## 二、PRD 的正确使用方式

### 2.1 什么时候应该读取 PRD

以下场景需要先读取 PRD：

- **项目启动**：第一次进入项目，需要了解整体业务
- **新增功能**：接到一个新需求，需要理解业务背景和用户场景
- **跨模块沟通**：需要理解某个功能在整体中的位置和与其他模块的关系
- **验收测试**：判断实现是否满足业务需求

### 2.2 怎么读取 PRD

读取 PRD 应按以下层次递进：

```
第1层：产品定位 → 这个产品是干什么的，核心差异化是什么
第2层：用户角色 → 有哪些角色，各自什么权限
第3层：核心业务模块 → 有哪些功能模块，模块之间什么关系
第4层：业务流程 → 关键业务怎么流转（五阶段状态机、审批流等）
第5层：功能细节 → 具体每个功能的输入、输出、边界
```

### 2.3 PRD 的局限性（智能体必须知道）

PRD **不能**直接指导写代码。它：

- ✅ 告诉你"需要一个跨学段任务分配功能"
- ✅ 告诉你"大学团队可以培训中小学团队"
- ❌ 不告诉你数据库要几张表、字段叫什么
- ❌ 不告诉你 API 路由怎么设计
- ❌ 不告诉你前端组件放哪个目录

**所以拿到 PRD 后，不能直接开始写代码**——必须先产出一份详细设计文档。

## 三、详细设计文档的正确使用方式

### 3.1 什么时候应该读取/产出详细设计文档

- **PRD 定稿后**：开始编码前，必须先有详细设计文档
- **接手已有项目时**：项目中已有详细设计文档，需要先理解再修改
- **多轮迭代时**：每一轮迭代都应该有对应的详细设计文档，说明本轮要改什么

### 3.2 怎么读取详细设计文档

```
第1层：差距分析 → 当前状态 vs 目标状态，明确要改什么
第2层：数据层 → 新增/修改哪些数据表，字段是什么
第3层：接口层 → API 路由、方法、参数、返回
第4层：前端层 → 新增/修改哪些页面、组件
第5层：实施顺序 → 先做什么、后做什么、依赖关系
```

### 3.3 详细设计文档的核心价值

- **消除歧义**：PRD 说"培训中小学团队"，设计文档具体到"新增 guidance_materials 表，6个字段，POST /api/guidance/materials 接口"
- **评估工作量**：数一下要改多少文件、多少表、多少接口
- **并行开发**：后端按 API 设计开发，前端按组件树开发，互不阻塞
- **代码审查依据**：最终的代码是否和设计一致

## 四、PRD → 详细设计文档 → 代码：标准工作流

智能体在处理软件开发任务时，应严格按照这个顺序执行：

```
┌──────────────┐     ┌──────────────────┐     ┌──────────────┐
│   用户输入     │     │    PRD（如果有）    │     │   详细设计文档  │
│  （需求描述）   │ ──► │   （理解业务意图）   │ ──► │  （设计方案）   │
└──────────────┘     └──────────────────┘     └──────────────┘
                                                      │
                                                      ▼
                                               ┌──────────────┐
                                               │    写代码      │
                                               │  （按设计实施）  │
                                               └──────────────┘
```

### 步骤详解

#### Step 1：理解需求（读取 PRD 或用户描述）

做的事情：
- 精读 PRD，搞清楚业务背景
- 列出所有涉及的功能点
- 明确用户角色和权限
- 理清业务流程和数据流

**输出**：对业务的理解，确认没有歧义

#### Step 2：产出详细设计文档（如果还不存在）

做的事情：
- **差距分析**：对比当前项目状态和目标状态
- **数据层设计**：列出新增/修改的数据表，每个表的字段、类型、约束
- **接口层设计**：列出每个 API 的方法、路径、请求参数、返回结构
- **前端层设计**：列出新增/修改的页面、组件、路由
- **实施顺序**：按依赖关系排列实施步骤

**输出**：一份结构清晰的详细设计文档（参考本项目 `.trae/documents/` 下的示例）

#### Step 3：按设计文档写代码

做的事情：
- 按实施顺序逐个完成
- 每个步骤严格按照设计文档中的数据表、API、组件来写
- 写完一个步骤验证一个步骤

**输出**：可运行的代码

#### Step 4：验证

做的事情：
- 启动服务验证 API 可用
- 检查前端页面可正常渲染
- 跑通完整业务流

## 五、智能体决策树

当用户提出需求时，智能体按以下决策树判断要做什么：

```
用户提出需求
│
├─ 需求是"帮我写一个XX功能"？
│   ├─ 项目中已有 PRD？ → 读 PRD 理解业务
│   ├─ 项目中有设计文档？ → 读设计文档开始编码
│   └─ 都没有？ → 先产出一份详细设计文档，用户确认后再编码
│
├─ 需求是"帮我理解这个项目"？
│   ├─ 读 PRD → 了解业务全貌
│   ├─ 读设计文档 → 了解技术方案
│   └─ 读代码 → 了解具体实现
│
├─ 需求是"帮我优化/重构"？
│   ├─ 读当前设计文档 → 理解现有架构
│   ├─ 读代码 → 找到具体改动点
│   └─ 产出新的设计文档 → 说明改动方案
│
└─ 需求是"这个功能有问题/有Bug"？
    └─ 直接定位代码 → 修复 → 验证
```

## 六、如何写好一份详细设计文档（模板）

如果你需要产出一份详细设计文档，请遵循以下结构：

```markdown
# 详细设计文档：<功能名称>

## 背景
- 需求来源（关联的 PRD 或用户需求）
- 要解决什么问题
- 当前状态 vs 目标状态

## 差距分析
| 需求项 | 当前状态 | 目标状态 | 优先级 |
|--------|----------|----------|--------|

## 数据层设计
### 新增数据表
表名、字段、类型、约束、外键

### 修改数据表
ALTER TABLE 语句、新增字段、修改约束

## 接口层设计
| 方法 | 路径 | 说明 | 请求参数 | 返回结构 |
|------|------|------|----------|----------|

## 前端层设计
### 新增页面/组件
路径、功能、关键交互

### 修改页面/组件
文件路径、改动内容

## 工具函数/通用逻辑
- 通知触发
- 权限校验
- 数据转换

## 实施顺序
1. 第1步：xxx（依赖：无）
2. 第2步：xxx（依赖：第1步）
3. 第3步：xxx（依赖：第1、2步）

## 验证方式
- 如何验证每步正确
- 端到端测试流程
```

## 七、常见错误

### 错误1：跳过设计直接写代码

- PRD → 直接写代码
- **后果**：做到一半发现字段不够用、API 结构不合理、前端没法对接
- **正确做法**：先花 15 分钟产出设计文档，确认后再写

### 错误2：把 PRD 当设计文档用

- PRD 说"支持跨学段协作"就直接开始建表
- **后果**：不知道要建 guidance_materials 表还是 cross_level_assignments 表
- **正确做法**：按设计文档模板细化到表结构级别

### 错误3：设计师和开发看同一份文档

- 产品经理产出 PRD 后，后端、前端都按 PRD 直接开发
- **后果**：后端按自己对 PRD 的理解设计表，前端按自己的理解开发组件，两者对不上
- **正确做法**：先有统一的设计文档，前后端都按同一份设计文档开发

### 错误4：不更新设计文档

- 开发过程中发现设计不合理，直接改代码，不更新设计文档
- **后果**：设计文档和代码不一致，后续维护者困惑
- **正确做法**：设计文档随代码一起更新，保持一致

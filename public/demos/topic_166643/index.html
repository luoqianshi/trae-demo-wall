1 产品概述与核心价值

开发者和效率工具用户在 GitHub、Figma、Notion 等网站上工作时，往往不知道有哪些 Chrome 插件可以提升当前场景的工作效率。传统的找插件路径——打开 Chrome 应用商店、输入关键词、在大量无关结果中筛选——既耗时又打断工作流。场景化插件检索助手正是为消除这个信息差而生。

产品定位

进入任意网站，自动识别页面场景，一键展示当前网站专属可用 Chrome 插件。用户无需手动搜索、无需离开当前页面，所见即所得地获取场景化插件推荐。

2 整体技术架构

技术选型

维度 选型 选型理由
扩展规范 Manifest V3 Chrome 官方推荐，Service Worker 取代 background page，安全性和性能更优；Edge 完全兼容
前端框架 原生 HTML + CSS + JS MVP 阶段追求极致轻量，弹窗页面体量小，无框架开销；后续可迁移至 Preact/Vue
数据存储 chrome.storage.local 本地持久化，支持 JSON 对象读写，无需服务器；收藏数据不上传、不丢失
插件数据源 本地 JSON 数据库 MVP 阶段纯本地方案，零运维成本，离线可用；二期切换至云端 API
样式方案 CSS 变量 + 原子化类名 贴合 Chrome 原生风格，维护简单；通过 CSS 变量统一管理主题色

架构分层

扩展分为三层，各层职责清晰、耦合度低：

Popup Layer（弹窗层）

  • 用户直接交互的 UI 界面
  • 负责场景展示、插件列表渲染、搜索筛选交互
  • 通过 chrome.runtime.sendMessage 与 Service Worker 通信

Service Worker（服务层）

  • 扩展的核心调度中心
  • 域名解析与场景识别
  • 插件数据查询、排序、过滤逻辑
  • 收藏数据的 CRUD 操作

Data Layer（数据层）

  • data/sites.json — 站点场景映射字典
  • data/plugins.json — 插件数据库（含场景关联）
  • chrome.storage.local — 收藏持久化
设计原则：MVP 阶段不引入任何后端服务或网络请求（安装跳转除外）。所有数据本地内置，场景识别本地完成，搜索筛选本地执行。这保证了零延迟响应、离线可用、零运维成本。

3 模块设计与实现方案

3.1 场景识别模块

这是整个扩展的入口模块。当用户点击扩展图标时，系统首先需要回答一个问题：用户当前在哪个网站？

识别流程

  1. Popup 打开时，发送消息给 Service Worker，请求获取当前 Tab URL
  2. Service Worker 调用 chrome.tabs.query({ active: true, currentWindow: true }) 获取当前激活标签页
  3. 从 URL 中提取 hostname，通过正则清洗得到根域名（如 docs.github.com → github.com）
  4. 在 sites.json 场景字典中查找匹配项
  5. 返回场景 ID 和场景元信息（中文名、分类、图标等）给 Popup 渲染

域名解析算法

function extractRootDomain(url) {
  try {
    const hostname = new URL(url).hostname;
    // 处理常见二级域名前缀
    const prefixes = ['www', 'docs', 'app', 'staging', 'dev', 'blog'];
    const parts = hostname.split('.');
    let start = 0;
    while (prefixes.includes(parts[start]) && parts.length > 2) {
      start++;
    }
    // 保留至少最后两段 (example.com) 或三段 (example.co.uk)
    const remaining = parts.slice(start);
    if (remaining.length > 3) {
      return remaining.slice(-3).join('.');
    }
    return remaining.join('.');
  } catch {
    return null;
  }
}

匹配与排序逻辑

排序方式算法说明
综合推荐（默认） score = rating * 0.4 + log(users) * 0.35 + recency * 0.25 综合评分、安装量、更新时间三维加权，平衡热度与质量
评分最高 sortBy(rating, desc) 直接按用户评分降序排列
安装量最高 sortBy(users, desc) 按安装体量降序，反映插件普及度
最新更新 sortBy(updatedAt, desc) 按最近更新时间降序，优先展示活跃维护的插件

3.3 搜索与筛选模块

搜索和筛选在 Popup 前端本地执行，无需任何网络请求，保证实时响应。

模糊搜索实现

对用户输入的搜索词，同时匹配插件的 name、description 和 tags 字段。匹配算法采用大小写不敏感的子串包含检测，并计算匹配度得分（命中名称权重高于描述）。

function fuzzyMatch(plugin, query) {
  const q = query.toLowerCase();
  let score = 0;
  if (plugin.name.toLowerCase().includes(q)) score += 10;
  if (plugin.description.toLowerCase().includes(q)) score += 3;
  if (plugin.tags.some(t => t.includes(q))) score += 5;
  return score > 0 ? score : 0;
}

筛选条件

筛选器条件实现
仅免费 price === 'free' 布尔切换，默认关闭
高分筛选 rating >= 4.5 布尔切换，默认关闭

3.4 收藏持久化模块

基于 chrome.storage.local 实现收藏数据的增删查，数据结构与操作如下：

存储数据结构

// chrome.storage.local 中存储的收藏数据
{
  "favorites": ["octotree", "refined-github", "figma-dev-mode"]
  // 存储的是插件 ID 数组，而非完整插件对象
}
设计决策：收藏数据只存储插件 ID 而非完整对象，这样当插件数据更新时，收藏列表自动获取最新信息，无需额外同步逻辑。

API 操作封装

const Favorites = {
  async getAll() {
    const { favorites = [] } = await chrome.storage.local.get('favorites');
    return favorites;
  },
  async add(pluginId) {
    const list = await this.getAll();
    if (!list.includes(pluginId)) {
      await chrome.storage.local.set({ favorites: [...list, pluginId] });
    }
  },
  async remove(pluginId) {
    const list = await this.getAll();
    await chrome.storage.local.set({ favorites: list.filter(id => id !== pluginId) });
  },
  async has(pluginId) {
    const list = await this.getAll();
    return list.includes(pluginId);
  }
};

3.5 安装跳转模块

每个插件卡片提供「前往安装」按钮，点击后通过 chrome.tabs.create({ url: storeUrl }) 在新标签页打开 Chrome 应用商店对应插件详情页。URL 格式统一为 https://chromewebstore.google.com/detail/{extension-id}，确保跳转安全可靠。

3.6 未知场景兜底

当用户当前网站不在 sites.json 预置字典中时，展示友好的兜底界面：顶部显示「当前平台暂无专属适配插件」的提示文案，下方提供一个全局搜索框，允许用户输入任意关键词进行跨场景插件搜索。

6 核心流程与状态机

6.1 弹窗打开 → 场景展示流程

  1. 用户点击扩展图标 → Popup popup.html 加载
  2. Popup 的 DOMContentLoaded 触发，发送 { type: 'GET_SCENE' } 消息给 Service Worker
  3. Service Worker 获取当前 Tab URL → 解析根域名 → 匹配 sites.json
  4. 若匹配成功：返回 { scene: { id, name, category } }；否则返回 { scene: null }
  5. Popup 根据场景 ID 向 Service Worker 请求插件列表 { type: 'GET_PLUGINS', sceneId, sort, filter }
  6. Service Worker 从 plugins.json 中按场景过滤、排序、截取后返回
  7. Popup 渲染插件卡片列表

6.2 搜索交互流程

  1. 用户在搜索框输入文字 → 触发 input 事件（200ms 防抖）
  2. Popup 本地执行模糊匹配过滤当前场景插件列表
  3. 重新渲染卡片列表，高亮匹配文字（可选）

6.3 收藏交互流程

  1. 用户点击心形图标 → 切换收藏状态
  2. 若添加收藏：调用 chrome.runtime.sendMessage({ type: 'TOGGLE_FAVORITE', pluginId })
  3. Service Worker 调用 Favorites.add() 或 Favorites.remove() 更新存储
  4. 返回最新收藏状态，Popup 更新图标样式
性能保障：场景识别在 Service Worker 中同步完成，耗时 < 1ms。插件数据预加载到内存，搜索过滤在前端执行，整个弹窗打开到内容完整呈现的目标时间 < 300ms。

8 开发计划与里程碑

8.1 开发里程碑

第 1 阶段：基础框架搭建（Day 1-2）

创建工程目录、编写 manifest.json、搭建 Popup HTML/CSS 骨架、实现 Service Worker 消息通信通道。完成「空白弹窗 → 消息传递 → 返回结果」的最小闭环。

第 2 阶段：核心功能开发（Day 3-5）

实现场景识别模块、编写 sites.json 和 plugins.json 数据库、完成插件列表渲染、搜索筛选排序逻辑、收藏功能。本阶段结束时，扩展可完整运行核心流程。

第 3 阶段：UI 打磨与边界处理（Day 6-7）

完善空状态界面、骨架屏加载态、搜索防抖优化、卡片交互动画。确保 300ms 内完成弹窗内容渲染。

第 4 阶段：测试与上架准备（Day 8-10）

编写单元测试覆盖核心模块、跨浏览器兼容性测试（Chrome + Edge）、准备应用商店素材（图标、截图、描述文档）、提交 Chrome Web Store 审核。

9 二期演进路线

MVP 验证产品假设后，二期将围绕数据规模、智能化和用户自定义三个方向演进：

云端数据服务

将插件数据从本地 JSON 迁移至云端 API，支持热更新插件库。用户无需升级扩展即可获取新增平台和插件数据。

智能识别增强

自动检测已安装插件并标记状态；基于用户使用频率和社区热度智能调整推荐排序；新上线插件优先展示。

用户自定义扩展

允许用户自行添加站点和插件关联；支持插件详情预览弹窗（功能介绍、截图、使用场景）；开放插件数据贡献通道。

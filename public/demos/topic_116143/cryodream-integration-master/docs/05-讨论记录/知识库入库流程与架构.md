## 二、入库模式

系统支持 9 种入库模式，通过 `ingestionMode` 参数指定：

| 模式 | 说明 | 处理方法 |
|------|------|----------|
| `standard` | 普通 RAG 入库 | `standardIngestDocument()` — 分块+向量化 |
| `deep` | 认知级 RAG 入库 | `cognitiveIngestDocument()` — LLM 摘要+分块+向量化 |
| `auto` | 自动判断 | `resolveIngestionMode()` 根据文档信号词和长度自动选择 standard/deep |
| `none` | 不入库 | 仅保存文档，不做任何提取 |
| `thinking-model` | 思维模型入库 | `thinkingModelIngestDocument()` |
| `event` | 事件提取 | `runEventIngestion()` |
| `viewpoint` | 观点提取 | `runViewpointIngestion()` |
| `case` | 案例提取 | `runCaseIngestion()` |
| **`structured`** | **结构化提取（核心）** | `runStructuredIngestion()` — 六步流水线 |

### 模式自动判断逻辑 (`resolveIngestionMode`)

```
1. 明确指定模式 → 直接使用
2. auto 模式 → 根据信号词和长度判断：
   ├─ Markdown/TXT 且 < 1500字 + 无深度信号 → standard
   ├─ 含标准信号词（API、说明书、操作手册等）→ standard
   ├─ 含深度信号词（观点、趋势、会议纪要等）→ deep
   └─ 文本长度 > 4000 → deep，否则 → standard
```

## 三、结构化提取六步流水线

`runStructuredIngestion()` 是知识图谱构建的核心，执行以下 6 步：

### 步骤 1：内容分类

**组件**: `ContentTypeClassifier`

**功能**: 调用 LLM 判断文档的内容类型

**输出分类**:
- 描述型 — 客观描述事物
- 事件密集型 — 包含大量因果事件
- 观点密集型 — 以观点讨论为主
- 案例型 — 以实际案例为主体
- 方法论型 — 介绍方法或理论

**作用**: 分类结果传递给后续提取器，动态调整提取策略（提取力度、数量约束）

### 步骤 2：实体提取

**组件**: `EntityExtractor`

**功能**: 从文档中提取命名实体

**提取策略** (根据分类动态调整):
| 分类 | 策略 |
|------|------|
| 描述型 | 只提取核心主体（1-3个） |
| 事件密集型 | 提取事件核心参与者（3-8个） |
| 观点密集型 | 只提取观点持有者和讨论对象（1-4个） |
| 案例型 | 只提取案例主角和方法论关键词（2-5个） |
| 方法论型 | 只提取核心概念和理论名称（2-4个） |

**提取原则**: "宁缺毋滥"
- 500字建议 2-4 个实体
- 2000字建议 6-8 个实体
- 排除泛指词、仅出现一次的名称、时间/数字

**去重逻辑** (`RelationBuilder.saveEntities`):
- 预加载知识库全部已有实体到内存映射
- 按名称+别名匹配去重
- 跨文档同名实体合并（别名累积）
- 本批次内去重（避免同一文档重复提取）

### 步骤 3：事件提取

**组件**: `EventExtractor`

**功能**: 从文档中提取因果事件

**条件**: 观点密集型文档（短文）跳过事件提取

**提取策略**:
| 分类 | 策略 |
|------|------|
| 描述型 | 通常无事件，确实没有则返回空数组 |
| 事件密集型 | 正常提取核心事件链（3-5个） |
| 观点密集型 | 只提取观点依附的核心事件（1-2个） |
| 案例型 | 只提取关键转折点（1-3个） |
| 方法论型 | 直接返回空数组 |

**必填约束**: 每个事件必须有 subject（主体）+ action（动作）+ result（结果）

**后处理过滤**: 跳过无 subject/action/result 的事件

**因果索引修正**: `originalIndexToSavedIndex` 映射，过滤事件后修正 `cause_event_index`

**关系构建** (`RelationBuilder`):
1. `saveEvents` — 保存事件到 DB，建立 Entity→Event 角色（发起/受影响/参与等）
2. `resolveEntityId` — 三级模糊匹配（精确→包含→反向包含），解决事件 subject 和实体名称不一致问题
3. `buildCooccurrenceRelations` — 孤立实体创建虚拟"同文档关联"事件（eventType=cooccurrence），确保无孤立节点
4. 同文档无因果链事件对建立"同文档"关系
5. Neo4j 写入（如果可用）

### 步骤 4：观点提取

**组件**: `ViewpointExtractor`

**条件**: 案例型短文跳过

**输出字段**: viewpoint_content, topic, claim_type（fact/opinion/prediction）, confidence, entity_name, related_event

**实体关联**: 通过 entity_name 匹配已有实体，建立 Entity→Viewpoint "发表观点"关系

**向量化**: 观点内容自动生成 contentEmbedding

### 步骤 5：案例提取

**组件**: `CaseExtractor`

**条件**: 案例型 或 文本长度 > 3000

**输出字段**: case_name, industry, scenario, background, approach, process, result, experience, lessons

**向量化**: approach 和 experience 分别生成 embedding

**Neo4j**: 写入案例节点（如果可用）

### 步骤 6：RAG 向量化入库

**功能**: 为所有提取的结构化数据生成 knowledge_chunk 并向量化，使其可被 RAG 检索命中

**数据格式**:
| 数据类型 | chunk 文本格式 |
|----------|---------------|
| 实体 | 【实体】名称（类型）：描述 |
| 事件 | 【事件】动作，结果：结果（事件类型） |
| 观点 | 【观点】观点内容（主题：主题）[claim_type] |
| 案例 | 【案例】案例名（行业） 方法：xxx 经验：xxx |

**字段复用**: `chunkLevel` 存 sourceType，`parentId` 存 sourceId，`metadata` 存 source_type 和 source_id

### 关系类型

**Entity → Event 角色** (`entity_event_roles.role`):
- 发起 / 导致 — 实体主动发起事件
- 受影响 — 实体被事件影响
- 参与 — 实体参与事件
- 共现 — 同文档孤立实体与虚拟"同文档关联"事件的连接

**Event → Event 关系** (`event_relations.relation_type`):
- 导致 — 因果关系（cause_event_index 驱动）
- 同文档 — 同文档内无因果链的事件对

**Entity → Viewpoint 关系**:
- 发表观点 — 通过 viewpoints.entity_id 关联

## 五、API 接口

### 文档入库

| 接口 | 方法 | 说明 |
|------|------|------|
| `/ingestion/document` | POST | 文档内容入库（kbId, title, content, fileType, ingestionMode） |
| `/ingestion/upload` | POST | 上传文件入库 |
| `/ingestion/file` | POST | 文件路径入库 |
| `/ingestion/url` | POST | URL 网页入库 |
| `/ingestion/douyin` | POST | 抖音链接入库 |
| `/ingestion/upload/async` | POST | 异步文件上传入库 |
| `/ingestion/douyin/async` | POST | 异步抖音入库 |
| `/ingestion/cognitive` | POST | 触发认知级/结构化入库（异步任务，需传 documentId + ingestionMode + modelConfigId） |

### 知识图谱

| 接口 | 方法 | 说明 |
|------|------|------|
| `/knowledge-graph/graph-data?kbId=xxx` | GET | 获取图谱可视化数据（nodes + edges + stats） |
| `/knowledge-graph/clear-data?kbId=xxx` | POST | 清空知识库结构化数据 |

### 入库触发流程

```
1. 上传文档 → POST /ingestion/document → 文档状态: parsed
2. 触发提取 → POST /ingestion/cognitive → 创建异步任务
3. 任务执行 → tieredIngestDocument() → runStructuredIngestion()
4. 完成 → 文档状态: completed
```

**注意**: 上传文档（步骤1）和触发提取（步骤2）是分开的。上传只保存文档并解析内容，需要单独调用 cognitive 接口触发提取。

## 六、前端知识图谱

**位置**: 知识库详情页中间区域，与文档编辑器 tab 切换

**组件**: `KnowledgeGraphView` — 基于 force-graph 库

**节点类型与配色**:
| 类型 | 颜色 | 形状 | 大小 |
|------|------|------|------|
| 实体 (entity) | 紫色 #6366f1 | 圆形 | 8 |
| 事件 (event) | 琥珀色 #f59e0b | 菱形 | 6 |
| 观点 (viewpoint) | 绿色 #10b981 | 六边形 | 5 |

**功能**:
- 类型筛选（独立切换按钮）

- 白色背景 + 彩色节点 + 深色标签 + 浅灰连线

## 八、已知约束与注意事项

1. **modelConfigId 必须指定** — 结构化提取调用 LLM，不传 modelConfigId 会报"没有可用的对话模型配置"
2. **entity_event_roles.event_id 不允许 null** — 共现关系通过虚拟事件（eventType=cooccurrence）实现
3. **@Transactional 陷阱** — `runStructuredIngestion` catch 块不更新文档状态，由 controller 的 catch 处理；`markDocumentFailed` 使用 REQUIRES_NEW 传播级别
4. **JSONB 字段安全** — artifacts/evidence/related_event_ids 等字段使用 safeJsonArray/safeJsonObj 处理无效 JSON
5. **PowerShell 中文编码** — Invoke-RestMethod 传中文必须用 UTF-8 文件方式，不能直接 ConvertTo-Json + Body
6. **Milkdown 上下文** — 切换 tab 时不销毁编辑器（隐藏而非卸载），避免 context missing 错误
7. **版本号存字符串** — 如 "1.01"、"1.02"
8. **歌词数据格式** — JSON 字符串：`{"lines":[{"id":1,"text":"[Verse 1]"},...]}`

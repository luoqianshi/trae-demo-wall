# 知识库模块完整开发计划

## 模块概述

**模块名称**：知识库管理模块
**模块目标**：实现完整的知识库管理功能，包括文档上传、预览编辑、入库流水线三大核心功能。与 RAG 模块一（知识入库流水线）形成闭环。
**计划周期**：2026-06-18 - 2026-06-20

### 用户故事

```
作为一名知识管理员，
我希望上传 Markdown 文档到知识库，
以便系统能够自动解析、提取元数据、入库向量检索。
```

```
作为一名知识管理员，
我希望预览和编辑文档内容，
以便在入库前确认文档质量。
```

```
作为一名知识管理员，
我希望点击"入库"按钮执行完整入库流水线，
以便将文档转化为可检索的向量数据。
```

```
作为一名知识库维护者，
我希望知识入库按钮默认执行系统内置 RAG 工作流，
以便通过调整默认工作流节点、提示词和模型配置来微调入库效果，而不是每次改后端代码。
```

### 功能边界

**包含范围**：
- 知识库 CRUD 管理
- 文档上传（支持 .md / .markdown / .txt / .pdf / 视频文件 / 抖音链接）
- 视频→Markdown 转录（FFmpeg Whisper 本地转录）
- 抖音链接→本地视频→Markdown（携带 Cookie 解析，宿主机媒体库保存视频，复用视频转录工作流）
- 文档预览与编辑
- 手动单文档入库与批量文档入库
- 分级入库：自动分流 / 普通 RAG / 认知级 RAG
- 入库失败原因展示与重试
- 入库流水线执行（工作流节点串联）
- 入库进度跟踪

**不包含范围**（后续模块）：
- RAG 模块二：动态检索引擎
- RAG 模块三：研判生成系统
- PDF 文档解析
- 批量文档入库

### 2.1 数据库设计（已存在）

```sql
-- 知识库表
CREATE TABLE knowledge_base (
    id BIGSERIAL PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    description VARCHAR(500),
    domain VARCHAR(100),
    embedding_model_id BIGINT,
    chunk_count INT DEFAULT 0,
    create_time TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    update_time TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    is_delete TINYINT DEFAULT 0
);

-- 文档表
CREATE TABLE document (
    id BIGSERIAL PRIMARY KEY,
    knowledge_base_id BIGINT NOT NULL,
    title VARCHAR(200) NOT NULL,
    file_type VARCHAR(20),
    file_path VARCHAR(500),
    file_size BIGINT,
    raw_text TEXT,
    global_metadata JSONB,
    status VARCHAR(20) DEFAULT 'pending',
    chunk_count INT DEFAULT 0,
    create_time TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    update_time TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    is_delete TINYINT DEFAULT 0
);

-- Chunk 表（含向量）
CREATE TABLE knowledge_chunk (
    id VARCHAR PRIMARY KEY,
    doc_id VARCHAR NOT NULL,
    kb_id VARCHAR NOT NULL,
    content TEXT,
    embedding VECTOR(1024),
    metadata JSONB,
    create_time TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    is_delete SMALLINT DEFAULT 0,
    chunk_index INT,
    chunk_text TEXT NOT NULL,
    raw_text TEXT,
    parent_id VARCHAR,
    chunk_level VARCHAR,
    events JSONB
);
```

#### 新版 metadata jsonb 与父子 Chunk 结构

`knowledge_chunk` 现在同时通过表字段和 `metadata jsonb` 表达父子结构：

| 层级信息 | 位置 | 说明 |
|----------|------|------|
| `chunk_level` | 表字段 + `metadata.2_Ontology_Routing.chunk_level` | `parent` / `child` |
| `parent_id` | 表字段 | 子块指向落库后的真实父块 ID |
| `parent_local_id` | `metadata.2_Ontology_Routing.parent_local_id` | LLM 输出中的本地父块标识，用于落库前映射 |
| `events` | 表字段 + `metadata.2_Ontology_Routing.events` | SPO 事件数组，替代旧 `event_id` |

新版 metadata 示例：

```json
{
  "1_Domain_Scope": {
    "domain": "个人成长/思维模型",
    "theme": "第一性原理思维解析与应用"
  },
  "2_Ontology_Routing": {
    "chunk_level": "child",
    "parent_local_id": "parent_0",
    "entities": [
      {"name": "埃隆·马斯克", "description": "第一性原理思维的实践者"}
    ],
    "concepts": [
      {"name": "第一性原理", "description": "从基本事实出发推导解决方案的思维方式"}
    ],
    "events": [
      {"subject": "埃隆·马斯克", "action": "应用", "object": "第一性原理", "result": "重构火箭制造成本", "event_time": "", "assertion_time": "", "event_type": "观点论证", "causal_role": "evidence", "evidence": "马斯克用第一性原理重构制造成本"}
    ]
  },
  "3_Epistemology_Tag": {
    "time_stamp": "2026-06-26",
    "claim_type": "案例分析",
    "source": "document",
    "confidence": 0.8,
    "chunk_summary": "马斯克用第一性原理重构制造成本"
  }
}
```

旧结构里的 `event_id` 已废弃，后续检索、图谱抽取和研判溯源应读取 `events` 数组。

### 2.4 入库流水线设计

#### 新思路：默认工作流驱动的知识入库

知识库详情页的 RAG 入库按钮不再被理解为一个固定写死的后端流程，而是一个默认工作流触发器。按钮提交文档、入库模式和运行时模型后，后端根据模式加载系统内置工作流模板，再由工作流节点完成文档加载、全局元数据提取、智能分块、向量化写入。

这种设计的核心价值是把“入库策略”从后端代码中解耦出来：

- 普通 RAG、认知级 RAG、自动分级 RAG 都可以对应不同系统工作流模板。
- 工作流模板中的节点顺序、节点参数、提示词、模型配置可以作为模块调优入口。
- 后端保留兜底能力，避免工作流配置不完整时任务直接失败。
- 后续要优化入库效果，优先调整默认工作流，而不是修改知识库页面或重写入库服务。

当前系统模板约定：

| 模式 | 模板 ID | 说明 |
|------|---------|------|
| 普通 RAG | `tpl-standard-rag-ingestion` | 文档加载 → LLM 语义分块 → 知识库写入 |
| 认知级 RAG | `tpl-cognitive-rag-ingestion` | 文档加载 → 全局元数据提取 → 认知级分块 → 知识库写入 |
| 自动分级 RAG | `tpl-tiered-rag-ingestion` | 根据文档规模和模式参数路由到普通或认知级入库 |

#### 当前执行链路

```
知识库详情页入库按钮
  ↓
submitCognitiveIngest(documentId, modelConfigId, ingestionMode)
  ↓
POST /api/ingestion/cognitive
  ↓
创建异步 Task，文档状态进入 processing
  ↓
KnowledgeBaseIngestionService.tieredIngestDocument
  ↓
根据 ingestionMode 选择默认工作流模板
  ↓
FlowGraphExecutor 按节点连线执行
  ↓
KnowledgeBaseWriter 写入 knowledge_chunk 和向量数据
  ↓
文档状态 completed / failed，Task 进度 100 / 失败原因
```

#### 模型选择优先级

RAG 入库模型选择采用运行时优先策略，避免工作流模板中残留的旧模型配置覆盖用户当前配置。

```text
前端 / 运行时显式传入 modelConfigId
  > 自动选择可用 chat / llm 模型
  > 工作流模板节点内置 model_config_id
```

自动选择模型时，后端会同时识别：

```text
model_type = chat
model_type = llm
```

因此，类似“讯飞Qwen3.6”这类 `chat` 类型模型也可以作为 RAG 入库 LLM 使用，不会再因为只筛选 `llm` 而被忽略。

#### 工作流可微调点

该模块后续调优时应优先从默认工作流入手：

| 调优对象 | 调优方式 | 影响范围 |
|----------|----------|----------|
| LLM 模型 | 修改 GlobalMetadataExtractor / IntelligentSemanticChunker 节点模型 | 影响元数据质量、分块质量和耗时 |
| 提示词 | 调整全局元数据提取和语义分块提示词 | 影响 domain/theme/entities/concepts/events 的抽取质量 |
| 分块参数 | 调整 chunk_size / overlap_size / 父子块策略 | 影响召回粒度和上下文完整性 |
| Embedding 模型 | 修改 KnowledgeBaseWriter 节点 embedding_model_id | 影响向量维度、检索召回和向量库兼容性 |
| 节点连线 | 增删 MetadataAttacher、质量检查、过滤节点 | 影响入库流水线能力边界 |
| 失败兜底 | 调整 LLM 超时、重试、规则分块回退策略 | 影响稳定性和任务完成率 |

原则：

```text
能通过默认工作流修正的，不优先改知识库页面；
能通过节点参数/提示词修正的，不优先改核心服务代码；
只有工作流执行引擎、模型选择、数据落库一致性问题，才进入后端代码修复。
```

#### 流程图

```
┌─────────┐    ┌─────────┐    ┌─────────┐    ┌─────────┐    ┌─────────┐
│ 文档上传 │───→│ 解析文本 │───→│ 提取元数据│───→│ 语义分块 │───→│ 向量入库 │
└─────────┘    └─────────┘    └─────────┘    └─────────┘    └─────────┘
     │              │              │              │              │
     ↓              ↓              ↓              ↓              ↓
  创建记录      解析为纯文本    LLM提取      按段落切分      PGVector入库
  status:new    更新raw_text   更新metadata   生成chunks     状态更新
```

#### 工作流节点串联

```
普通 RAG：
DocumentLoader
  → IntelligentSemanticChunker
  → KnowledgeBaseWriter

认知级 RAG：
DocumentLoader
  → GlobalMetadataExtractor
  → IntelligentSemanticChunker
  → KnowledgeBaseWriter
```

节点职责：

```
节点1: DocumentLoader
  输入: document_id / content
  输出: raw_text

节点2: GlobalMetadataExtractor
  输入: raw_text
  输出: 文档级全局 metadata，作为后续 chunk 元数据继承来源

节点3: IntelligentSemanticChunker
  输入: raw_text + metadata + model_config_id
  输出: chunks[]，包含 parent / child 层级、parent_local_id、events(SPO) 和新版 metadata jsonb

节点4: KnowledgeBaseWriter
  输入: chunks[], kb_id, doc_id, embedding_model_id
  输出: 入库结果
```

当前认知级 RAG 不再依赖单独 MetadataAttacher 节点作为必经路径，分块节点会在生成 chunk 时直接构造新版 metadata jsonb；规则兜底路径也会继承全局元数据，避免出现 `未分类 / 未知主题 / entities=[] / concepts=[]` 的空元数据。父子结构由 `chunk_level`、`parent_id`、`parent_local_id` 共同表达，事件关系统一使用 `events(SPO)`，不再使用旧 `event_id`。

## 技术方案

### 3.1 文件存储

**方案**：本地文件系统存储 + 数据库路径引用

```java
// 文件存储路径
private static final String UPLOAD_DIR = "/data/documents/";

// 存储策略
String fileName = UUID.randomUUID() + "_" + originalName;
String filePath = UPLOAD_DIR + kbId + "/" + fileName;

// 后续可扩展：COS/OSS 对象存储
```

### 3.2 文档统一 Markdown 化

**方案**：上传阶段统一保存原始文件，并将可解析内容转换为 Markdown 存入 `knowledge_document.raw_text`。

| 原始类型 | 转换策略 | raw_text 存储内容 |
|---------|---------|------------------|
| md / markdown | 原样保留 | Markdown 原文 |
| txt | 包装为 Markdown 段落 | 文本内容，保留换行 |
| pdf | 提取每页文本并按页码组织 | `## 第 N 页` + 页面文本 |
| 视频文件 | FFmpeg 抽音轨 → Whisper 转录 → SRT → Markdown | `# 视频标题` + `## HH:MM:SS` 时间戳分段字幕 |

**关键约束**：
- `file_type` 记录原始文件类型
- `file_path` 记录原始文件保存路径
- `raw_text` 统一保存 Markdown 格式内容
- 上传解析完成后文档状态为 `parsed`（已解析），不自动入库
- 只有用户手动点击"认知级 RAG 入库"后，才进入 `processing → completed` 入库状态
- 后续智能分块、全局元数据、父子 Chunk 均基于 Markdown 内容执行
- 不再剥离 Markdown 标题、列表、代码块等结构信息

### 3.3 异步入库

**方案**：Spring @Async + ThreadPoolTaskExecutor

@Async("taskExecutor")

## 风险与对策

| 风险 | 影响 | 对策 |
|------|------|------|
| 大文件上传超时 | 用户体验 | 前端分片上传，后端合并 |
| 入库过程中断 | 数据不一致 | 状态机管理，支持断点续传 |
| 向量维度不匹配 | 检索失败 | 上传时校验模型维度，一致才入库 |
| LLM 调用失败 | 元数据提取失败 | 任务失败和 knowledge_document.failed 独立同步，避免事务回滚导致页面仍显示进行中 |
| 成功后仍显示上次失败信息 | 文档状态 completed 但 error_message 残留 | 所有入库成功分支统一清空 knowledge_document.error_message |
| 模型配置 max_tokens 过小 | JSON 输出被截断，结构化修复仍失败 | RAG 元数据提取显式使用 4000 输出预算，分块显式使用 6000 输出预算，修复器显式使用 4000 输出预算，不再被模型配置 1000 限死 |
| LLM JSON 输出不完整 | 元数据提取或分块解析失败 | StructuredJsonOutputRepairer 按 schema 将原始响应和错误信息发回模型修复，最多重试 2 次；仍失败再进入失败态同步 |
| 工作流模板残留旧模型 | 入库实际模型与预期不一致 | 运行时模型优先覆盖节点旧模型，fallback 支持 chat / llm |
| 提示词过复杂 | 模型响应慢、超时或返回不可解析 | 优先在默认工作流中拆分提示词职责，普通 RAG 保持轻量分块，认知级 RAG 分阶段抽取元数据 |
| Chunk 元数据空结构 | 检索路由失效 | 分块器兼容新版 metadata jsonb，规则兜底继承 document.metadata |
| events 全为空 | 无法做轻量 GraphRAG 事件抽取 | 全局元数据和 Chunk 元数据统一使用事理图谱事件结构；Chunk 缺失 events 时先按 chunk_text 筛选全文事件，再规则推断，无证据则保持空数组 |
| Event Time 与 Assertion Time 混淆 | 时序图谱错误，把发布时间当作事件发生时间 | 每个 event 自带 `event_time`；`assertion_time` 仅在文本明确发布/记录/断言时间时填写；`3_Epistemology_Tag.time_stamp` 表示入库/元数据生成时间，不替代事件发生时间 |
| 旧 event_id 回流 | 新旧结构混用，前端和检索解析歧义 | 全局元数据、MetadataAttacher、默认工作流模板均移除 event_id，统一使用 events(SPO) |
| 任务长期 running | 用户无法判断真实状态 | 所有异常链路必须回写 Task failed 和 document error_message |

## 后续优化点

### 默认工作流配置化

- 在系统工作流页面明确标记“当前默认知识入库工作流”。
- 支持把某个工作流模板设置为普通 RAG、认知级 RAG、自动分级 RAG 的默认模板。
- 支持工作流模板版本管理，入库任务记录执行时使用的模板版本，便于回溯。
- 支持工作流模板灰度：同一知识库可选择稳定版、实验版入库模板。

### 入库质量观测

- 在任务结果中记录每个阶段耗时：文档加载、元数据提取、语义分块、Embedding、写库。
- 记录 LLM 分块是否成功、是否触发规则兜底、最终 chunk_method。
- Chunk 详情页展示 domain/theme/chunk_level/parent_id/entity_count/concept_count/event_count 的质量指标。
- 对空元数据、父子关系缺失、低置信度、过短 chunk、过长 chunk 给出质量告警。

### 提示词与模型调优

- 普通 RAG 保持轻量 LLM 分块，重点保证速度和稳定性。
- 认知级 RAG 分阶段抽取元数据，避免一个提示词同时承担分块、实体、概念、事件、SPO、父子结构全部任务。
- 对不同模型维护不同提示词 profile，例如讯飞、火山、DeepSeek 可有不同 JSON 输出约束。
- 增加 LLM 返回内容的调试开关，仅在开发环境保存脱敏后的响应片段，便于定位 JSON 解析问题。

### 稳定性与回退

- LLM 超时应按节点维度配置，不同节点可设置不同 read timeout 和重试次数。
- 所有 fallback 都必须继承上游可用的 domain/theme，并对 entities/concepts/events 做 chunk_text 局部筛选；不允许写入无证据的全文级实体、概念和事件。
- 任务异常必须最终落到 completed 或 failed，不能长期停留在 running。
- 支持对失败任务进行“从指定节点重跑”，减少大文档重复处理成本。

### 检索侧联动

- 入库 metadata 应服务后续混合检索，domain/theme/entities/concepts/claim_type/confidence/time_stamp/event_time/assertion_time/event_type/causal_role 都应可作为过滤条件。
- Embedding 文本建议拼接 chunk_text + entity name/description + concept name/description，降低短标签语义坍塌。
- 后续检索模块应优先使用 metadata 预过滤，再做向量召回。

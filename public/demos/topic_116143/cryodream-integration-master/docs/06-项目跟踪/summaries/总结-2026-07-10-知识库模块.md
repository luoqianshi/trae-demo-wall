# 知识库模块总结（思维 / 事件 / 案例）

> 本文是对当前知识库模块中 **思维模型 / 事件入库 / 案例入库** 三大结构化入库子模块的完整代码扫描与架构总结。
> 三者均采用「工作流模板驱动 + LLM 结构化提取 + 双写检索」的统一范式，但在数据形态、检索策略、展示视图上各有差异。

---

## 一、整体架构

### 1.1 统一范式

三个子模块共享同一套入库骨架：

```
[前端触发 ingestionMode]
  → /ingestion/cognitive 异步任务
  → KnowledgeBaseIngestionService.tieredIngestDocument(mode 路由分发)
  → xxxIngestDocument(documentId, modelConfigId)
      → 加载 tpl-xxx-ingestion 模板 graphJson
      → injectXxxRuntimeValues 注入运行时值（document_id / model_config_id / kb_id / raw_text）
      → flowGraphExecutor.execute 整图执行
          → DocumentLoader → PromptTemplate → LanguageModel → FormatValidator → XxxWriter
      → 文档状态更新为 completed，resolvedIngestionMode 标记
```

### 1.2 三模块横向对比

| 维度 | 思维模型 | 事件入库 | 案例入库 |
|------|----------|----------|----------|
| **定位** | Text-to-Tool，提取 Agent 可调用的 Function Calling 工具 | 时序情报提取，事件+实体图谱 | 多维商业案例库，症状→方案→结果 |
| **模板 ID** | `tpl-thinking-model-ingestion` | `tpl-event-ingestion` | `tpl-case-ingestion` |
| **数据表** | `thinking_model` | `knowledge_events` | `knowledge_cases` |
| **RAG 双写** | ❌ 跳过向量化 | ✅ 写 `knowledge_chunk`（chunk_level='event'） | ✅ 写 `knowledge_chunk`（chunk_level='case'） |
| **FormatValidator** | `json_object` | `json_object` | `json_object` |
| **检索方式** | 不参与 RAG 检索，直接由 Agent 调用 | pgvector cosine + LIKE 降级 | JSONB `@>` 硬过滤 + pgvector + LIKE 降级 |
| **前端视图** | 管理卡片网格 + 详情弹窗 | 时间线 / 列表 / 关系图 三视图 | 卡片列表 + 详情面板 |
| **入口节点** | DocumentLoader（结构化任务，非对话式） | DocumentLoader | DocumentLoader |
| **去重策略** | 同名工具模糊匹配覆盖（`findByNameFuzzy` ILIKE） | 无（每文档独立事件） | 无 |

## 二、思维模型模块（ThinkingModel）

### 2.1 模块定位

将方法论文章压成 **Agent 可直接调用的标准化 Function Calling 工具 JSON**。跳过分块和向量化，直接落库生效。输出包含 `tool_schema`（含 name/description/parameters）、`execution_prompt`（步骤化指令）、`routing_category`（4 大分类）、`tags`（路由关键词）。

### 2.2 数据模型

**表**: `thinking_model` | **实体**: [ThinkingModel.java](file:///g:/ice-project/comfyUI-draw-flow/service/src/main/java/com/ice/template/model/entity/ThinkingModel.java)

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | VARCHAR(64) | 主键，ASSIGN_UUID |
| `kb_id` | VARCHAR | 所属知识库 |
| `model_id` | VARCHAR | 如 `tool_swot_001` |
| `model_name` | VARCHAR | 模型中文名 |
| `routing_category` | VARCHAR | 战略与商业 / 诊断与分析 / 流程与执行 / 表达与沟通 |
| `tags` | JSONB | 数组，AI Agent 路由匹配关键词 |
| `tool_schema` | JSONB | Function Calling 工具定义（name/description/parameters/required） |
| `execution_prompt` | TEXT | 步骤化指令，AI 拿到后直接干活 |
| `raw_text` | TEXT | 原始输入文本，用于溯源 |
| `is_active` | BOOL | 启用状态 |
| `is_delete` | INT | 逻辑删除 |

### 2.3 工作流节点链

**模板定义**: [KnowledgeSchemaMigration.java](file:///g:/ice-project/comfyUI-draw-flow/service/src/main/java/com/ice/template/config/KnowledgeSchemaMigration.java) `ensureThinkingModelIngestionTemplate()`

```
DocumentLoader ──text──▶ LanguageModel.input_value
PromptTemplate ──prompt──▶ LanguageModel.system_message
LanguageModel ──response──▶ FormatValidator.input
FormatValidator ──output──▶ ThinkingModelWriter.input
```

| 节点 | 关键配置 |
|------|----------|
| DocumentLoader | 运行时注入 `document_id`，`file_type=md` |
| PromptTemplate | 内嵌 `EXTRACTION_PROMPT`，约束 LLM 输出标准化工具 JSON Schema |
| LanguageModel | `model_config_id`（留空自动选择），`temperature=0.1`，`modelType=chat` |
| FormatValidator | `expected_format=json_object` |
| ThinkingModelWriter | 自动注入 `raw_text`，解析 JSON → 构建 ThinkingModel → `saveOrOverwrite` 落库 |

**Service 核心方法**：
- `extractAndSave` — 同步提取 + 落库，调用 `StructuredJsonOutputRepairer.parseOrRepairObject` 修复 JSON
- `extractOnly` — 预览流程，先用 `JUDGMENT_PROMPT` 判断是否思维模型（confidence ≥ 0.5），结果缓存入 `pendingExtractions`（10 分钟自动清理）
- `confirmSave` — 按 `extractId` 取缓存落库
- `saveOrOverwrite` — **按模型名称 ILIKE 模糊匹配去重**，同名工具覆盖更新
- `resolveModelConfig` — 无配置抛异常而非静默降级

### 2.6 关键设计约束

1. **跳过分块和向量化**，直接提取标准化工具 JSON 落库
2. `FormatValidator` 用 `json_object`，不是 `json_candidates`
3. `LanguageModel` 必须指定 `model_config_id`，无配置抛异常
4. `routing_category` 仅限 4 个值
5. `tool_schema` 必须含 `name` / `description` / `parameters`
6. `execution_prompt` 必须步骤化，使 AI 能按方法论执行
7. 同名工具模糊匹配去重（`findByNameFuzzy` ILIKE）
8. LLM 调用不包裹 `@Transactional`

## 三、事件入库模块（Event）

### 3.1 模块定位

从文档中提取**带时间维度的结构化事件**，支持时间轴、列表、关系图三视图展示。采用「事件为中心、自包含」设计——实体作为 JSONB 内嵌数组存储在事件内，不单独建表。

### 3.2 数据模型

**表**: `knowledge_events` | **实体**: [KnowledgeEvent.java](file:///g:/ice-project/comfyUI-draw-flow/service/src/main/java/com/ice/template/model/entity/KnowledgeEvent.java)

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | VARCHAR(64) | 主键 |
| `kb_id` | VARCHAR | 知识库 |
| `doc_id` | VARCHAR | 绑定文档 ID |
| `event_date` | DATE | 事件日期 |
| `time_granularity` | VARCHAR(10) | `exact` / `month` / `year` |
| `search_index` | TEXT | 浓缩关键词，专供向量化 |
| `entities` | JSONB | 参与主体数组 |
| `action` | TEXT | 事件核心动作（必填） |
| `source_type` | VARCHAR(20) | `official` / `news` / `social_media` |
| `confidence_score` | INT | 1-10 |
| `verification_status` | VARCHAR(20) | `verified` / `unverified` |
| `impact_inference` | TEXT | LLM 推演的商业影响 |
| `source_url` | TEXT | 来源链接 |

> 注：实际实体未采用 `short_title / result / long_description / related_entities` 设计，而是自包含事件（实体内嵌、`impact_inference` 充当影响字段、`source` 拆为 `source_type + source_url`）。

```

PromptTemplate ──prompt──▶ LanguageModel
LanguageModel ──response──▶ FormatValidator
FormatValidator ──output──▶ EventWriter
```

| 节点 | 关键配置 |
|------|----------|
| DocumentLoader | 注入 `document_id` |

| LanguageModel | `temperature=0.1`，`max_tokens=4096` |
| FormatValidator | `expected_format=json_object` |
| EventWriter | 注入 `kb_id` + `raw_text`，含 `embedding_model_config_id` |

**EventWriter 核心逻辑**：
- 校验 `action` 必填
- 模糊时间标准化：`year` → YYYY-01-01，`month` → YYYY-MM-01，`exact` → YYYY-MM-DD
- `confidence_score` 限制 1-10
- **RAG 双写**：`search_index` 优先向量化，空则降级 `action + impactInference` 拼接
- 向量化失败仅 log warn，不阻塞主流程
- 返回 `saved_count` / `skipped_count`

**`/event/search` 语义检索 + 降级**：
```java
// pgvector 余弦距离
SELECT parent_id, embedding <=> ? AS distance
FROM knowledge_chunk
WHERE kb_id = ? AND chunk_level = 'event' AND embedding IS NOT NULL AND is_delete = 0
ORDER BY embedding <=> ? LIMIT ?
// 向量化失败降级为 keyword LIKE（search_index OR action）
```

**`/event/graph-data` 关系图构建**：
- 事件节点 + 实体节点 + 实体-事件「参与」灰边
- 同一实体被多个事件引用 → 事件间按时间排序 → 红色半透明「关联」边（`rgba(239, 68, 68, 0.4)`）

### 3.6 关键设计点

1. **事件为中心、自包含**：实体内嵌 JSONB，避免频繁 join
2. **模糊时间标准化**：LLM 输出 `time_anchor` → `year/month/exact` 三档粒度
3. **可信度评估**：`source_type` 三档 + `confidence_score` 1-10 + `verification_status` 二元
4. **双写检索**：`knowledge_events` 全量 + `knowledge_chunk` 向量副本（`chunk_level='event'`，`parent_id` 反向引用）
5. **降级策略**：向量化失败仅告警，检索时向量失败再降级 LIKE
6. **关系图关联**：同实体多事件 → 时间排序 → 红色半透明边
7. **历史背景**：原 `KnowledgeGraphView.tsx` 已被 `EventView` 替换，已于 2026-07-11 清理删除

## 四、案例入库模块（Case）

### 4.1 模块定位

从文档中提取**多维特征矩阵的商业案例**，采用「症状→方案→结果」结构。设计核心是**防伪存真**——剥离 PR 废话，指出幸存者偏差，多维标签支撑混合检索。

### 4.2 数据模型

**表**: `knowledge_cases` | **实体**: [KnowledgeCase.java](file:///g:/ice-project/comfyUI-draw-flow/service/src/main/java/com/ice/template/model/entity/KnowledgeCase.java)

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | VARCHAR(64) | 主键 |
| `kb_id` | VARCHAR | 知识库 |
| `source_doc_id` | VARCHAR | 关联外部文档（回溯原文） |
| `case_data` | JSONB | 核心结构化 JSON（title/context/problem/solution/outcome/credibility/attachments） |
| `search_index` | TEXT | 浓缩关键词，专供向量化 |

**`case_data` 结构**：
```json
{
  "title": "...",
  "context": {
    "industry": [], "business_model": [], "company_stage": [], "target_audience": []
  },
  "problem": { "symptom_summary": "...", "root_causes": [] },
  "solution": { "strategy_type": [], "execution_steps": [] },
  "outcome": { "result_summary": "...", "key_success_factors": [] },
  "credibility": {
    "source_nature": "official_report | first_hand_review | third_party_analysis | PR_article",
    "authenticity_score": 1-10,
    "survivorship_bias_warning": "..."
  },
  "attachments": []
}
```

### 4.3 工作流节点链

**模板定义**: [KnowledgeSchemaMigration.java](file:///g:/ice-project/comfyUI-draw-flow/service/src/main/java/com/ice/template/config/KnowledgeSchemaMigration.java) `ensureCaseIngestionTemplateNew()`

```
DocumentLoader ──text──▶ LanguageModel
PromptTemplate ──prompt──▶ LanguageModel
LanguageModel ──response──▶ FormatValidator
FormatValidator ──output──▶ CaseWriter
```

| 节点 | 关键配置 |
|------|----------|
| DocumentLoader | 注入 `document_id` |
| PromptTemplate | 「极其挑剔的商业咨询顾问」角色，5 大原则：剥离 PR / 防伪存真 / 多维标签 / 附属物提取 / 症状而非病因 |
| LanguageModel | `temperature=0.1`，`max_tokens=4096` |
| FormatValidator | `expected_format=json_object` |
| CaseWriter | 注入 `kb_id`，含 `embedding_model_config_id` |

**PromptTemplate 核心约束**：
- `credibility.source_nature` 枚举 4 档，`authenticity_score` 范围（官方报告 8-10 / 一手复盘 6-8 / 三方分析 4-6 / PR 稿 1-3）
- `survivorship_bias_warning` 必填，指出隐性门槛（资金、人脉、时代红利）
- `context` 每字段必须为纯字符串数组

**CaseWriter 关键逻辑**：
- 校验 `title`（必填）、`context`（必填），缺失跳过
- **向量化全量入库**：向量文本含 `search_index + problem.symptom_summary + problem.root_causes + solution.strategy_type + solution.execution_steps + outcome.result_summary + outcome.key_success_factors`，确保检索时能命中方案和结果
- `metadata` 注入 `ctx_` 前缀的 context 标签（`ctx_industry` / `ctx_business_model` 等），支撑混合检索过滤
- `chunkLevel='case'`，`parent_id` 反向引用案例

**`/case/search` 三段式混合检索**：
```java
// 第一步：JSONB @> 硬性过滤（行业、商业模式、可信度）
whereClause.append(" AND case_data->'context'->'industry' @> ?");
// 第二步：在过滤结果中做向量相似度搜索
whereClause.append(" AND source_doc_id IN (SELECT parent_id FROM knowledge_chunk 
    WHERE kb_id = ? AND chunk_level = 'case' AND embedding IS NOT NULL 
    ORDER BY embedding <=> ? LIMIT ?)");
// 第三步：向量化失败降级为关键词 LIKE
```

**GIN 索引**（支撑 JSONB `@>` 毫秒级查询）：

### 7.4 案例向量化策略变更

**旧策略**：仅向量化 `search_index + problem`，严禁 `solution` 入库（防止"答案污染"检索）

**新策略**：全量向量化 `search_index + problem + solution + outcome`，原因：
- 事件和案例是"知识素材"，应被全面检索而非选择性检索
- 用户搜索时可能从问题角度、也可能从方案角度命中，限制向量化范围会丢失召回
- 数据量大不是问题——pgvector 本身支持大规模近似检索

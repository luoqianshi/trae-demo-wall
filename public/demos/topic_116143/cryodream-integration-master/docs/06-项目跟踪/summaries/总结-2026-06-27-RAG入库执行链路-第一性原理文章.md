## 2. 一篇文章从点击入库到完成经历了什么

### 2.1 前端发起分级 RAG 入库



前端传入的 `ingestionMode=deep` 表示强制走认知级入库，不再由 auto 规则判断普通/认知级。

## 3. 认知级入库的核心流水线

认知级入库的核心链路可以理解为：

```text
原始文章
  -> 文档状态 processing
  -> 选择聊天模型
  -> 全局元数据 LLM 提取
  -> 结构化 JSON 修复/校验
  -> 构建新版 metadata jsonb
  -> 智能父子 Chunk 分块
  -> 每个 child 抽取局部 entities/concepts/events
  -> 局部 events 与 chunk_text 对齐校验
  -> child 生成 embedding
  -> 写入 knowledge_chunk
  -> 更新 knowledge_document.completed
  -> 更新 knowledge_base.chunk_count
  -> 任务 completed
```

关键代码位置：

```text
KnowledgeBaseIngestionService.cognitiveIngestDocument()
GlobalMetadataExtractor.extract()
GlobalMetadataExtractor.build3DMetadata()
IntelligentSemanticChunker.chunk()
StructuredJsonOutputRepairer.parseOrRepairObject()
VectorStoreClient.saveChunks()
```

```json
{
  "1_Domain_Scope": {
    "domain": "思维模型/商业创新",

  },
  "2_Ontology_Routing": {
    "chunk_level": "child",
    "parent_local_id": "parent_0",
    "entities": [],
    "concepts": [],
    "events": []
  },
  "3_Epistemology_Tag": {
    "claim_type": "案例应用",
    "source": "document",
    "confidence": 0.9,
    "time_stamp": "2026-06-27",
    "chunk_summary": "..."
  }
}
```

关键规则：

```text
1. domain/theme 可从全局 metadata 或 LLM 分块结果继承。
2. entities/concepts/events 必须与当前 chunk_text 局部对齐。
3. child events 优先使用 LLM 局部抽取结果。
4. 如果局部 events 缺失，只从 globalEvents 中筛选当前 chunk_text 能支撑的事件。
5. 仍无证据时才使用规则推断。
6. 如果还是没有证据，events 保持 []，不再全量继承全文事件。
7. event_time 表示事件自身发生时间。
8. assertion_time 表示文本明确记录/发布/断言该事件的时间。
9. 3_Epistemology_Tag.time_stamp 表示 metadata 生成/入库时间，不替代 event_time。
```

## 11. 本次调试中暴露并修复的问题

### 11.1 JSON 输出被截断

问题：

```text
模型配置 max_tokens = 1000
全局元数据 JSON 输出超过 1000 tokens
模型响应中途截断
JSON 无法闭合
```

修复：

```text
全局元数据提取 max_tokens = 4000
结构化 JSON 修复器 max_tokens = 4000
认知级分块 max_tokens = 6000
```

### 11.2 LLM 输出不稳定

问题：

```text
LLM 可能输出 Markdown、解释、注释、尾逗号、不完整 JSON。
```

修复：

```text
新增 StructuredJsonOutputRepairer。
解析失败后把原始 prompt、原始输出、错误信息、期望 schema 发回模型修复。
最多重试 2 次。

```

### 11.5 局部实体不完整

问题：

```text
#9 Chunk 的 events.subject 已经包含“马斯克”，但 entities 只包含 SpaceX、猎鹰火箭、猛禽发动机，没有包含“马斯克/埃隆·马斯克”。
```

原因：

```text
1. 原提示词只要求抽取 entities，没有明确要求 events.subject / events.object 必须进入 entities。
2. 后处理只按实体规范名精确匹配 chunk_text，导致全局实体“埃隆·马斯克”无法匹配原文中的简称“马斯克”。
```

修复：

```text
1. prompt 增加约束：当前 child.text 中出现的人物、组织、产品、地点必须进入 entities。
2. prompt 增加约束：events.subject 必须进入 child.entities；events.object 若是人物、组织、产品、地点，也必须进入 child.entities。
3. prompt 增加约束：如“马斯克”对应全局实体“埃隆·马斯克”，entities 使用全局规范名称。
4. prompt 增加约束：全局实体只作为规范候选库，只有当前 child.text 明确出现名称、简称或别名时才允许补入，禁止无证据继承全文实体。
5. 后处理改为“全局元数据参考补全 + 当前 Chunk 证据校验”：只从 global entities 中补充能被 chunk_text 支撑的规范实体。
6. 后处理支持简称匹配，例如 chunk_text 出现“马斯克”时，可补入全局规范实体“埃隆·马斯克”；但不会因为全文有“特斯拉”就补到 SpaceX Chunk。
7. 当前 #9 旧数据已补入“埃隆·马斯克”。
```

### 11.6 Parent 块被误展示成普通 #0 Chunk

问题：

```text
数据库里有 Parent #0 和 Child #0。前端语义分块弹窗没有区分 chunk_level，导致用户看到两个 #0。
同时 parent 块曾经用所有 child 文本拼接作为 chunk_text，看起来像全文。
```

原因：

```text
1. parent 和 child 分别独立编号，二者都可以有 chunk_index=0。
2. parent 本意是主题聚合块，不参与向量检索，但前端 list 接口没有按 child 过滤。
3. 后端 parent.chunk_text 使用了 children 拼接文本，导致 parent 看起来像全文块。
```

修复：

```text
1. ChunkQueryRequest 增加 chunkLevel 过滤。
2. 前端语义分块弹窗默认请求 chunkLevel=child，只展示参与向量检索的 child 块。
3. 前端若展示 parent，标签显示 Parent #0；child 继续显示 #0/#1。
4. 后续新入库 parent.chunk_text 改为 parent_summary，parent.raw_text 保留聚合原文。
5. 当前旧 parent chunk_text 已替换为摘要文本。
```

## 12. 当前实现的优点与后续建议

### 12.1 当前优点

```text
1. 已经支持认知级 RAG 入库。
2. 支持父子 Chunk。
3. 支持新版 metadata jsonb。
4. 支持 chunk 级 events。
5. events 已区分 event_time 和 assertion_time。
6. 支持结构化 JSON 修复。
7. 支持失败态与成功态同步。
8. parent 作为上下文聚合，child 参与向量检索。
```

---

### 12.2 当前风险

```text
1. 长文档仍然可能遇到输入上下文窗口限制。
2. 当前全局 metadata 仍是一次性读取全文提取。
3. 对更长文章，最好改成分段提取 candidates 后合并。
4. parent 当前只有 1 个，说明模型把全文聚合成一个大 parent；后续可要求按主题拆多个 parent。
5. 部分 child concepts 为空，说明局部概念抽取还可以加强。
```

---

### 12.3 建议下一版优化

建议将全局元数据提取改为：

```text
文档预切片
  -> 每片提 entities/concepts/events candidates
  -> 后端去重合并
  -> LLM 做全局归并
  -> 生成最终 global_metadata
```

建议将父子 Chunk prompt 改为：

```text
每个 parent 只覆盖一个明确大主题。
一个 parent 下最多 3-5 个 child。
全文至少 2 个 parent，除非文章极短。
```

这样可以让后续 GraphRAG/事理图谱更稳定。

### 阶段一：破局 —— 逃离 Dify 的“黑盒知识库”
*   **起因**：你发现 Dify 原生的知识库虽然好用，但逻辑太死板（只能做基础切块和向量化），根本无法实现我们构想的“让大模型先通读、打上领域/置信度等 3D 标签”的高级玩法。
*   **第一次优化（解耦架构）**：我们决定把知识库从 Dify 里剥离出来。提出用 **Python (FastAPI) + Qdrant** 写一个独立的后端引擎。Dify 只做前端，通过 HTTP 请求调用我们的引擎。
*   **突破点**：实现了逻辑的完全掌控，数据资产真正掌握在自己手里。

### 阶段二：语言探索 —— 引入企业级 Java 基因
*   **起因**：你提出“能用 Java 吗？”
*   **第二次优化（技术栈平移）**：我为你展示了 **Java (Spring Boot) + LangChain4j** 的方案。证明了在解耦架构下，后端语言是自由的。Java 的强类型系统和高并发能力，让这个引擎具备了企业级落地的稳健性。
*   **突破点**：架构的普适性被验证，无论前端用什么，后端的 `/ingest` 和 `/search` 标准接口稳如泰山。

### 阶段三：灵魂拷问 —— 拒绝“杀鸡用牛刀”
*   **起因**：你敏锐地指出一个致命问题：“既然核心逻辑都在我自己的后端了，那我为了一个前端界面去私有化部署庞大的 Dify，岂不是太笨重了？”
*   **第三次优化（前端轻量化）**：我们果断放弃了私有化部署 Dify。转而寻找更轻量、专注工作流编排的工具。你相中了 UI 绝美的 **Langflow**，并务实地接受了用“浏览器翻译插件”来解决汉化问题，避免了陷入改前端源码的泥潭。
*   **突破点**：甩掉了沉重的历史包袱，系统变得极其轻盈。

### 阶段四：终极进化 —— 万物归一的“原生节点”
*   **起因**：你突发奇想：“能否直接在 Langflow 上做，创建对应的节点？”
*   **第四次优化（Serverless 化 / 节点化）**：这是最惊艳的一步！我们决定**彻底抛弃独立的 Java/Python 后端服务**。直接利用 Langflow 强大的 Custom Component（自定义组件）能力，把“V6.0 入库”和“V6.0 检索”的复杂逻辑，封装成两段 Python 脚本，变成 Langflow 画布上可以直接拖拽的两个节点！
*   **突破点**：架构达到了极致的收敛。现在你只需要维护一个 Langflow 服务和一个 Qdrant 数据库。所有的业务逻辑全部可视化、模块化。

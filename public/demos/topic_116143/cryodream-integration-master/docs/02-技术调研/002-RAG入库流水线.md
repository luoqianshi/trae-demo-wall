# RAG 入库流水线

> 已解析 Markdown 文档 → 分元数据 → 分块 → 向量化 → 落库的全流程详解。

## 一、整体架构

```text
┌─────────────────────────── 入口 ───────────────────────────┐
│  用户在知识库详情页选择文档 → 选择入库模式 → 提交            │
│  POST /ingestion/cognitive { documentId, ingestionMode }    │
└─────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────── 模式路由 ────────────────────────┐
│  KnowledgeBaseIngestionService                              │
│  ├── none      → 仅标记文档状态，不分块不入库               │
│  ├── standard  → standardIngestDocument()                   │
│  ├── deep      → graphIngestDocument() → cognitiveIngest()  │
│  └── auto      → resolveIngestionMode() 自动分流            │
│       ├── standard 信号 → standardIngestDocument()           │
│       └── deep 信号    → graphIngestDocument()               │
└─────────────────────────────────────────────────────────────┘
                              │
              ┌───────────────┴───────────────┐
              ▼                               ▼
┌─────── Standard RAG ───────┐  ┌─────── Deep / Cognitive RAG ───────┐
│  1. LLM 语义分块 (plain)    │  │  1. 全局元数据提取 (LLM)           │
│  2. 规则分块兜底             │  │  2. 智能语义分块 (LLM + 元数据)    │
│  3. 向量化                  │  │  3. 父子 Chunk 构建               │
│  4. 落库                    │  │  4. 向量化（仅子块）               │
│                             │  │  5. 落库                          │
└─────────────────────────────┘  └────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────── 存储 ────────────────────────────┐
│  knowledge_chunk (PGVector)                                 │
│  ├── content   → 向量化 + 召回用文本                         │
│  ├── chunk_text → Chunk 原文                                │
│  ├── metadata  → 三维背包 JSONB                             │
│  ├── events    → 事理图谱 JSONB                             │
│  ├── parent_id → 父子关联                                   │
│  └── embedding → PGVector 向量列                            │
└─────────────────────────────────────────────────────────────┘
```

## 二、三种入库模式详解

### 2.1 Standard（普通 RAG）

```text
文档 rawText
  │
  ▼
IntelligentSemanticChunker.chunkPlain()
  ├── 文本 < 500 字 → 单块直接返回
  └── 文本 >= 500 字 → LLM 语义分块
       │
       ▼ (LLM 失败)
  SemanticChunker.chunk() → 规则分块兜底
       │
       ▼
  每个 Chunk 附带轻量 metadata (source, file_type, ingestion_mode)
       │
       ▼
  Embedding 向量化 → vectorClient.saveChunks()
```

**特点**：
- 不提取全局元数据（无 Domain/Theme/Entities/Concepts/Events）
- 不构建父子 Chunk
- Chunk metadata 为轻量 baseMetadata
- 适合：API 文档、操作手册、日志、规章制度

### 2.2 Deep / Cognitive（认知级 RAG）

```text
文档 rawText
  │
  ▼
Step 1: GlobalMetadataExtractor.extract()
  → LLM 一次性阅读全文
  → 输出: { domain, theme, entities[], concepts[], events[], summary }
  │
  ▼
Step 2: GlobalMetadataExtractor.build3DMetadata()
  → 组装三维背包: { 1_Domain_Scope, 2_Ontology_Routing, 3_Epistemology_Tag }
  │
  ▼
Step 3: IntelligentSemanticChunker.chunk()
  → LLM 携带全局实体库做分块
  → 输出: parents[] → children[]
  → 每个 child 携带独立 entities, concepts, events, claim_type, confidence
  │
  ▼
Step 4: 父子 Chunk 构建
  → parent: chunkLevel=parent, chunkText=摘要, rawText=子块拼接
  → child:  chunkLevel=child,  chunkText=原文,  parentId=父块真实ID
  │
  ▼
Step 5: 向量化 (仅子块)
  → Embedding 模型 → float[] → vectorClient.vectorToString()
  → 父块只做上下文聚合，不参与向量召回
  │
  ▼
Step 6: vectorClient.saveChunks() 批量落库
```

**特点**：
- 全局元数据提取 → 下发给分块器，确保边界不被截断毒化
- 父子 Chunk：父块聚合上下文，子块精确召回
- 每个 Chunk 独立三维背包
- 适合：观点文章、行业分析、竞品研究、会议纪要

### 2.3 Auto（自动分流）

由 `resolveIngestionMode()` 根据文档内容自动选择 standard 或 deep：

```text
信号检测规则：
├── standard 信号: API, 接口, 说明书, 操作手册, 菜单, 日志, 规章, 制度
├── deep 信号:    观点, 认为, 吐槽, 竞品, 趋势, 会议纪要, 行业分析, 风险, 机会, 情绪, 战略, 决策
│
├── 短文 (< 1500 字) + 无 deep 信号 → standard
├── 含 standard 信号 → standard
├── 含 deep 信号    → deep
└── 正文 > 4000 字 → deep（默认长文走认知级）
```

## 三、元数据提取：三维背包 (3D Metadata)

每个 Chunk 最终携带一个 `metadata` JSONB 字段，由三层维度组成：

```json
{
  "1_Domain_Scope": {
    "domain": "自媒体/知识付费",
    "theme": "2026行业洗牌观察"
  },
  "2_Ontology_Routing": {
    "chunk_level": "child",
    "parent_local_id": "parent_0",
    "entities": [
      {"name": "张三", "description": "私域操盘手"}
    ],
    "concepts": [
      {"name": "流量成本", "description": "单粉获取成本的计算与趋势"}
    ],
    "events": [
      {
        "subject": "张三",
        "action": "宣称",
        "object": "新打法",
        "result": "月赚100万",
        "event_time": "",
        "assertion_time": "",
        "event_type": "观点论证",
        "causal_role": "evidence",
        "evidence": "张三在朋友圈晒单宣称靠新打法赚了100万"
      }
    ]
  },
  "3_Epistemology_Tag": {
    "time_stamp": "2026-06-30",
    "claim_type": "营销主张",
    "source": "document",
    "confidence": 0.3,
    "chunk_summary": "张三在朋友圈宣称靠新打法月赚100万"
  }
}
```

### 3.1 第一维：1_Domain_Scope（领域范围）

| 字段 | 来源 | 作用 |
|------|------|------|
| domain | GlobalMetadataExtractor LLM 输出 | 领域硬过滤（如"自媒体"vs"AI技术"） |
| theme | GlobalMetadataExtractor LLM 输出 | 主题聚类（如"2026行业洗牌"） |

**分配逻辑**：
- 全局提取一次 → 所有 Chunk 共享
- LLM 分块器如果输出了 domain/theme，优先使用分块级结果
- 否则 fallback 继承全局值
- 兜底：domain="未分类"，theme="未知主题"

### 3.2 第二维：2_Ontology_Routing（本体路由）

| 字段 | 来源 | 作用 |
|------|------|------|
| chunk_level | 分块器 | parent / child 路由策略 |
| parent_local_id | 分块器 | 同一批次内父块引用，落库时映射为真实 parentId |
| entities[] | LLM 分块器 + 全局对齐 | 人物/组织/地点/产品 → 精确路由 |
| concepts[] | LLM 分块器 + 全局对齐 | 专业术语/核心概念 → 概念检索 |
| events[] | LLM 分块器 + 全局匹配 + 规则推断 | 事理图谱骨架 → 因果链追踪 |

**entities 对齐逻辑**（核心，防语义坍塌）：

```text
1. LLM 为每个 child 抽取局部 entities
2. 若局部 entities 为空 → 从全局 entities 中按 chunkText 文本匹配补入
3. 全局匹配规则：
   - 实体名出现在 chunkText 中 → 匹配
   - 别名匹配（如 "马斯克" → "埃隆·马斯克"，按 · 拆分姓/名）
   - 文本归一化后包含检测
4. events 的 subject/object 中的实体也必须进入 entities（enrichEntitiesFromEvents）
```

**events 解析逻辑**（三级降级）：

```text
1. LLM 为每个 child 抽取局部 events → 用 chunkText 做 evidence 验证
2. 若局部 events 为空 → 从全局 events 中按 chunkText 匹配（score >= 2 个字段命中）
3. 若全局匹配也为空 → 规则推断 inferEventsFromChunkText()
   - 扫描动作词（提出/应用/导致/解决/重构...）
   - 用第一个 entity 作 subject，第一个 concept 作 object
   - 自动推断 event_type 和 causal_role
```

**events 字段详解**：

```json
{
  "subject":       "主语（人/组织/系统）",
  "action":        "动作（提出/应用/导致/解决...）",
  "object":        "对象（概念/人/技术/产品）",
  "result":        "结果或影响",
  "event_time":    "事件自身发生时间（文本未明确则留空，绝不用发布时间代替）",
  "assertion_time":"文本发布/记录/断言该信息的时间",
  "event_type":    "事件类型（因果影响/观点论证/商业行为/事件/unknown）",
  "causal_role":   "事理角色（cause/effect/evidence/background/unknown）",
  "evidence":      "支撑该事件的原文短句（<= 120字）"
}
```

### 3.3 第三维：3_Epistemology_Tag（认识论标签）

| 字段 | 来源 | 作用 |
|------|------|------|
| time_stamp | 当前日期 | 防御概念漂移（不同时期"私域"含义不同） |
| claim_type | LLM 分块器 | 事实陈述 / 营销主张 / 观点预测 / 情绪发泄 |
| source | LLM 分块器 / 固定 "document" | 信息来源标记 |
| confidence | LLM 分块器 / 默认 0.8 | 置信度 0.0-1.0，决定输出权重 |
| chunk_summary | LLM 分块器 / 规则生成 | 子块摘要，用于上下文补充 |

**claim_type 判定逻辑**：
- LLM 在分块时直接为每个 child 标注
- 默认值："事实陈述"
- 典型值：事实陈述、观点预测、营销主张、情绪发泄、段落聚合（父块专用）

**confidence 典型场景**：
- 0.9-1.0：客观规律、行业公认、数据支撑
- 0.7-0.8：事实陈述、可验证信息
- 0.3-0.5：营销主张、情绪化观点、未经证实的爆料

## 四、智能语义分块核心逻辑

### 4.1 分块流程图

```text
原文 (rawText)
  │
  ├── 文本 < 500 字 ────────────────────────────→ 单块返回（附全局元数据）
  │
  └── 文本 >= 500 字
       │
       ▼
  构建 Prompt（注入全文 + 全局实体候选库）
       │
       ▼
  LLM 返回 JSON
       │
       ├── JSON 解析成功 → structuredJsonOutputRepairer
       │     │
       │     ├── 返回 parents[] + children[] 结构 → 正常路径
       │     │
       │     ├── 返回扁平 chunks[] 结构 → 降级：包装为单父块 + 子块
       │     │
       │     └── 返回结构异常 → fallback 规则分块
       │
       └── JSON 解析失败
             │
             ▼
       structuredJsonOutputRepairer.parseOrRepairObject()
             │
             ├── 首次解析成功 → 返回
             │
             └── 首次失败 → 最多 2 轮 LLM 修复
                   │
                   ├── 修复成功 → 返回
                   └── 修复失败 → fallback 规则分块
```

### 4.2 LLM 分块 Prompt 核心约束

```
1. domain/theme 必须根据全文填写，不能写"未知"
2. 至少拆成 2 个 parent，每个聚合一个明确主题
3. 每个 child.text 必须从原文复制，禁止改写
4. 每个 child 必须抽取 entities 和 concepts
5. 可参考全局实体候选库做名称规范化（如"马斯克"→"埃隆·马斯克"）
6. 禁止无证据继承全文实体，只有 chunkText 中出现才允许补入
7. events 的 subject 必须进入当前 child.entities
8. 每个 event 必须能被当前 child.text 直接支撑
9. chunk_summary 必须概括该子块内容
```

### 4.3 规则分块兜底

当 LLM 不可用或全部重试失败时：

```text
1. 按 \n\n+ 分段
2. 每段 > 600 字 → 按句子边界再拆
3. 当前累积 > 600 字 → 保存当前块
4. 继承全局 domain/theme（若有）
5. 从全局实体/概念库按文本匹配分配 entities/concepts
6. 不做父子 Chunk，全部 child 级别
```

### 4.4 覆盖率校验

分块完成后自动校验：

```text
子块文本拼接 → 去空白 → 与原文去空白对比
coverage = mergedClean.length / originalClean.length
coverage < 80% → WARN 日志
coverage >= 80% → INFO 日志
```

## 五、全局元数据提取 Prompt

```text
请阅读以下文档内容，并提取全局元数据信息。

文档内容：
{{DOCUMENT_CONTENT}}

输出格式：
{
  "domain": "领域范围（自媒体/知识付费/AI技术/投资理财/医疗健康）",
  "theme": "核心主题（2026行业洗牌观察/人工智能发展趋势）",
  "entities": [最多 12 个，{"name":"实体名称","description":"实体描述"}],
  "concepts": [最多 12 个，{"name":"概念名称","description":"概念定义"}],
  "events":   [最多 8 个，{subject/action/object/result/event_time/assertion_time/event_type/causal_role/evidence}],
  "summary":  "文档摘要（不超过100字）"
}

关键约束：
- event_time 是事件自身发生时间，assertion_time 是信息发布时间，不能混用
- 无明确时间时 event_time 必须留空
- causal_role: cause/effect/evidence/background/unknown
- evidence 必须是原文短句
- 有人物/组织行动产生结果时，events 不能为空
```

**LLM 参数**：temperature=0.1，max_tokens=4000

## 六、父子 Chunk 落库映射

```text
分块器输出:
  parent_0: { parentLocalId: "parent_0", chunkLevel: "parent", ... }
  child_0:  { parentLocalId: "parent_0", chunkLevel: "child",  ... }
  child_1:  { parentLocalId: "parent_0", chunkLevel: "child",  ... }
  parent_1: { parentLocalId: "parent_1", chunkLevel: "parent", ... }
  child_2:  { parentLocalId: "parent_1", chunkLevel: "child",  ... }

落库映射:
  1. 先存所有 parent → 得到真实 UUID
  2. 建立 parentIdMap: { "parent_0" → "uuid-xxx", "parent_1" → "uuid-yyy" }
  3. 再存所有 child → parentId = parentIdMap.get(parentLocalId)
```

**父块 vs 子块**：

| 维度 | 父块 (parent) | 子块 (child) |
|------|--------------|-------------|
| chunkText | 摘要（500字内） | 原文 |
| rawText | 子块原文拼接 | 子块原文 |
| chunkLevel | parent | child |
| parentId | null | 父块真实 UUID |
| entities | [] (不独立抽取) | LLM 抽取 + 全局对齐 |
| concepts | [] (不独立抽取) | LLM 抽取 + 全局对齐 |
| events | 子块 events 聚合 | LLM 抽取 + 全局匹配 |
| 向量化 | 不做 | 做 |
| claim_type | 段落聚合 | 事实陈述/营销主张/... |
| confidence | 1.0 | LLM 标注 / 0.8 |

## 七、向量化策略

### 7.1 模型选择优先级

```text
1. 知识库配置的 embeddingModelId → knowledgeBase.embeddingModelId
2. 工作流模板配置的 embedding_model_id
3. 数据库中已启用的 embedding 类型模型（取第一个）
4. 以上均空 → 跳过向量化，仅存文本
```

### 7.2 向量化内容

```text
Standard 模式:
  所有 Chunk → embeddingClient.embed(chunk.chunkText)

Deep 模式:
  仅 child Chunk → embeddingClient.embed(chunk.chunkText)
  parent Chunk → 不向量化（仅上下文聚合存储）
```

### 7.3 向量存储

```text
float[] → vectorClient.vectorToString() → 存入 knowledge_chunk.embedding (PGVector vector 列)
content 字段 = chunkText（用于向量召回的文本）
```

## 八、JSON 修复机制

LLM 输出的 JSON 经常不合法，系统内置 `StructuredJsonOutputRepairer`：

```text
1. 首次解析
   ├── 成功 → 返回
   └── 失败 → 进入修复流程

2. 修复流程（最多 2 轮）
   构建 repairPrompt:
     - 任务名称
     - 期望 JSON Schema
     - 原始 Prompt
     - 上次 LLM 输出
     - 解析错误信息
   → LLM 重新输出修复后的 JSON
   → 解析
     ├── 成功 → 返回
     └── 失败 → 继续下一轮

3. 全部失败 → 抛出 RuntimeException
```

**JSON 提取逻辑**（三层降级）：
1. ` ```json ... ``` ` 代码块
2. ` ``` ... ``` ` 代码块（以 `{` 开头）
3. 找第一个 `{` 和配对的 `}`（考虑字符串内嵌套）

**JSON 清洗**：
- 移除 `//` 和 `/* */` 注释
- 移除尾逗号（`,}` → `}`，`,]` → `]`）

## 九、模型配置解析链路

入库流程中需要两类模型：聊天模型（LLM）和嵌入模型（Embedding）。

### 9.1 聊天模型（用于元数据提取和语义分块）

```text
解析优先级:
1. 运行时参数传入的 modelConfigId
2. resolveFallbackLlmModelConfigId()
   → 查数据库中已启用 + 有 baseUrl 的 LLM/chat 模型
   → 优先有 apiKey 的 > 优先 chat 类型 > 优先最新创建
3. 工作流模板中的 model_config_id 字段
4. 以上均空 → 抛异常，提示用户配置模型
```

### 9.2 嵌入模型（用于向量化）

```text
解析优先级:
1. 知识库配置的 embeddingModelId
2. 工作流模板中的 embedding_model_id 字段
3. 数据库中已启用的 embedding 类型模型（取第一个）
4. 以上均空 → 跳过向量化
```

## 十、文档状态流转

```text
parsed (文档解析完成，等待入库)
  │
  ▼ 用户选择入库模式并提交
processing (入库中)
  │
  ├── 成功 → completed
  └── 失败 → failed (errorMessage 记录失败原因)

状态字段:
  status:                parsed / processing / completed / failed
  ingestionMode:         none / auto / standard / deep
  resolvedIngestionMode: standard / deep（实际执行的模式）
  chunkCount:            生成的子块数量
  globalMetadata:        全局元数据 JSON（deep 模式生成）
```

## 十一、关键防御机制

| 风险 | 防御 | 实现 |
|------|------|------|
| 语义边界截断 | 全局元数据下发给分块器 | GlobalMetadataExtractor → IntelligentSemanticChunker |
| LLM JSON 不合法 | 自动修复 | StructuredJsonOutputRepairer（最多 2 轮 LLM 修复） |
| LLM 分块失败 | 规则分块兜底 | IntelligentSemanticChunker.fallbackRuleBasedChunk() |
| 分块覆盖率不足 | 自动校验 + WARN | validateChunks() 检查拼接覆盖率 >= 80% |
| 语义坍塌 | 实体/概念用 Name+Desc 拼接 | 向量化时使用完整描述文本 |
| 全局实体未传播 | 分块时注入全局候选库 | buildGlobalEntitiesText() → CHUNKING_PROMPT |
| 别名不一致 | 自动别名构建 | "埃隆·马斯克" → 别名 "马斯克" |
| 父块 ID 映射 | 先存父块再存子块 | parentIdMap: localId → real UUID |

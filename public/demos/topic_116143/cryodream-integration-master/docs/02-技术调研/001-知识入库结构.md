# 知识入库结构 V2

> 基于实际实现梳理，反映当前系统真实架构与入库流程。

## 一、系统全景

```text
┌─────────────────────────────── 前端入口 ───────────────────────────────┐
│  上传文档弹窗 (DocumentUploadDrawer)                                    │
│  ├── 文本输入 (text)         → 同步 POST /ingestion/document           │
│  ├── 文件上传 (file)         → 同步 POST /ingestion/upload             │
│  ├── 视频/音频 (video)       → 异步 POST /ingestion/upload/async       │
│  ├── 网页链接 (url)          → 同步 POST /ingestion/url                │
│  └── 抖音入库 (douyin)       → 异步 POST /ingestion/douyin/async       │
│                                                                        │
│  知识库详情页 → 手动入库按钮 → POST /ingestion/cognitive (异步)         │
│  任务中心 /tasks → 3 秒轮询运行中任务 → 完成后展示结果/错误             │
└────────────────────────────────────────────────────────────────────────┘
                                    │
                                    ▼
┌─────────────────────────────── 后端编排 ───────────────────────────────┐
│  KnowledgeBaseIngestionService                                         │
│  ├── 入库模式: none / auto / standard / deep                          │
│  ├── 图驱动优先，内联解析兜底                                          │
│  └── 异步任务: 创建 Task 记录 → CompletableFuture 后台执行 → 状态回写  │
│                                                                        │
│  FlowGraphExecutor (图执行器)                                           │
│  ├── 加载 WorkflowTemplate → 解析 FlowGraphDTO                        │
│  ├── 拓扑排序节点 → 按序执行 FlowNodeExecutor                         │
│  ├── 节点间通过 FlowExecutionContext 传递变量                          │
│  └── 失败节点记录为 FAILED step，不中断整图                             │
│                                                                        │
│  IngestTaskLogger (任务日志，独立事务)                                  │
│  ├── start → finish (completed / failed)                               │
│  └── updateProgress (status, progress, errorMessage)                   │
└────────────────────────────────────────────────────────────────────────┘
                                    │
                                    ▼
┌─────────────────────────────── 数据落库 ───────────────────────────────┐
│  knowledge_base → knowledge_document → knowledge_chunk → PGVector      │
└────────────────────────────────────────────────────────────────────────┘
```

## 二、工作流模板总览

| 模板 ID | 用途 | 节点链路 | 触发方式 |
|---------|------|----------|----------|
| `tpl-standard-rag-ingestion` | 普通 RAG 入库 | DocumentLoader → IntelligentSemanticChunker → KnowledgeBaseWriter | 手动入库 standard 模式 |
| `tpl-tiered-rag-ingestion` | 分级 RAG 入库（自动分流） | LLM 分流 → standard 或 deep 路径 | 手动入库 auto 模式 |
| `tpl-cognitive-rag-ingestion` | 认知级 RAG 入库 | DocumentLoader → GlobalMetadataExtractor → IntelligentSemanticChunker → KnowledgeBaseWriter | 手动入库 deep 模式 |
| `tpl-file-parse-ingestion` | 文件解析入库 | FileLoader → 存入知识库 | 文件上传（非视频） |
| `tpl-video-parse-ingestion` | 视频转录入库 | VideoAudioTranscriber → 存入知识库 | 视频/音频上传 |
| `tpl-douyin-parse-ingestion` | 抖音链接入库 | DouyinVideoDownloader → VideoAudioTranscriber → SaveToKnowledgeBase | 抖音链接解析 |
| `tpl-web-parse-ingestion` | 网页解析入库 | UrlInput → Jsoup → Jina → Scrapling（逐级降级） → SaveToKnowledgeBase | 网页链接解析 |

## 三、入库源与流程详解

### 3.1 文本输入 → 同步

```text
用户输入标题+内容 → POST /ingestion/document
  → KnowledgeBaseIngestionService.ingestDocument()
  → 创建 knowledge_document (status=parsed)
  → 返回 documentId
```

### 3.2 文件上传 → 同步

```text
用户选择 .txt/.md/.pdf 文件 → POST /ingestion/upload
  → 保存文件到 ./uploads/knowledge/{kbId}/
  → 图驱动: FileLoader → SaveToKnowledgeBase
  → 兜底: DocumentParser 解析 → 内联存文档
  → 返回 documentId
```

### 3.3 视频/音频上传 → 异步

```text
用户选择视频/音频文件 → POST /ingestion/upload/async
  → 上传文件暂存到 ./data/async-uploads/
  → 创建 Task (status=pending, progress=0)
  → 立即返回 Task 对象，弹窗关闭
  → 后台 CompletableFuture:
      1. 标记 running
      2. 保存文件到知识库目录
      3. 图驱动: VideoAudioTranscriber → SaveToKnowledgeBase
         - FFmpeg 抽音频 → Whisper 转录 → LLM 结构化 → 存文档
      4. 兜底: DocumentParser 解析 → 内联存文档
      5. 完成或失败 → 更新 Task 状态
      6. 清理暂存文件
```

### 3.4 网页链接 → 同步

```text
用户输入 URL → POST /ingestion/url
  → 图驱动: UrlInput → Jsoup → Jina → Scrapling 逐级降级
  → 兜底: 内联网页抓取
  → 返回 documentId
```

### 3.5 抖音链接 → 异步

```text
用户粘贴抖音分享文本 → POST /ingestion/douyin/async
  → 创建 Task (status=pending, progress=0)
  → 立即返回 Task 对象，弹窗关闭
  → 后台 CompletableFuture:
      1. 标记 running
      2. 提取 URL（清理反引号/中文标点/括号包裹）
      3. 解析抖音短链 → 获取视频详情（携带 Cookie）
      4. 图驱动: DouyinVideoDownloader → VideoAudioTranscriber → SaveToKnowledgeBase
         - 下载视频到 ./data/knowledge-media/kb/{kbId}/douyin/{date}/{awemeId}/source.mp4
         - FFmpeg 抽音频 → Whisper 转录 → LLM 结构化 → 存文档
      5. 完成或失败 → 更新 Task 状态
```

### 3.6 手动入库 → 异步

```text
知识库详情页 → 选择入库模式 → POST /ingestion/cognitive
  → 创建 Task (status=pending)
  → 后台执行:
      - none: 仅标记文档状态
      - standard: tpl-standard-rag-ingestion
      - deep: tpl-cognitive-rag-ingestion
      - auto: tpl-tiered-rag-ingestion → LLM 分流
```

## 四、核心节点执行器

| 节点类型 | 执行器 | 输入 | 输出 | 说明 |

| `SemanticChunker` | SemanticChunkerNodeExecutor | text | chunks | 简单语义分块 |

### 父子 Chunk 落库约定

```text
parent chunk:
  chunk_level = parent
  parent_id = null
  chunk_text = 父块摘要或聚合文本

child chunk:
  chunk_level = child
  parent_id = 对应 parent chunk 的真实 ID
  chunk_text = 子块原文
```

```text

  │

  │
  ▼

  │
  ▼ 后台 CompletableFuture

  │
  ├─ DouyinApiClient 解析短链
  │   ├── HTTP 302 跟随获取真实 URL
  │   └── 提取 aweme_id
  │
  ├─ DouyinApiClient.getVideoDetail()
  │   ├── 携带 Cookie 管理中的抖音 Cookie
  │   └── 获取视频下载地址和元数据
  │
  ├─ MediaStorageService.saveDouyinVideo()
  │   ├── 确保目录存在
  │   └── HTTP 下载视频到 ./data/knowledge-media/kb/{kbId}/douyin/...
  │
  ├─ 图驱动: tpl-douyin-parse-ingestion
  │   ├── DouyinVideoDownloader → file_path, title, metadata
  │   ├── VideoAudioTranscriber → text, srt
  │   │   ├── FFmpeg 抽音频
  │   │   ├── Whisper 转录
  │   │   └── LLM 结构化 Markdown
  │   └── SaveToKnowledgeBase → documentId
  │
```

## 十、异步任务体系

### 10.1 任务类型

| type | 说明 | 触发方式 |
|------|------|----------|
| `upload_parse_ingest` | 文件上传解析入库 | 视频/音频异步上传 |
| `douyin_ingest` | 抖音链接入库 | 抖音异步解析 |
| `video_ingest` | 视频转录同步入库 | 视频同步上传（内建 Task） |
| `file_ingest` | 文件同步入库 | 文件同步上传（内建 Task） |
| `tiered_ingest` | 分级 RAG 入库 | 手动入库 |

### 10.2 任务状态流转

```text
pending → running → completed
                  → failed
```

### 10.3 IngestTaskLogger

- `start()` / `finish()` / `markRunning()` / `updateProgress()` 均使用 `REQUIRES_NEW` 独立事务
- 写入失败不阻断入库主流程
- `finish()` 自动设置 progress: completed=100, failed=0

### 10.4 前端轮询

- `/tasks` 页面每 3 秒轮询运行中任务
- 任务完成后展示结果（documentId / 错误信息）
- 全局 TaskIndicator 组件显示运行中任务数量

## 十一、错误处理与防御

| 问题 | 防御机制 |
|------|----------|
| 抖音分享文本含反引号/括号 | `DouyinLinkUtils.trimUrl()` 清理包裹字符 |
| 工作流节点失败被吞掉 | `findFailedStepMessage()` 检测 FAILED step 并返回具体节点错误 |
| 媒体存储目录不存在 | `@PostConstruct` + 下载前 `ensureRootDirectory()` |
| MultipartFile 临时文件被清理 | 异步上传先暂存到 `data/async-uploads/`，后台任务用 `StagedMultipartFile` |
| 图驱动不可用 | 内联解析兜底（DocumentParser） |
| LLM 结构化 JSON 解析失败 | `StructuredJsonOutputRepairer` 重试修复 |
| 空 metadata 结构 | 分块器兼容新版 metadata；fallback 继承 domain/theme |
| 语义坍塌 | 实体和概念以 Name+Desc 拼接后向量化 |
| 幻觉复利 | 原始快照 + 溯源锚点 |

## 十二、入库模式详解

### none（不入库）

- 仅解析保存原文，不进行分块和向量化
- 文档 status = parsed
- 后续可在详情页随时手动入库

### standard（普通 RAG）

- 工作流：`tpl-standard-rag-ingestion`
- DocumentLoader → IntelligentSemanticChunker → KnowledgeBaseWriter
- 轻量语义分块，无全局元数据提取

### deep（认知级 RAG）

- 工作流：`tpl-cognitive-rag-ingestion`
- DocumentLoader → GlobalMetadataExtractor → IntelligentSemanticChunker → KnowledgeBaseWriter
- 全局元数据提取 + 父子 Chunk + 新版 metadata jsonb + events

### auto（自动分流）

- 工作流：`tpl-tiered-rag-ingestion`
- LLM 分析文档特征，选择 standard 或 deep 路径
- 分流信号：
  - standard 信号：API、接口、说明书、操作手册、菜单、日志
  - deep 信号：观点、吐槽、竞品、趋势、行业分析、风险、决策

## 十三、与 V1 的主要变化

| 维度 | V1 | V2 |
|------|----|----|
| 视频上传 | 同步等待（弹窗阻塞） | 异步任务（弹窗立即关闭） |
| 抖音入库 | 不存在 | 异步任务，完整链路（短链解析→下载→转录→入库） |
| 网页解析 | 无降级 | 三级降级（Jsoup→Jina→Scrapling） |
| 文件解析 | 仅内联 | 图驱动优先 + 内联兜底 |
| 媒体存储 | 无 | 本地媒体库 `./data/knowledge-media/` |
| Cookie 管理 | 在模型设置中 | 独立路由 `/cookie-settings` |
| 错误提示 | 笼统"未生成文档" | 具体节点名+错误原因 |
| URL 清洗 | 不清理 | 清理反引号/中文标点/括号 |
| 异步上传文件安全 | N/A | 暂存到本地 + StagedMultipartFile |
| 工作流模板 | 3 个 | 7 个（新增文件/视频/抖音/网页解析模板） |
| 节点执行器 | 6 个 | 27 个（含抖音下载、视频转录、网页抓取等） |

🧠 V6.0 认知级 RAG 架构设计白皮书

一、 架构核心哲学
1. 逻辑上分层，物理上扁平：彻底放弃图数据库中的深层嵌套树状结构，所有数据以"文本碎片（Chunk）"形式平铺在向量数据库中，依靠"全息元数据"实现高维降维打击。
2. 分类学与本体论分离：将主观叙事（Theme/主题）与客观字典（Concept/概念）严格切分，确保知识库的无限扩展性。
3. 元情报思维：不轻易丢弃低置信度数据（如吹牛、营销话术），将其视为反映市场情绪的有效信号。
  
二、 数据模型：全息元数据背包 (3D Metadata)
每一个存入数据库的 Chunk，都必须背着这个"三维背包"。这是整个架构的灵魂。

{
  "chunk_id": "doc123_chunk2",
  "chunk_text": "原始文本内容...",
  "metadata": {
    "1_Domain_Scope": {
      "domain": "自媒体/知识付费", 
      "theme": "2026行业洗牌观察" 
    },
    "2_Ontology_Routing": {
      "event_id": "event_zhangsan_fail_05",
      "entities": [{"name": "张三", "desc": "私域操盘手"}],

三、 历史致命风险与系统级防御机制
在推演过程中，我们排雷了 8 个足以摧毁系统的致命风险，并在架构中植入了防御机制：

致命风险
灾难场景
V6.0 防御机制
1. 层次爆炸
图谱太深，检索路径长，Token 爆炸。
物理扁平化：用元数据 Tag 代替物理层级。
2. 罗生门冲突
不同人对同一事件说法不一，AI 精神分裂。
认识论标签：引入 claim_type 和 confidence，区分事实与主张。
3. 分类学混淆
标签乱作一团，无法区分"客观名词"和"主观合集"。
维度隔离：强制拆分 Theme（文件夹）和 Concept（字典）。
4. 语义坍塌
孤立短标签（如"苹果"、"打法"）在向量空间中无法区分。
微型注释：实体和概念必须以 Name + Desc 拼接后向量化。
5. 交互摩擦
面对模糊提问，AI 疯狂反问，像审讯室，用户弃用。
隐式重构：LLM 后台自动补全条件，仅在致命缺失时触发单点反问。
6. 概念漂移
2024年的"私域"和2026年的"私域"被缝合在一起。
时间感知：元数据强制带时间戳，检索时默认限制时间窗口。
7. 边界毒化
机械按字数切分，导致因果关系断裂，LLM 提取出错误标签。
文档级继承：先全局提取元数据，再下发给语义分块（Semantic Chunking）。
8. 幻觉复利
LLM 错误提取被固化，污染整个知识网络。
原始快照+溯源锚点：保留不被篡改的原文，生成报告必须带引用链接。

四、 实战案例：一篇拆解文章的完整生命周期

为了让你清晰看到数据是如何流动的，我们以一篇公众号文章为例。

阶段 1：文档入库 (Ingestion)
输入：一篇名为《深扒张三：上个月号称赚100万，实则亏损，私域打法已死？》的文章。

- Step 1.1 全局阅读与提取：
工作流中的"全局 LLM"阅读全文，提取出：
  - Theme: "2026行业洗牌观察"
  - Entities: [{"name": "张三", "desc": "卖课操盘手"}]
  - Concepts: [{"name": "私域打法", "desc": "基于微信生态的转化策略"}]
- Step 1.2 语义分块 (Semantic Chunking)：
系统按段落逻辑切分文章。
  - Chunk 1："张三在朋友圈晒单，宣称靠新打法赚了 100 万。"
  - Chunk 2："但据前员工爆料，投流成本极高，实际亏损 50 万。"
- Step 1.3 局部元数据挂载与入库：
  - Chunk 1 挂载：claim_type: 营销主张, confidence: 0.3。
  - Chunk 2 挂载：claim_type: 事实陈述, confidence: 0.8。
  - 将 Name+Desc 拼接后进行 Embedding，存入向量数据库，并保留原文快照。
    
阶段 2：动态检索 (Retrieval)
输入：你随手在对话框输入："最近张三那个私域的事儿，到底靠谱吗？"

- Step 2.1 隐式重构 (Query Rewriter)：
后台 LLM 介入，将你的废话翻译为标准 JSON 查询：
{"time": "last_3_months", "entities": ["张三"], "concepts": ["私域打法"]}
- Step 2.2 混合检索 (Hybrid Search)：
  - 预过滤：数据库瞬间屏蔽掉非张三、非近期的几十万条数据。
  - 向量召回：在剩下的数据中，精准捞出 Chunk 1 和 Chunk 2。
    
阶段 3：研判生成 (Generation)
输入：捞出的 Chunk 1（置信度 0.3）和 Chunk 2（置信度 0.8），以及"终极合成 Prompt"。

- Step 3.1 情报分析师 LLM 输出：
> 💡 一句话核心研判
> 张三近期的私域盈利宣传不靠谱，实际处于亏损状态。
>
> 🏗️ 底层逻辑与概念
> 涉及概念【私域打法】：基于微信生态的转化策略。目前该打法的核心瓶颈在于前端投流成本的急剧上升。
>
> 📊 核心数据与事实（高置信度）
> *   [前员工爆料 | 置信度 0.8]：张三实际亏损 50 万，投流成本极高，资金链紧张。 [引用: Chunk_2]
>
> 📢 市场叙事与情绪（低置信度）
> *   [张三朋友圈 | 置信度 0.3]：张三对外宣称赚了 100 万。这种高调的营销主张，通常是为了掩盖现金流危机，并试图通过收割新手来回血。 [引用: Chunk_1]
>
> 🎯 综合行动建议
> 警惕近期张三可能推出的高价课程，其底层商业模型已无法跑通，切勿盲目入场。

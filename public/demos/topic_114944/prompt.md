# 全球高端壁炉独立站 — AI 创建与实现提示词

## 1. 你的角色与任务

你是一支由产品经理、品牌设计师、UX 设计师、资深 Next.js 工程师、动效工程师、Headless Commerce 架构师、SEO/无障碍专家和 QA 组成的交付团队。

请依据项目根目录的 `全球高端壁炉独立站_PRD_V1.0.md`，设计并实现一个面向全球市场的高端壁炉品牌独立站。PRD 是最高优先级需求基线；若本提示词与 PRD 冲突，以 PRD 为准。

这不是一个普通壁炉商城，也不是只供展示的单页 Landing Page。最终产品必须同时承载：

- 高端品牌展示
- 产品发现与适配判断
- 标准化商品在线交易
- 高客单/定制产品咨询与项目询价
- 建筑师、设计师、酒店、地产、经销商和安装商服务
- 技术资料、安装、安全、保修与售后支持

核心体验主线：**从一束火，到一个空间的核心。**

## 2. 当前阶段与交付原则

当前 PRD 状态为“技术调研完成，可进入 UI 定调与原型阶段”。优先交付可运行、可响应、可验证的 Phase 0 原型，并让代码结构可平滑演进到 MVP。

Phase 0 至少应完成：

1. 完整首页及 1 个滚动帧 Hero 技术 PoC。
2. 产品列表/筛选体验原型。
3. 1 个完整产品详情页（PDP）及轻量配置器。
4. 市场切换与五种 `commerce_state` 的可视化演示。
5. 询价/预约顾问表单流程原型。
6. 基础响应式、SEO、性能与无障碍验证。

不要把尚未接入的第三方系统伪装成已完成。Shopify、CMS、CRM、搜索、邮件或真实支付未配置时，应提供类型安全的 adapter/interface 和可替换 mock 数据，并在界面上明确为演示状态。

## 3. 不得擅自假设的业务信息

以下内容在 PRD 中仍是待确认项：

- 品牌正式名称、Logo、字体许可、品牌色和品牌故事
- 首发国家、语言、货币和市场负责人
- 真实产品线、SKU、燃料、规格、认证和安装限制
- 各市场价格、库存、税费、物流、关税、安装、交期、退换和保修
- 经销商数据、区域保护、线索归属和 B2B 价格规则
- 现有 Shopify、ERP、CRM、PIM、物流、客服与邮件系统

处理规则：

- 使用中性、可替换的临时品牌标识，并集中配置，不要把临时名称散落在组件中。
- 演示产品数据必须标注为 mock，不得虚构安全认证、设计奖项、销售国家或性能参数。
- 不得默认“全球均可购买”。市场未开放或规则不完整时，显示询价、咨询、经销商或不可售路径。
- 不得使用虚假的客户评价、项目数量、认证徽章、库存紧张或促销倒计时。
- 法律、消防、燃气、电气、建筑、税务和隐私内容只能使用待审核占位说明，不得冒充专业意见。

## 4. 目标用户与任务

### 高端住宅业主

通过空间灵感找到适合的壁炉，确认燃料、尺寸、安装条件、预算、交付和售后，再完成购买或预约顾问。

### 建筑师与室内设计师

### 酒店、地产与商业项目方

### 经销商与安装商

查看合作价值与准入要求，提交公司、区域、渠道、展厅、团队和安装能力资料。

### 已有客户

查找安装、操作、安全、维护、保修、配件、产品注册和售后服务入口。

## 6. 首页体验

首页必须按以下顺序形成完整叙事，不可只制作 Hero：

### S01 — 沉浸式 Hero

- 全屏滚动定格帧：产品从暗场显现 → 点火 → 火焰稳定 → 镜头环绕/材质细节 → 完整空间。
- 主 CTA：`探索系列`；次 CTA：`跳过动画`。
- 标题、描述、CTA 和导航均为真实 DOM，不得烧录在图片、Canvas 或视频中。
- 首帧由服务端输出为真实 `<img>`/Next Image；JavaScript 关闭或动画失败时仍可理解和转化。
- 页面保持浏览器原生滚动，不锁滚轮、不反向滚动、不使用强制吸附。
- 提供暂停/播放或跳过控制；尊重 `prefers-reduced-motion`。

### S02 — 产品路径

以高质量视觉卡片让用户按空间、安装方式或燃料快速进入，并突出 Product Finder。目标是在 3 次点击内进入合适产品。

### S03 — 核心价值

用克制短文案说明设计、真实火焰/仿真效果、源头制造、控制、安全与定制能力。所有事实性声明必须由真实资料支持。

### S04 — Signature Products

展示 3–6 个主推产品。每个产品至少包含场景图、名称、简短定位、关键适配标签、当前市场状态与正确 CTA。

### S05 — 配置体验

提供尺寸、可视面、材质、颜色和控制方式的轻量预览。选择变化时同步更新预览、配置摘要、价格/起售价（有真实数据时）及可售状态。

### S06 — 工程可信度

展示测试、研发、制造、质保、认证和全球项目的内容结构。没有真实证明材料时使用明确占位，不展示虚假数字或徽章。

### S07 — 项目案例

按住宅、酒店、商业与户外场景进入。案例卡片包含地点、空间类型、使用产品和真实图像；详情说明挑战、方案与成果。

### S08 — 分流 CTA

为不同用户提供明确入口：在线购买、预约顾问、项目询价、专业客户、寻找经销商。CTA 根据市场和商品状态动态变化。

## 7. 视觉与品牌方向

### 关键词

高端、克制、建筑感、编辑式、沉浸、真实材质、温暖火光、工程可信度、全球品牌。

### 色彩

- 主体：炭黑、深灰、暖灰、米白。
- 高亮：火焰橙、余烬红或铜色，只选择一组克制使用。
- 每屏限制强调色数量，保证文本对比度达到 WCAG 2.2 AA。
- 不沿用旧 NFT 项目的深海军蓝、荧光绿、紫色按钮或太空视觉。

### 排版

- 大字号编辑式标题 + 短句叙事。
- 正文行长和层级克制、易读。
- 产品规格、安装和资料区域可高密度，但必须用表格、定义列表、分组与留白建立秩序。
- 字体必须拥有 Web 使用许可；未确认品牌字体时使用高质量系统字体回退。

### 图像与动效

- 优先使用真实火焰、高级材质、建筑空间、产品细节、结构与安装图。
- 摄影/渲染保持一致光照、镜头、材质和产品比例。
- 动效节奏慢、有物理感和镜头感，必须帮助理解产品。
- 避免廉价促销风、霓虹科技风、玻璃拟态滥用、无意义粒子、夸张视差、满屏圆角卡片和通用 SaaS 模板感。
- `版本3.mp4` 可作为镜头节奏和氛围参考，但不能直接替代响应式帧序列和静态降级资产。

## 8. 产品发现与 Product Finder

产品列表至少支持以下结构化筛选：

- 燃料/能源
- 安装方式
- 形态与可视面
- 室内/户外或空间类型
- 尺寸
- 价格/询价方式
- 当前市场可售性

要求：

- 筛选状态反映在 URL，可分享、可返回、可被分析。
- 显示活动筛选、结果数量、清空入口、无结果建议和加载/错误状态。
- 移动端筛选抽屉可用键盘关闭并正确管理焦点。
- Product Finder 使用 6–10 个问题收集空间、能源、安装、形态、尺寸和预算偏好。
- 推荐结果必须解释“为什么适合”，允许返回修改答案并进入产品对比。
- P1 为最多 4 个产品对比预留数据结构和入口。

## 9. 产品详情页与轻量配置器

PDP 必须包含：

1. 产品名、系列、价格/起售价、当前市场状态、核心卖点和主 CTA。
2. 场景、正面、侧面、细节、火焰、安装、尺寸、结构和控制媒体；支持全屏与缩放。
3. 尺寸、可视面、颜色、材质、燃烧介质、控制和配件选项。
4. 国家、室内/户外、能源、烟道/通风、供电/燃气、最小空间及电视/家具净距等适配提示。
5. 尺寸、重量、功率、效率/热输出、燃料、容量、运行时间、控制、安全和认证等结构化规格。
6. 安装复杂度、责任边界、现场勘察、包装、交期、物流和安装商信息。
7. 规格书、安装手册、用户手册、CAD、BIM、认证与保修资料。
8. 相关案例、FAQ、质保、服务能力和相似产品。

MVP 配置器使用结构化选项切换静态或预渲染图，生成可复制/保存的配置摘要，并把配置上下文传入购买、询价或预约流程。不要在 Phase 0 为展示效果强行加入重型 3D；只有自由旋转或材质切换确有价值时再按需加载 Three.js/R3F。

## 10. 市场与交易状态

每个 SKU/配置必须通过单一规则层输出：

```ts
type CommerceState =
  | 'BUY_ONLINE'
  | 'QUOTE_REQUIRED'
  | 'CONSULT_REQUIRED'
  | 'DEALER_ONLY'
  | 'NOT_AVAILABLE'
```

状态与前台行为：

| 状态 | 前台行为 |
| --- | --- |
| `BUY_ONLINE` | 显示真实价格/库存/运输提示，可加入购物车并进入托管结账 |
| `QUOTE_REQUIRED` | 展示配置摘要并进入报价表单 |
| `CONSULT_REQUIRED` | 解释需要现场/安装审核并预约顾问 |
| `DEALER_ONLY` | 展示当地授权渠道与经销商查找入口 |
| `NOT_AVAILABLE` | 明确当前市场不可售，推荐替代产品或订阅通知 |

市场选择规则：

- 首次访问可根据 IP/浏览器语言提出建议，但不得强制跳转。
- 用户必须能确认或更改国家、语言和货币，选择需被记忆。
- URL 使用 `/{locale}/{market}/` 或等效可索引结构。
- 语言不等于市场；价格、税、认证、运输、保修和服务按 market 独立配置。
- 未开放市场不得展示无法兑现的 Checkout。
- 结账前再次校验市场、SKU、库存、运输资格和限制。

## 11. 询价、咨询与专业客户流程

主 CTA 根据状态显示 `Buy now`、`Configure`、`Request quote`、`Book consultation` 或 `Find dealer`。

询价/咨询表单至少支持：

- 联系人和客户类型
- 项目类型与国家
- 产品与配置摘要
- 数量、预算和计划时间
- 安装/现场条件
- 图纸或资料上传（原型阶段可模拟并说明）
- 隐私和联系同意

提交成功页/邮件数据结构包含唯一编号和配置摘要。CRM payload 需保留来源页面、产品、配置、UTM、语言、市场和资料下载记录。原型中可记录到本地 mock endpoint，但不能声称已进入真实 CRM。

Professionals 按三类入口组织：

- Architects & Designers
- Hospitality & Developers
- Dealers & Installers

提供服务承诺、典型流程、案例、资料下载、样品/定制说明、项目表单与合作申请。专业账户、经销价和完整 B2B 门户不属于 MVP 核心路径。

## 12. 支持、账户与售后

Support 是购买决策与品牌信任的一部分，不是上线后的附属页面。MVP 至少需要：

- 可搜索的安装、操作、安全、维护、常见问题、保修、配件与服务渠道内容。
- 按产品与市场展示适用手册、维护建议、保修边界和服务联系方式。
- 安全与安装基础资料无需登录即可访问，并清楚标注版本、语言和适用市场。
- 产品注册与售后工单可在 Phase 0 使用原型流程，但数据结构需支持序列号、购买渠道、日期、安装商、凭证以及问题图片/视频。
- 涉及燃气、火焰、电气或结构安全的问题，在提交服务请求前展示明确的紧急安全提示和当地专业服务建议。

账户、订单、地址、收藏、报价、已保存配置和产品注册属于 P1 能力。MVP 可预留入口与接口，但不得用不可用的空壳页面干扰核心购买/询价路径。

## 14. 技术架构

### 核心栈

- Next.js App Router + React + TypeScript（开启严格类型检查）
- Server Components 优先；仅在交互、浏览器 API 或动效需要时使用 Client Components
- Tailwind CSS 或 CSS Modules + Design Tokens
- GSAP ScrollTrigger + Canvas 2D + `requestAnimationFrame`
- Shopify Storefront API + Shopify Checkout + Markets
- Sanity（或 Contentful）管理品牌、案例、技术、资料和多语言内容
- Cloudflare R2 + CDN/Images 或同等级媒体服务
- Algolia 或同等级多语言搜索
- Vercel 或等价 Next.js 部署平台
- GA4 + GTM + Search Console + Web Vitals RUM

### 架构边界

- 商业核心交给成熟平台，不自研支付、订单、税务、库存或仓储系统。
- 商品、内容、媒体、市场和资料分离建模，通过稳定 ID 关联。
- 可预渲染页面尽量预渲染；价格、库存和可售性按业务时效刷新。
- 外部系统通过 repository/adapter 层接入，UI 不直接依赖第三方响应结构。
- 动画资产使用独立 CDN 和版本化 manifest，不打入应用包。
- 第三方脚本必须延迟加载，并接受性能、隐私与故障隔离评审。
- 环境变量提供 `.env.example`，严禁提交密钥。

## 15. Hero 滚动帧实现规范

推荐方案：Canvas 2D 图像序列 + GSAP ScrollTrigger。不要用直接拖动视频时间轴冒充逐帧方案；不要为固定镜头 Hero 强制使用实时 3D。

### 资产

- 桌面 180–240 帧，移动端 100–160 帧，最终以 PoC 实测为准。
- 桌面 1600/1920 宽，平板 1280，移动端 828/960；不同端独立构图。
- AVIF 为主、WebP 回退；首帧单独输出高质量静态图。
- 桌面完整序列目标约 8–12 MB，移动端约 4–7 MB。
- 路径：`scene-name/{breakpoint}/frame-0001.avif`。
- manifest 记录版本、帧数、尺寸、格式、URL 和校验信息。

### 加载与绘制

- SSR 输出首帧并使用 preload/`fetchPriority="high"`。
- 初始仅加载首帧及邻近 8–16 帧；接近 Hero 后分批预取其余帧。
- ScrollTrigger 只更新目标帧索引，绘制统一由 `requestAnimationFrame` 节流。
- Canvas 尺寸随容器和 DPR 变化，DPR 封顶 1.5–2。
- 可用时采用异步解码/`createImageBitmap`；限制并发与内存。
- 离开场景或卸载组件时释放位图、监听器、ScrollTrigger 和 RAF。
- 横竖屏与断点变化时重新计算尺寸和裁切。
- 慢网、低内存、低性能或资源失败时切换低帧率、轻量视频或静态图。

### 可访问性

- `prefers-reduced-motion: reduce` 默认展示静态主视觉或短淡入。
- Canvas 提供可理解的替代说明；关键信息全部存在于 DOM。
- 控件可键盘操作、有可见焦点、正确名称和状态。
- 动画加载不能阻塞滚动、导航或 CTA。

## 16. 响应式与组件状态

至少覆盖 360、390、768、1024、1440 和 1920 像素宽度，并验证常见横屏。

每个交互组件都需要：

- 默认、hover、focus-visible、active、disabled
- loading、empty、error、success
- 长文本、多语言扩展和无图片回退
- 键盘操作和焦点管理
- 触摸目标至少约 44×44 CSS px

不要只实现桌面截图。移动端不是桌面缩小版：Hero 使用独立裁切，筛选、导航、媒体、配置与 CTA 应重新组织信息优先级。

## 17. 性能预算

必须将以下目标纳入实现和验收：

- Core Web Vitals P75：LCP ≤ 2.5s、INP ≤ 200ms、CLS ≤ 0.1。
- 移动端首屏关键资源目标 ≤ 2.0 MB，不包含后续渐进加载的完整帧序列。
- 首屏业务 JavaScript 尽量 ≤ 180 KB gzip。
- LCP 图/首帧不得懒加载；其他图像使用响应式尺寸、AVIF/WebP、明确宽高和懒加载。
- 动效代码、配置器和非首屏功能按路由/组件拆包。
- 不在主线程批量同步解码；真实设备验证动画流畅度和内存。
- 静态媒体使用内容哈希与长缓存；价格/库存避免错误陈旧缓存。

若为了达到预算需要降低视觉复杂度，优先保留内容、导航、CTA 和产品理解，再渐进增强动画。

## 18. SEO

- 产品、系列、案例、技术与文章有服务端可索引 HTML。
- 为各页面生成独立 title、description、canonical、Open Graph 和分享图。
- 配置可扩展的 `hreflang`、本地化站点地图和重定向策略。
- 使用语义化 heading、landmark、Breadcrumb 和内部链接。
- 结构化数据按页面使用 Organization、Product、Offer（仅有真实销售数据时）、BreadcrumbList、Article、VideoObject 和符合政策的 FAQ。
- 图片使用描述性文件名、准确 alt、尺寸和响应式来源。
- 规格使用 HTML 表格或定义列表，不让 Canvas/视频替代正文。
- 为下架产品预留替代推荐及 301/410 策略。

## 19. 无障碍

关键消费者路径目标为 WCAG 2.2 AA：

- 提供跳至主要内容链接、语义化结构、可见焦点和合理焦点顺序。
- 所有功能可通过键盘完成；菜单、对话框、筛选和表单正确管理焦点。
- 表单有持久标签、字段说明、可理解错误和提交状态。
- 文本/控件对比度达标，不仅依赖颜色传达状态。
- 视频默认静音、可暂停，并有字幕或文字说明。
- 尊重减少动态效果；避免闪烁、大幅视差和滚动劫持。
- 筛选、对比、配置和文件下载对辅助技术可用。
- 自动化检查不能替代键盘和读屏人工路径验证。

## 20. 安全与隐私

- 使用 Shopify 托管 Checkout，前台不采集或存储银行卡数据。
- 配置 HTTPS/HSTS、CSP、安全响应头、输入校验、CSRF/XSS 防护和依赖扫描。
- 上传接口预留文件类型/大小限制、恶意文件扫描和速率限制。
- 对表单和搜索提供 Bot/Rate Limit 防护边界。
- CMS、Shopify 与 CRM 遵循最小权限、MFA 和审计要求。
- Cookie 同意前不加载非必要追踪；按市场提供隐私配置。
- 服务端日志不得记录密钥、完整敏感信息或支付数据。
- 提供错误边界和无敏感信息泄漏的用户提示。

## 21. 埋点

建立类型安全的统一 analytics 层；在未接入 GA4/GTM 时输出可测试的开发事件，不把 vendor 调用散落在组件中。

至少覆盖：

- `market_suggested`、`market_selected`、`language_changed`
- `hero_animation_started`、`hero_progress_25/50/75/100`、`hero_skipped`、`hero_fallback_used`
- `product_filter_used`、`finder_started`、`finder_completed`、`product_compared`
- `pdp_viewed`、`variant_selected`、`compatibility_checked`、`resource_downloaded`
- `configure_started`、`configure_saved`、`quote_started`、`quote_submitted`
- `dealer_search`、`dealer_contact`、`consultation_booked`
- `add_to_cart`、`begin_checkout`、`purchase`、`checkout_error`
- `support_search`、`product_registered`、`service_request_submitted`

事件参数避免直接发送个人敏感信息，并包含必要的 market、locale、product/configuration 和来源上下文。

## 23. 开发质量与测试

- 使用严格 TypeScript，不用 `any` 逃避领域建模。
- 组件保持单一职责，避免把整个首页写进一个文件。
- 先为关键业务规则写测试，再实现：commerce state、市场分流、配置摘要、表单校验和 Hero 帧索引/降级逻辑。
- 单元测试：纯业务规则、格式化、筛选、状态映射、analytics payload。
- 组件测试：导航、市场选择器、筛选、配置、动态 CTA、表单错误与减少动态效果。
- 端到端测试：消费者购买/询价、设计师资料与项目表单、移动端导航、键盘路径。
- 运行 lint、typecheck、test、production build。
- 使用 Lighthouse/Web Vitals 检查关键页面，并在至少一台真实或受限性能设备上验证 Hero。
- 检查 404、断网、慢网、资源失败、空结果、无 JavaScript 和第三方 API 失败。

## 24. 完成定义

只有满足以下条件才能声明当前阶段完成：

- 首页不是单屏演示，S01–S08 均已实现并形成清晰叙事。
- 用户在 3 次点击内进入适合的产品发现路径。
- 任何演示市场下，产品都明确显示五种 commerce state 之一及正确 CTA。
- PDP 提供决策所需的媒体、结构化规格、安装、安全、资料与服务信息。
- 询价/咨询流程保留来源、产品、配置、市场与语言上下文。
- Hero 首帧优先、滚动前后可响应；加载失败、减少动态效果和无 JS 时可靠降级。
- 桌面、平板和手机使用合适构图与交互，不存在明显溢出或遮挡。
- 关键路径可键盘操作，自动化无障碍检查无严重问题。
- SEO 元数据、语义结构和结构化内容存在，不依赖 Canvas/视频传达关键信息。
- lint、typecheck、tests 与 production build 通过。
- 对照性能预算给出实际测量结果；若未达标，说明差距和修复计划，不得隐藏。
- README 记录运行、测试、构建、环境变量、架构边界、mock 数据和未接入项。

## 25. 输出要求

实施时按以下顺序输出和执行：

1. 读取 PRD 与仓库现状，列出已确认事实、未知项、风险和验收清单。
2. 给出页面/路由地图、核心数据模型、组件边界和分阶段计划。
3. 先完成设计 tokens、布局骨架、首页 Hero PoC 与可售规则的最小垂直切片。
4. 每个切片执行“实现 → 运行 → 验证 → 修正”，不要只生成代码。
5. 最后报告已完成页面、真实运行证据、测试/构建结果、性能数据、降级验证、仍为 mock 的集成和待业务确认项。

不要复用旧的 `Orbis.Nft` 内容、太空主题、NFT 卡片、荧光绿色系统、社交 CTA 或视频背景页面结构。最终结果必须让人一眼识别为高端壁炉品牌与复杂耐用品选购体验，并完整体现 PRD 的品牌、电商、询价、专业客户、技术资料和售后混合模式。
